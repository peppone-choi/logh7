# ADR-0004 한국어화 방식

- 상태: **제안(우선안 선정)** — 한글 표시 PoC(Linear LOGH-36)로 확정
- 작성: 최병호
- 관련: ADR-0002, docs/l10n/text-format.md, docs/l10n/glossary.md, Evidence E-019~E-021, E-026, E-027

## 맥락 (트랙 B 정적 분석, `evidence:client`)

| 사실 | 근거 |
|---|---|
| 게임 텍스트의 약 98%가 외부 `data\MsgDat\*.dat`(HFWR 포맷, Shift_JIS NUL 종료 문자열 테이블, 21개 전부 파싱 검증, 비어 있지 않은 문자열 4,833개). exe 내부 UI 문자열은 약 2% | E-019, E-021 |
| 문자열에 `$xname$`, `$r10$` 같은 치환 토큰 → 번역 시 보존 필요 | text-format §2.3 |
| 그릴 때 `setlocale(LC_CTYPE,"Japanese")` 후 `mbstowcs` 로 cp932 → UTF-16 변환(`FUN_004eac60`) | E-020 |
| 글꼴은 `CreateFontA(… DEFAULT_CHARSET …, "ＭＳ ゴシック")`(face 문자열 `0x0076e240`), 글자마다 `ExtTextOutA` 로 그려 D3D 텍스처에 캐시, **캐시 키는 UTF-16 코드포인트** | E-026 |
| 네트워크 직렬화: 일반 문자열은 NUL 종료 cp932 바이트열, **캐릭터 이름 등 일부 필드는 `u8 count + u16[]`(UTF-16)** | protocol-draft §2 |
| 자기검증·패커 없음 → 문자열·코드 패치 가능 | E-022 |
| 이미지(버튼·배경)에 박힌 일본어 텍스트 존재 가능 | text-format §1 |

한글은 CP932에 없고, CP949 바이트열은 CP932 선행 바이트 범위와 일부만 겹쳐 CP932 전제 처리(길이·줄바꿈·선행 바이트 판정)를 깰 수 있다.

## 선택지

| | A. 로캘 전환(CP949) | B. CP932 호환 사설 매핑 | C. 유니코드 직접 처리 |
|---|---|---|---|
| 리소스 | MsgDat 를 **CP949** 로 재작성(HFWR 포맷 유지) | MsgDat 를 "한글 음절 → CP932 한자 코드 슬롯" 매핑 바이트열로 재작성 | MsgDat 를 UTF-16/UTF-8 로 확장 |
| exe 변경 | `setlocale` 인자 `"Japanese"` → `"Korean"` 문자열 패치 1곳 + 글꼴명 `ＭＳ ゴシック` → 한글 글꼴명 패치 1곳 | `mbstowcs` 결과에 역매핑 적용(코드 패치 또는 DLL 훅) + 글꼴명 패치 | 로더·직렬화·변환 전반 수정(대공사) |
| CP932 전제 로직 | **깨질 위험**(선행 바이트 판정이 다른 곳에 있으면) | 그대로 유지(바이트열이 여전히 유효한 CP932) | 해당 없음 |
| 표현 가능 한글 | KS X 1001 2,350자 + 한자 | 매핑 슬롯 수(수천) 이내 — 2,350자 충분 | 11,172자 |
| 채팅 입력(IME) | 한국어 IME → CP949 그대로 | 입력값을 사설 매핑으로 변환하는 훅 필요 | 입력 경로 수정 |
| 서버 전송 인코딩 | 일반 문자열 CP949, 이름 필드는 UTF-16 그대로 | 일반 문자열 사설 매핑 CP932, 이름 필드 UTF-16 | UTF-16/UTF-8 |
| 작업량 | **최소** | 중간 | 최대 |

## 결정 (잠정)

1. **A(로캘 전환)를 1순위로 PoC 한다.** 변환이 한 함수에 모여 있고, 글꼴 charset 이 이미 DEFAULT_CHARSET, 글리프 캐시가 UTF-16 키라서 **exe 문자열 2곳 패치 + MsgDat CP949 재작성**만으로 한글이 그려질 가능성이 높다.
2. PoC 에서 CP932 전제 로직(줄바꿈·길이 계산·IME)이 깨지면 **B(사설 매핑)로 전환**한다. B는 바이트열 규칙을 바꾸지 않으므로 안전하다.
3. C는 채택하지 않는다(재검토 조건 참고).
4. 캐릭터 이름은 프로토콜상 UTF-16 필드라 **A/B와 무관하게 한글 이름이 가능**할 것으로 본다(`evidence:guess`, PoC에서 확인).
5. 패치 방법은 ADR-0002와 맞춘다: exe 문자열 패치(배포 런처가 적용) 또는 프록시 DLL 훅 중 PoC 결과가 단순한 쪽.
6. 이미지 속 일본어는 별도 작업(TGA/BMP 편집)으로 P4 에픽에 포함.
7. 번역 리소스는 업데이트 서버(47902)로 배포하는 것을 목표로 한다(ADR-0002 결정 4).
8. 용어는 CLAUDE.md §5 / glossary.md 기준.

## 확정 조건 (LOGH-36)

1. 격리 VM 에서 A 방식 패치본으로 메뉴·대사 1화면 한글 표시 스크린샷
2. 줄바꿈·말줄임이 정상인지, `$…$` 토큰 치환이 정상인지 확인
3. 채팅 입력(한국어 IME)으로 한글 송신 → 서버 → 다른 클라이언트 표시 왕복
4. 결과를 이 ADR에 기록하고 상태를 "채택"으로

## 재검토 조건

- 한글 글꼴에서 글자 폭·높이가 UI 레이아웃과 맞지 않으면 → 글꼴 크기 패치 또는 전용 비트맵 글꼴 검토.
- 서버·클라이언트 모두 CP949 처리가 부담되면 → B로 전환.
- 11,172자 전체 지원이 꼭 필요해지면 → C 재검토.
