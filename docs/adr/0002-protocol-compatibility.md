# ADR-0002 프로토콜 호환 전략

- 상태: 채택 — 단, 게임 클라이언트 주소 가로채기 방식은 P2 스파이크(동적 확인) 후 확정
- 작성: 최병호
- 관련: ADR-0001, ADR-0004, docs/re/connection-flow.md, docs/protocol/protocol-draft.md

## 맥락

- 공식 서버·실 서비스 캡처가 없다. 프로토콜은 클라이언트 정적 분석 + 우리 스텁 서버에 붙여 얻는 로컬 트래픽으로 복원한다.
- 클라이언트 수정은 제약 없음(exe 패치·보호 해제·후킹 DLL 허용, 사용자 소유 오프라인 복제본 한정).
- 확인된 사실 `evidence:client`:
  - 게임 클라이언트 `G7MTClient.exe`에 기본값 `202.8.80.179` / `47900` / `ginei00` 문자열(E-005). 로그인 화면에서 서버 선택이 있다(W p.8) → 서버 목록을 어디선가 받는다.
  - 업데이터 `Gin7UpdateClient.exe`에 `202.8.80.179` / `47902`와 `SERVER.INI` 키(`SERVER_ADDRESS`, `SERVER_PORT`, `PROXY_*`)(E-006) → **설정 파일로 업데이트 서버 주소 변경 가능성.**
  - 패커 흔적 없음, ASLR/NX 없음(E-004) → 바이너리 패치 난이도 낮음.

## 선택지

| | 1. 무패치 + 네트워크 리다이렉트 | 2. 최소 바이너리 패치(주소 문자열/설정화) | 3. 후킹 DLL(프록시 DLL로 `connect`·`gethostbyname` 가로채기) |
|---|---|---|---|
| 방법 | 격리 환경에서 `202.8.80.179`를 로컬(루프백 별칭·NAT)로 라우팅 | exe 안의 IP/포트를 우리 주소로 치환하거나 설정 파일을 읽게 수정 | `winmm.dll`·`dinput8.dll` 등 클라이언트가 로드하는 DLL 이름으로 프록시를 두고 소켓 API 훅 |
| 원본 보존 | 완전 | 낮음 | 높음(exe 무수정) |
| 플레이어 배포 | 어려움(각자 라우팅 설정) | 쉬움(패처 1회 실행) | 쉬움(DLL 동봉) |
| 추가 이점 | 분석 초기 단계에 적합 | 단순 | 한국어화(ADR-0004)·편의 기능 훅과 한 곳에 모을 수 있음 |

## 결정

단계별로 쓴다.

1. **분석·P2(접속 성립) 단계: 선택지 1.** 격리 VM 안에서 `202.8.80.179`를 스텁 서버로 보낸다(원본 무수정으로 "진짜 원본 동작"을 관찰).
2. **플레이어 배포 단계: 선택지 3을 기본, 2를 대안.** 한국어화에도 후킹 DLL이 필요할 가능성이 높아(ADR-0004) 하나의 프록시 DLL에 주소 리다이렉트·텍스트 처리·편의 기능을 모은다. 후킹이 어려운 경우 IP 문자열 패치로 대체.
3. **업데이트 서버(47902)는 우리가 구현한다.** 처음에는 "최신 버전" 응답만 하는 스텁, 이후 원래 업데이트 프로토콜을 복원해 **한국어 패치·클라이언트 수정본 배포 채널로 재사용**한다(`evidence:guess`, 프로토콜 확인 필요).
4. 프로토콜은 **원본 클라이언트 바이트 호환이 기준**이다. 우리 편의로 메시지 형식을 바꾸지 않는다. 확장은 원본이 무시하는 방식(새 opcode는 클라이언트 패치와 짝)으로만.

## 결과

- P2 첫 스파이크: 스텁 서버가 TCP 47900 접속을 받아 첫 패킷을 기록 → 프레이밍 가설(docs/protocol) 검증.
- 서버 목록(`ginei00`) 제공 경로 확인 필요(클라이언트 내장 vs 서버 응답 vs 업데이터가 넘김).

## 재검토 조건

- 클라이언트에 무결성 검사(자기 체크섬)·안티디버그가 발견되면 선택지 2의 비용 재평가.
- 원본이 암호화된 채널을 쓰고 키 교환이 서버 비밀에 의존하면 → 클라이언트 패치로 암호화 우회 필요(스파이크 이슈).
