# ADR-0002 프로토콜 호환 전략

> 세션 2 정정: 로그인 요청의 실제 opcode는 0x7000이며 LGLoginOK의 IPv4는 u32 필드다. 업데이터의 0x80xx는 외부 opcode가 아닌 오류 본문 값이다. 구현은 [최신 로그인 명세](../protocol/login-messages.md)와 [업데이터 명세](../protocol/update-protocol.md)를 따른다. 명령행 인자·서버 주소 반환 전략은 유지한다. `evidence:client` (E-302·E-303).
>
> 세션 3 정정: argv[3]은 실제 게임 로그인 경로에서 0x7000의 첫 계정 문자열로 전달된다. argv[4]는 선택 세션 ID 후보, argv[5]는 둘째 인증 문자열이다. 옛 robot usage 문자열의 "세션 서버 이름" 표기보다 실제 코드 흐름을 우선한다. [세션 로그인 정적 명세](../protocol/session-login.md), `evidence:client` E-311. 동적 상호운용은 미검증이다.

- 상태: 채택 — 명령행 인자 방식(정적 근거 high), P2 동적 확인으로 validated 예정
- 작성: 최병호
- 관련: ADR-0001, ADR-0004, docs/re/connection-flow.md, docs/protocol/protocol-draft.md

## 맥락

- 공식 서버·실 서비스 캡처가 없다. 프로토콜은 클라이언트 정적 분석 + 우리 스텁 서버에 붙여 얻는 로컬 트래픽으로 복원한다.
- 클라이언트 수정은 제약 없음(exe 패치·보호 해제·후킹 DLL 허용, 사용자 소유 오프라인 복제본 한정).
- 확인된 사실 `evidence:client`:
  - 게임 클라이언트 `G7MTClient.exe`에 기본값 `202.8.80.179` / `47900` / `ginei00` 문자열(E-005). 로그인 화면에서 서버 선택이 있다(W p.8) → 서버 목록을 어디선가 받는다.
  - 업데이터 `Gin7UpdateClient.exe`에 `202.8.80.179` / `47902`와 `SERVER.INI` 키(`SERVER_ADDRESS`, `SERVER_PORT`, `PROXY_*`)(E-006) → **설정 파일로 업데이트 서버 주소 변경 가능성.**
  - 패커 흔적 없음, ASLR/NX 없음(E-004) → 바이너리 패치 난이도 낮음.

## 트랙 B 정적 분석으로 추가 확인된 사실 (2026-09-27) `evidence:client`

- `G7MTClient.exe`는 `argv[1]=host argv[2]=port argv[3]=계정 문자열(기본 ginei00) argv[4]=선택 세션 ID 후보(기본 1) argv[5]=인증 문자열(기본 dummy)`를 읽는다. 앞의 필수 인자가 빠지면 로그인 UI 경로로 전환한다. argv[3]과 argv[5]는 0x7000의 두 문자열로 전달되며, 실제 의미는 동적 확인 전까지 candidate다(E-011, E-311; `evidence:client`).
- 로그인 성공 응답 **LGLoginOK(0x7001)** 가 다음 접속용 세션 서버 host·port·token 을 내려준다(E-018) → 세션 서버 주소는 **우리 서버가 결정**한다.
- `202.8.80.179` 는 IP 리터럴이라 `gethostbyname` 실패 후 `inet_addr` 로 처리된다 → **hosts 파일 리다이렉트는 불가**, NAT가 필요(E-014).
- 업데이터는 `update.ini [UPDATE] SERVER_ADDRESS/SERVER_PORT` 로 업데이트 서버를 바꿀 수 있지만 **클라이언트에 인자를 넘기지 않는다**(E-012).
- 자기 체크섬·패커·안티디버그 없음(E-022) → 문자열 패치 가능.
- 통신은 MultiTerm MPS: `[u16 len BE][frame type]`, 0x34~0x36 키 교환, **Blowfish 변형 + 체크섬·시퀀스 봉투**(protocol-draft §1·§3). 가로채기 방식과 무관하게 **서버가 이 암호 계층을 그대로 구현해야** 로그인에 도달한다.

## 결정

1. **접속: 선택지 1(명령행 인자) + 서버가 LGLoginOK 에서 세션 서버 주소를 반환.** 클라이언트 무수정. 분석(P2)과 배포 모두 이 방식을 기본으로 한다. 배포물은 "인자를 붙여 실행하는 작은 런처" + 설정 파일.
2. 업데이터 체인을 쓰고 싶을 때(패치 배포, 결정 4)는 `update.ini` 의 `SERVER_ADDRESS/SERVER_PORT` 로 업데이트 서버를 지정하고, 게임 서버 주소는 **선택지 3(문자열 패치)** 을 병행한다.
3. 선택지 2(NAT)는 분석 중 원본 체인을 그대로 관찰해야 할 때만, 선택지 4(DLL)는 한글화(ADR-0004)에 후킹이 필요할 때 그 DLL에 함께 싣는다.
4. **업데이트 서버(47902)는 우리가 구현한다.** 처음에는 "최신 버전" 응답 스텁(0x6810→0x6811, 0x6820→0x6822 후보), 이후 원래 업데이트 프로토콜(제어 메시지 평문 + HTTP Range 파일 전송)을 복원해 **한국어 리소스·클라이언트 패치 배포 채널로 재사용**한다(`evidence:client` 정적 형식, `evidence:guess` 배포 계획).
5. 프로토콜은 **원본 클라이언트 바이트 호환이 기준**이다. MPS 계층(프레이밍·키 교환·Blowfish 변형·봉투·시퀀스)과 게임 메시지 계층을 서버 코드에서 분리한다(ADR-0001 `server/protocol`). 확장은 원본이 무시하는 방식(새 opcode는 클라이언트 패치와 짝)으로만.

## 결과

- P2 첫 단계: 스텁 서버가 인자로 실행된 클라이언트의 TCP 47900 접속을 받아 **첫 0x34 키 교환 블록**을 기록 → Blowfish 변형·봉투 가설 검증(Linear: 암호 계층 구현 이슈).
- 서버 목록은 로비 0x2005/0x2006 후보 응답으로 제공한다. `ginei00`는 실제 게임 경로에서 기본 계정 문자열이며, 원 서비스의 구체 세션명·목록값은 미확정이다. `evidence:client` E-311·312.

## 재검토 조건

- 키 교환에 서버 비밀(원 서비스 개인키 등)이 필요한 것으로 밝혀지면 → 클라이언트 쪽 키/검증 패치(선택지 3·4)로 전환.
- 인자 실행 시 로그인 GUI가 뜨지 않거나 계정 입력 경로가 달라지면 → 런처 설계 수정.
