# ADR-0001 서버 스택

- 상태: 채택 (2026-09-27) · **개정 2 (2026-09-27): 언어·런타임 원점 재검토 + 게임 서버에서 Spring 제외**
- 작성: 최병호
- 관련: ADR-0002, ADR-0003, ADR-0004, ADR-0005

## 맥락

- 원본 클라이언트는 x86 Win32(2004-04 빌드)이고 WS2_32 **원시 TCP**로 로그인 서버(기본 `:47900`)와 업데이트 서버(`:47902`)에 붙는다. 통신은 MultiTerm MPS: `[u16 len BE][frame type]`, Blowfish 변형·키 교환·체크섬/시퀀스 봉투, 정수 big-endian, 문자열 Shift_JIS(한글화 후 CP949 가능성), 이름 필드는 UTF-16. 메시지 종류 약 300개. `evidence:client` (E-014~E-016, E-024)
- 서버가 모든 커맨드를 처리하고(W p.10), 게임 시간은 실시간 ×24로 쉬지 않으며, 전략 월드와 여러 **전술 RTS 인스턴스**(그리드 단위, 진영당 최대 300유닛)가 동시에 돈다. 전략 커맨드 81개, 조직 121직책, 인사·작전·병참·전술 규칙이 방대하다. `evidence:manual`
- 요구: 동시접속 50명 이상(매뉴얼 설계 한도 세션당 2,000명), **GCP 배포 전제·로컬 연습**(D-2), 가능한 한 빠른 오픈, **1인 개발**.
- 사용자 숙련 스택: Kotlin/Spring Boot, TypeScript/Next.js. (OpenSAM 은 별개 프로젝트로 재사용 대상이 아니다.)
- 세션 2 확인(2026-09-27): 사용자에게 C#/.NET 숙련 여부를 한 번 질문했고, "아니요 — Kotlin으로 진행" 답변을 받았다. 언어 재검토 조건은 충족하지 않아 Kotlin을 유지한다. `evidence:guess` (사용자 결정 D-5).
- 부수 구성요소: 계정 포털·관리 화면(웹), 플레이어용 런처·한글 패치 적용기(Windows), 필요 시 x86 프록시 DLL(ADR-0002/0004), 분석 도구(Python, 기존).

### 결론

- **게임 서버는 Kotlin/JVM 유지.** "객관적으로 모든 면에서 최선"이라서가 아니라, 이 프로젝트의 최대 제약(1인·빠른 오픈·방대한 규칙)에서 **숙련도와 모델링 표현력**이 가장 크게 작용하기 때문이다. Java보다 Kotlin(간결성·코루틴·sealed 계층·DSL).
- **민감도**: 사용자가 C#에 익숙하다면 C#/.NET이 역전한다(숙련 2→4면 약 4.55). 웹과 한 언어로 최대한 빨리 여는 것이 최우선이고 전술 부하가 작다고 확인되면 TypeScript도 대안이다. 이 두 조건 중 하나가 참이면 재검토한다.
- **락인 완화**: 프로토콜 메시지를 **스키마 파일(YAML 등)로 정의하고 코덱을 생성**한다. 언어를 바꾸더라도 스키마·골든 바이트 테스트·규칙 데이터 파일(ADR-0003)은 그대로 옮겨 간다.
- **구성요소별로 맞는 도구를 쓴다**(언어 수는 최소화):

| 구성요소 | 선택 | 이유 |
|---|---|---|
| 게임 서버(게이트웨이·엔진·영속화·운영 API) | **Kotlin/JVM** | 위 결론 |
| 계정 포털·관리 화면 | **Next.js (TypeScript)** | 사용자 숙련, 서버와는 내부 API로만 연결 |
| 플레이어용 런처·패치 적용기, 필요 시 x86 프록시 DLL | **Rust**(1순위) — ADR-0004 PoC 후 확정 | 단일 실행 파일, i686 타깃으로 32비트 DLL까지 한 도구체인. JVM은 부적합 |
| 분석·추출·변환 도구 | **Python** | 기존 도구 계속 |

## 개정 1 — 게임 서버에 Spring이 맞는가

| 관점 | Spring Boot를 게임 서버 JVM에 넣을 때 | 판단 |
|---|---|---|
| 핫패스(Netty TCP → MPS 암호 → tick 엔진 → 인메모리 월드) | 제공하는 것이 거의 없다. Spring의 네트워크 스택은 HTTP 중심, 원시 TCP는 어차피 Netty 직접 | 불필요 |
| 상태 모델 | 요청 스레드풀·`@Transactional`·JPA 엔티티 중심 관성이 **서버 권위 인메모리 상태 + 단일 쓰기 주체**와 충돌(DB 호출이 핫패스에 섞이거나 여러 스레드가 상태를 직접 변경) | 위험 |
| 자원 | GCP 소형 VM에서 컨텍스트 메모리·기동 시간은 순수 비용 | 불리 |
| 대체 수단 | DI → 생성자 주입(필요 시 Koin), 메트릭 → Micrometer 단독, 스케줄 → 엔진 시계, 관리 HTTP → 내장 Ktor, 영속화 → Exposed/jOOQ + Flyway | 충분 |

→ **게임 서버 프로세스에는 Spring을 쓰지 않는다.** 관리 기능이 커져 RBAC·감사·SSO가 필요해지면 별도 프로세스의 관리 백엔드로만 도입을 검토한다(핫패스에는 넣지 않음).

## 결정 (종합)

- 게임 서버: **Kotlin + JDK 25 LTS + Netty 4.2 + kotlinx.coroutines**. 월드 상태 인메모리, **단일 쓰기 주체 tick 엔진**(전략 틱 + 전술 인스턴스별 틱; 전술 인스턴스는 서로 독립이라 코어 병렬화 가능). 패킷·관리 명령 등 외부 입력은 모두 엔진 커맨드 큐로만 들어간다.
- 운영 HTTP: 게임 프로세스에 **내장 Ktor**(내부 주소에만 바인딩) — 헬스체크, Prometheus 메트릭, 관리 명령(커맨드 큐 경유), 조회용 스냅샷.
- 영속성: **PostgreSQL** — 주기적 월드 스냅샷 + append-only 이벤트 로그 + 계정. 접근은 Exposed 또는 jOOQ + HikariCP, 마이그레이션 Flyway(최종 선택·버전 고정은 구현 착수 시 웹 확인). 게임 경로는 DB를 동기 호출하지 않고 전용 IO 디스패처로 write-behind.
- 프로토콜: 메시지 스키마 파일 → Kotlin 코덱 생성, 골든 바이트 테스트.
- Redis 없음(단일 노드 규모에서 불필요).
- 빌드: Gradle(Kotlin DSL). 모듈 `server/protocol`(MPS 프레이밍·암호·코덱) · `server/engine` · `server/gateway`(47900/47902) · `server/ops-api`(Ktor) · `server/persistence` · `server/app`. 웹 `web/`(Next.js). 클라이언트측 도구 `client-tools/`(Rust, ADR-0004 PoC 후).

## 결과

- 프로토콜 명세(`docs/protocol/`) ↔ 스키마 ↔ Kotlin 코덱을 1:1로 대응시켜 골든 바이트 테스트로 고정한다.
- 엔진 밖(게이트웨이·운영 API·영속화)은 엔진 상태를 직접 바꾸지 못하고 커맨드/이벤트로만 소통한다 — 코드 리뷰 기준.
- 단일 프로세스라 장애 시 전체 중단 → 스냅샷 주기와 재기동 복구가 운영 핵심(ADR-0005).
- Linear: LOGH-17(서버 골격)·LOGH-45(관리 API·화면)·P6 설명의 "Spring Boot" 표기, LOGH-26(런처)의 구현 언어를 이 ADR에 맞춰 갱신한다.

## 재검토 조건

- 사용자가 C#에 익숙하다고 확인되거나, 웹과 단일 언어로 가야 할 이유가 생기고 전술 부하가 작다고 측정될 때 → 언어 재검토(스키마·테스트·규칙 데이터는 이식).
- 동시접속이 단일 JVM 한계에 가까워질 때 → 세션 단위 수평 분할.
- 관리 기능에 RBAC·감사·SSO가 필요해질 때 → 별도 관리 백엔드.
