# 유지보수 절차

작성: Peppone Choi ([peppone-choi](https://github.com/peppone-choi)) · 2026-11-06 · 체크리스트 14장 "유지보수 공지→신규 입장 제어→…→재개"

## 서버 기능

- **공지**: `/admin`의 유지보수 절에서 보내거나 `POST /commands/notice`(본문=공지, `X-LOGH7-Operator` 헤더)로 보낸다.
  - 접속 중인 모든 플레이어에게 `[운영] …` 지점 채팅 한 줄로 간다. 황위 계승 알림 같은 기존 서버 알림과 같은 방식이다.
  - 공지는 1~60자이며 제어 문자를 쓸 수 없다.
  - 원본의 채팅 영역이 한 줄 높이이면 긴 공지의 마지막 부분부터 보일 수 있다. 스크롤로 앞부분을 확인할 수 있으며, 점검 시각·상태는 짧은 문구로도 알린다.
  - 감사 기록은 ASCII만 받으므로 공지는 원문 대신 `chars:<길이>+sha256:<앞 16자>`로 남긴다.
- **신규 입장 차단**: `/admin`의 「새 로그인 차단/허용」이나 `POST /commands/maintenance/on|off`로 바꾼다.
  - 차단 중에는 새 로그인에 원본 클라이언트의 로그인 실패 응답을 보낸다.
  - 이미 접속한 플레이어는 끊지 않는다.
  - 원본 클라이언트의 실패 창에는 점검 문구가 없다(`evidence:client`). 차단 전에 게임·런처·웹으로 점검을 알린다.
- **감시**
  - `logh7_maintenance_closed`(0/1)와 `logh7_maintenance_refused_logins_total`을 내보낸다.
  - 차단으로 거부된 로그인은 로그인 실패 계수(`login_rejected_total`)에 넣지 않는다. 계획된 점검이 로그인 실패 경보를 울리지 않게 하기 위해서다.
- **개별 접속 종료**: 대상 세션의 운영 포트에서 `/admin`을 열고 「현재 세션의 플레이어 접속」의 세션 이름과 번호를 확인한다. 계정의 연결을 선택한 뒤 「선택한 접속 종료」를 누른다. 운영 인증(공유 토큰 또는 운영자 계정)과 감사 파일을 설정해야 이 조작을 사용할 수 있다.
  - 현재 입장한 연결만 선택할 수 있다. 접속을 새로 열면 새 연결 ID를 받으므로, 이전 화면에서 종료를 요청하면 404와 새로 고침 안내를 받는다. 다른 플레이어의 연결과 재입장 권한은 유지된다.
  - 원본 클라이언트는 기존 「접속 종료」 창을 보여 준다. 감사 파일은 `PLAYER_DISCONNECT` 요청·결과와 대상 연결을 기록한다.

## 순서(현재 도구로)

1. **공지**: 점검 시각과 예상 시간을 공지한다. 필요하면 여러 번 보낸다.
2. **신규 입장 차단**: `maintenance/on`
3. **진행 중 작업 정리**: 남은 플레이어에게 마지막 공지를 보낸다.
   - 명령·이동 예약은 저장 상태에 남고, 재시작 뒤 재개된다(오프라인 정산·재시작 복구 검사 범위).
   - 운영 화면을 새로 고침해 현재 접속을 확인한다. 개별 종료가 필요한 연결은 그 목록에서 선택한다.
4. **저장**: `POST /commands/backup`으로 실행 중 백업을 만들고 `state_backup.py verify`로 확인한다([백업](backup.md)).
5. **배포·재시작**: 서버를 정지한다. 그다음 `server_release.py install/activate`로 새 릴리스를 켜고 다시 시작한다([백업](backup.md#서버-릴리스-전환롤백-2026-11-03)).
6. **재개**: 재시작한 서버는 차단이 꺼진 상태로 시작한다. 차단 상태는 메모리에만 있다. `/health` 200과 `logh7_engine_up` 1을 확인한 뒤 공지로 재개를 알린다.

## 확인 범위

- 로그인 교환 시험: 차단 중에는 맞는 비밀번호도 실패 응답과 REJECTED 상태가 된다. 차단 횟수만 늘고 로그인 실패 계수는 늘지 않는다. 해제 뒤에는 정상 인증된다.
- 운영 API 시험: 켜기 CHANGED·다시 켜기 UNCHANGED·잘못된 모드·빈/61자 공지 거부·공지 전달, 지표, 관리 화면 표시와 감사 순서를 확인했다.
- 로컬 실서버: 켜기·공지가 `changed`를 돌려줬다. 지표 `logh7_maintenance_closed 1`과 감사 요청·결과 두 줄씩 남은 것도 확인했다(월드 없는 최소 서버라 공지 수신자는 0명).
- 원본 확인(2026-11-06): `work/maintenance-native-20261106`의 별도 복원 저장과 루프백 48330~48333에서 main `64881792`를 실행했다. run-04는 차단 중 원본 로그인 실패 창과 차단 계수 1·인증 실패 계수 0을 확인했다. 같은 서버에서 해제한 뒤 run-05의 정상 입장과 `Fresh : [운영] 점검 공지 시험` 표시를 확인했다. 다시 차단한 뒤에도 기존 접속의 새 창고 조회와 공지 수신이 유지됐다. 원래 spot 공지 경로로 확인했으며 별도 표시 패치는 추가하지 않았다. 긴 공지의 앞부분도 원본 위쪽 스크롤 버튼으로 확인했다.
- 작은 재시작 확인(같은 날): 접속 중 만든 백업 12개 파일을 검증하고 원본·서버를 종료한 뒤 같은 main으로 재기동했다. `/health` 200·엔진 지표 1·차단 지표 0을 확인하고, run-06의 정상 재접속과 `[운영] 점검이 끝났습니다.` 표시·개요 창의 인구 보존을 확인했다. 정지한 시험 저장을 기존 원본과 대조해 오딘 거점 전체 상태·국가 금고·예산 기록과 qafresh의 국가/함정 스타일·위치·이동 횟수·기함·화물·항속·명령을 보존하고 행동 CP 차감이 없음을 확인했다. run-04~06은 무음·Job 0·원본 해시 보존을 확인했고 시험 서버도 종료했다. 원본 게임 파일·주 서버 저장·Docker는 변경하지 않았다.
- **남은 범위**: 진행 중 이동·생산·직무를 가진 유저의 정리와 전체 CP/직위 중복 방지, 복수 세션의 원본 입장·공지, 새 릴리스로 교체하는 리허설. 이번 인물에는 진행 중 항행 명령이 없었다. 위 소규모 확인으로 체크리스트의 전체 유지보수를 완료 처리하지 않는다.

### 개별 접속 종료 (2026-11-07)

암호화 TCP 두 접속 중 운영자가 선택한 연결만 닫혔다. 같은 계정의 재접속 뒤 이전 연결 종료 요청이 거절됐고, 재접속한 플레이어와 다른 플레이어는 모두 시각 요청에 계속 응답했다. 운영 API는 무인증·다른 출처·인증 또는 감사 미설정의 조작을 거절했고, 허용된 요청과 결과는 감사 파일에 기록했다.

로컬 운영 화면을 헤드리스 Chrome으로 열어 실제 접속을 선택하고 종료했다. 1920×1080 원본의 「접속 종료」 창에서 결정 버튼으로 정상 종료했다. 같은 계정의 기존 인물로 다시 입장해 전략 요청을 계속 처리했고, 브라우저에서 이전 연결 ID를 재전송하자 404가 돌아왔다. 감사 결과는 `CHANGED`와 `NOT_FOUND`였고 재접속 창도 정상 종료했다. 원본 해시·전경과 커서·사전 무음·Job 0을 확인했다. 자료는 `work/operator-disconnect-20261107`에 있다.

공통 로비에서 같은 계정으로 Alpha·Beta에 동시에 암호화 접속했다. 두 운영 화면에 각각 `Alpha (1)`·`Beta (2)`가 표시됐고, 브라우저에서 Alpha를 종료하자 Beta는 기존 연결에서 인물 조회에 응답했다. Alpha의 이전 ID로 Beta에 종료 요청을 보내거나 Alpha 재입장 뒤 요청을 반복하면 둘 다 404가 반환됐다. Alpha의 새 연결도 인물 조회에 응답했고 두 세션에 각자 감사 결과가 남았다. 자료는 `work/operator-disconnect-multisession-20261107`에 있다. 두 원본 동시 접속과 공개 운영 환경의 조작은 미확인이다.
