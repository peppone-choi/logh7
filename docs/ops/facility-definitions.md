# 시설 정의 편집
작성: Peppone Choi ([peppone-choi](https://github.com/peppone-choi)) · 2026-11-06 · 체크리스트 14장 운영 편집

운영자가 시설 이름을 바꾸고, 그 시설이 무엇을 하는 곳인지(용도)와 이용 조건 안내를 적는다. 관리 화면 `/admin/facilities`.

## 무엇을 바꾸나
- **종류 정의**: 시설 종류(원본 시설 분류 0~38)마다 이름·용도·이용 조건. 같은 종류의 모든 시설에 적용된다.
- **거점별 재정의**: 시설 하나(시설 ID = 거점 ID×100+종류+1)의 이름·용도. 비운 칸은 종류 정의를 따른다.
- 이름을 비우면 서버 기본 이름(원본 분류명의 한국어 직역)을 쓴다. 종류 번호·시설 ID·원본 규칙 문자열은 바뀌지 않는다.
- 이용 조건은 안내 문장이다. 실제 출입은 방별 접근·소속·직위 판정을 따른다. 기본 문장은 설계 추정(`evidence:guess`)이며 운영자가 고칠 수 있다.
- **지원 명령**은 서버의 실제 직무 카드에서 시설별로 모은다. 행정·방위 직위는 해당 물리 시설에 연결한다. 직접 연결된 직무 명령이 없으면 개인·부대 명령은 해당 직무 카드에서 확인하도록 안내한다. 이 화면은 명령을 추가하지 않는다.
- 한도: 이름 24자, 용도·이용 조건 200자, 줄바꿈·제어 문자 금지.

## 저장과 게임 반영
- 원천은 국가 정의와 같은 PostgreSQL(`LOGH7_DEFINITIONS_JDBC_URL`)의 V4 표(`facility_definition_revision`·`facility_kind`·`facility_override`)다. 행이 없는 종류는 서버 기본값을 쓴다. 이행: `psql -v ON_ERROR_STOP=1 -f server/persistence/src/main/resources/db/migration/V4__facility_definitions.sql`.
- 편집은 국가 정의와 같은 운영자 로그인·Origin 검사·버전 충돌(409)·감사 기록(`FACILITY_DEFINITION_EDIT`)을 쓴다. 감사 기록이 없으면 저장하지 않는다(503).
- 게임은 메모리 게시본 `PublishedFacilityDefinitions.current()`를 읽는다. 저장 직후 바로 게시하고, 서버는 5초마다 DB를 다시 읽는다. 더 낮은 버전은 게시하지 않는다(역전 방지).
- DB가 없으면 기본 정의를 읽기 전용으로 보여 준다. DB에 V4가 없거나 연결이 끊기면 마지막 게시본을 유지하고 서버 시작을 막지 않는다(국가 정의는 시작을 막는다).
- 게임의 정보 메뉴 → 행성·요새 → 시설·스폿에서 시설 이름을 선택하면 **용도 / 이용 조건 / 지원 명령**을 읽는다. 시설 목록의 이름은 서버 게시본을 따르며, 거점별 재정의가 종류 정의보다 우선한다. 24자 이름은 상세 제목에 전부 표시하고 목록 버튼은 12자를 넘으면 줄인다. 설명은 200자까지 여덟 줄 안에 표시한다.
- 열린 안내는 10초마다 갱신한다. 목록에 보이는 시설도 차례로 조회한다. 조회는 MCP를 소비하지 않으며 실제 명령 실행·출입 권한은 기존 서버 판정을 따른다.
- 원래 **원거리 이동 / 근거리 이동** 메뉴와 **현재 시설 HUD**도 서버 이름을 사용한다. 같은 거점의 시설 이름은 설명의 첫 쪽만 조회해 캐시하고, 현재 시설은 10초 주기로 다시 조회한다. HUD는 갱신된 이름을 표시하며 이미 열린 이동 메뉴는 다시 열면 갱신된다. 버튼은 최대 12자(긴 이름은 말줄임표), 전체 이름은 안내창에서 읽는다. 이동 목록은 원본이 붙이던 내부 번호 `[ID]`를 표시하지 않는다([근거](../protocol/world-navigation.md#이동-목록의-내부-번호-숨김-2026-11-10)). 메뉴를 닫아도 이름을 유지하고 새 로그인 때 캐시를 비운다. 350개를 넘으면 오래된 항목을 교체하며 낮은 버전은 게시하지 않는다. 다른 직무 문구 등 모든 고정 시설명 서식이 이 경로를 쓰는 것은 아니다.
- 전송은 원본 직무 조회 `032e/032f`의 표시 전용 모드 6을 사용한다. 시설 ID와 요청 토큰을 대조하고 이름 1쪽·용도 3쪽·이용 조건 3쪽·명령 2쪽을 같은 버전으로 모두 받은 뒤 게시한다. 구버전·다른 시설·손상·부분 응답은 표시를 덮어쓰지 않는다. 명령 안내 한도는 192자다. 원본 자산은 수정하지 않는다. `evidence:guess`(확장 프로토콜·안내 배치)

## 확인
- 검사: 엔진 4개(기본값 39종·재정의 우선·검증·게시 역전 방지), PostgreSQL 3개(재열기 보존·동시 편집 1건만 반영·V1~V3만 있는 구형 DB에서 국가 유지와 시설 사용 불가 보고), 운영 화면 1개(로그인·Origin·충돌·감사·게시·DB 장애 시 읽기 전용).
- 실서버 리허설(`work/update-rehearsal-20261106/facility`, Git 제외): 전용 QA PostgreSQL(tmpfs)에 국가 정의 덤프와 V4를 적용하고 서버를 띄웠다. 종류 22 이름·용도 저장, 오딘 황궁(시설 104923) 재정의 저장, 오래된 버전 409, 25자 이름 400을 확인했다. 서버를 다시 시작해도 버전 2와 두 편집이 그대로였고, 재정의 지우기 뒤 종류 이름으로 돌아갔다. 감사 기록은 CHANGED 3·CONFLICT 1·INVALID 1. 화면은 브라우저로 확인했다. 컨테이너는 지웠고 Docker 볼륨 163개는 그대로다.
- 원본 연동 확인(`work/facility-guide-native-20261106`, Git 제외): 별도 PostgreSQL 18(E: 바인드 디렉터리)과 QA 서버에서 공통 이름 ‘행성 행정청’과 거점 1049의 ‘오딘 민정청’·151자 설명을 저장했다. 브라우저 폼에서 이용 조건을 제출해 버전 2→3으로 바꾸고, 접속 중인 원본의 세 안내 탭과 공통/거점별 이름 우선순위를 확인했다. 오래된 버전 409·25자 이름 400도 확인했다. DB 컨테이너와 서버 재시작 후 같은 버전·이름·설명·이용 조건이 보존되고 원본 재접속에 표시됐다.
- 추가 검사: 프로토콜 2개(최대 길이·9쪽 배치·잘못된 요청), 게이트웨이 2개(게시 갱신·재정의·실제 명령·시설 소멸·암호화 통신), 운영 화면 1개(수정된 이름의 선택 목록 포함), x86 DLL `/W4 /WX`·guard(페이지 혼합·오래된 응답·손상·긴 한국어 줄바꿈).

## 백업·복원 (2026-11-06)
시설 정의는 국가 정의와 같은 DB에 있으므로 정의 DB 백업(`pg_dump --format=custom`)에 함께 들어간다. 복원 순서는 [백업](backup.md#국가-정의-db와-릴리스-복귀-2026-11-06)의 정의 DB 복원과 같다.

리허설(`work/update-rehearsal-20261106/facility-restore`, Git 제외, main `2c455a93`, 원본 클라이언트 실행 없음):
- 전용 QA PostgreSQL(tmpfs, 127.0.0.1, 새 볼륨 없음)에 국가 정의 덤프와 V4를 적용한 원본 DB를 만들고, 서버의 `/admin/facilities`로 종류 2개(22·3)와 거점 재정의 2개(시설 104923·105003)를 저장했다. 정의 버전 0→4.
- `pg_dump -Fc` 목록에 `facility_` 표 3개가 들어 있었다. 다른 DB에 `pg_restore --no-owner --exit-on-error`로 복원하자 32개 표의 건수·내용 해시가 원본과 모두 같았다(`facility_definition_revision` 1행·`facility_kind` 2행·`facility_override` 2행 포함).
- 복원 DB로 서버를 다시 띄우자 정의 버전 4와 네 편집(종류 이름·용도, 두 재정의)이 그대로 보였다.
- 컨테이너는 지웠고 Docker 볼륨 163개는 그대로다. 운영 DB의 정기 백업 연결은 미확인이다.
