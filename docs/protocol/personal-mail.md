# 개인 명함 교환과 편지 보관

작성: 최병호 · 2026-10-29

`07fcaf0` 기반 `korean-stage5-wt`의 첫 서버 연결 묶음이다. 개인 주소 등록·받은함/보낸함·송신·읽음·개별 삭제·파일 재개방을 구현했으며 **새 Kotlin 빌드·서버 검사·원본 실기는 아직 실행하지 않았다.** 앞 run-288은 빈 받는 이 창까지만 확인한 실행이다. 이 문서를 실제 메일 송신 완료 증거로 사용하지 않는다.

## 범위와 근거

[매뉴얼 03](../manual/03-communication.md)의 개인 주소 명함 교환, 주소록 100개, 수신함 120통, 주소록 밖 상대에게 답장, 전술 중 수신 불가를 따른다. 개인 주소는 로그인 계정·인물·세션 세대에 묶는다. **직무 주소·직무 승계·망명 주소록 초기화, 메신저, 건의 편지는 이번 묶음에서 연결하지 않았다.** `evidence:manual`

원본 정적 분석은 기존 `logh7-client-triage` 및 `logh25-host-20261008` 산출물과 읽기 전용 CD EXE를 사용했다. 새 실행·분석 케이스나 원본 수정을 하지 않았다. 주요 경계는 다음과 같다. `evidence:client`

| 코드 | 원래 형식과 연결 |
|---|---|
| `0f04/0f05` | 빈 조회 → u8 개수 + SimpleInformationCharacter 목록. 최초 부트스트랩은 월드 표시 전에도 계정 자신의 주소록만 읽을 수 있음 |
| `0f0b` | 두 SimpleInformationCharacter + 상태/결과 u8. 원본 `0054a3d0`의 요청 1 → 상대 요청 표시 2 → 상대 응답 3 → 결과 4 연결 |
| `0f0c` | 상대 SimpleInformationCharacter. 인증된 자기 주소록에서만 해당 ID 삭제 |
| `0f08/0f09` | 주소 SimpleInformationCharacter + 두 플래그로 조회. Begin → `0f0a` 항목들 → End(0). 조회 플래그는 되돌려 주며 개인 주소만 허용 |
| `0f0a/0f10` | InformationMail의 ID/ref u32, 읽음 u8, 송·수신 SimpleInformationCharacter, 날짜 u32, 제목 u8 길이+UTF-16BE, 본문 u16 길이+UTF-16BE |
| `0f11/0f12` | 주소 SimpleInformationCharacter + 받은함 여부 u8 + 메일 ID u32. 소유자 확인 뒤 읽음/해당 보관함 사본 삭제 |

SimpleInformationCharacter의 네이티브 0x124바이트 구조체를 wire에 그대로 쓰지 않는다. 이름·칭호는 길이에 NUL을 포함하며 빈 값은 길이 0으로 쓸 수 있다. 선택 부대/거점과 최대 네 직무 항목은 파서에서 길이를 확인하며 읽지만 개인 주소 출력에는 넣지 않는다. 끝의 세 값은 얼굴 ID·나이 계산값·주소 구분값이며 마지막 주소 구분값이 0인 개인 주소만 이번 API가 처리한다. 얼굴·나이가 0이 아니어도 개인 주소다. wire의 이름·계급·얼굴·나이·날짜·메일 ID를 계정 권한이나 서버 저장 원본으로 믿지 않는다.

InformationMail의 native writer `0045aca0`, reader `00472e40`과 이전 입력 경계 조사에 맞춰 제목 127·본문 511 UTF-16 단위까지 허용한다(NUL 각각 한 단위 별도). 잘린 길이·뒤 여분 바이트·중간 NUL·서로게이트·허용 밖 제어 문자는 거부한다. 본문의 CR/LF/탭은 보존한다. 빈 wire 필드는 원작 코덱처럼 허용하며 빈 제목의 기본 문구는 원래 작성 UI가 제공한다. 한국어·일본어·영문은 UTF-16로 보관하고 리소스용 사설 글리프는 서버 저장에 쓰지 않는다.

## 인증·교환·배달

`GameExchange`는 기존 GAME 티켓, 시작 상태, 현재 계정의 등록 인물을 확인한다. `GameCommunication`은 세대와 인물→계정 대응을 다시 확인하고, 변경 요청에는 공개된 `GamePresence`의 연결/인물/세대를 요구한다. 주소록 초기 조회만 아직 월드가 공개되지 않은 부트스트랩을 허용한다. 파일 I/O는 전용 단일 실행자에서 처리하며 기존 pending-world 응답 경계로 반환한다.

명함 교환은 같은 그리드의 같은 실제 스폿/방 소유자 또는 같은 소속 부대의 채팅 문맥에서만 요청한다. 상대 연결에 60초 임시 요청을 보내고, **그 상대 연결의 명시적 수락** 뒤 두 주소록을 한 저장으로 갱신한다. 거절·만료·방 이동·재접속·요청 없는 수락은 등록으로 이어지지 않는다. 주소록 삭제는 상대 주소록을 지우지 않는다. 요청 수 1,024개 및 이름 표시 최대 12단위는 이 서버의 제한/표시 정책이다. `evidence:guess`

편지는 주소록 등록 여부와 독립적으로 현재 세대에 등록된 인물에게 보낼 수 있어 수신 편지의 답장도 허용한다. 오프라인 상대도 같은 보관함에 저장된다. 온라인 상대에게는 현재 받은함/보낸함 선택을 유지하는 목록 갱신을 보내며, 전술 중 수신은 서버의 현재 상태에서 거부한다. 송신자 표시와 수신자 표시, 날짜는 서버 자료로 채운다. 읽음 상태는 하나의 원본 레코드에 저장하고 받은함 삭제·보낸함 삭제는 독립 플래그로 남긴다.

CD의 일반 메일 캐시는 `00457774 + 100 × 0x75c = 00485764`에서 바로 다음 객체와 맞닿는다. `004c26a4`도 100을 검사한다. 따라서 **서버는 120통을 보관하되 클라이언트에는 최신 100통만 보낸다.** 현재는 화면의 메일을 지워야 더 오래된 20통이 나타나며 별도 페이지 UI는 없다. 매뉴얼의 120통을 이유로 native 배열 한도를 120으로 바꾸지 않았다. 보낸함도 120통, 전체 저장 레코드 100,000개·소유자 4,096개를 상한으로 둔다. 보낸함/전체 상한은 소실된 원서버 규칙으로 확정한 값이 아니라 로컬 구현 정책이다. `evidence:client`(배열) / `evidence:guess`(출력·저장 정책)

## 영속성과 중복

캐릭터 파일이 있으면 같은 폴더의 `<캐릭터 파일명>.mail.session-<세대>`를 사용한다. 세대가 바뀌면 이전 파일은 보존하고 새 파일을 연다. 캐릭터 파일 없이 만든 시험 Gateway는 메모리 저장소이므로 프로세스 재시작 보관을 보장하지 않는다.

`FileCommunicationStore`는 별도 lock 파일의 배타 잠금, 버전/세대·ID·소유자·개수 검사, 임시 파일 강제 기록, 같은 디렉터리의 원자 교체를 사용한다. 송신 보관·수신 원본·작업 키가 한 상태에 들어가며 저장 성공 뒤에만 메모리 상태와 알림을 공개한다. 교체 실패 시 이전 파일과 메모리 상태가 유지된다. 디렉터리 메타데이터의 전원 장애 내구성은 OS/파일시스템에 의존한다.

같은 서버 작업 키로 재시도하면 기존 메일 ID를 돌려주고 삭제한 사본을 되살리지 않는다. 같은 키에 내용/상대가 달라지면 거부한다. 호환 DLL은 원래 송신 직전 CALL `004b4c93`에서 기존 요청 ID/ref 두 필드에 무작위 63비트 요청 키를 넣는다(ID는 -2 이하, ref는 나머지 32비트). 서버는 인증 계정·인물·세대 파일에 묶인 키로 저장하고 재접속/저장 재개방 뒤 같은 요청을 재수신해도 새 메일·배달 알림을 만들지 않는다. 송신 성공 ACK에서만 ref를 되돌려 대기 중 요청과 대조하며 보관함 항목의 ref는 기존 -1을 유지한다. 새 사용자 송신은 새 키여서 같은 내용 두 통을 임의로 합치지 않는다. 이 필드 사용은 **대체 서버와 호환 DLL의 확장 정책이며 원작 서버 규칙으로 확정하지 않았다.** 별도 wire 필드를 추가하거나 원본 직렬화/암호화를 대체하지 않는다. `evidence:guess`

수정하지 않은 ID=0 클라이언트 요청은 이전처럼 수신마다 UUID를 쓰므로 연결을 넘어선 요청 중복을 식별하지 못한다. 새 DLL도 응답 없는 요청을 자동 재전송하지 않으며 프로세스를 완전히 종료하고 사용자가 새로 작성한 송신은 다른 요청이다. 삭제된 양쪽 사본도 중복 방지를 위해 저장 레코드로 남으며 전체 상한에 포함된다. 편지 처리에 별도 CP·자금 차감은 없다.

## 정상 거절과 한국어 초안 보존 후보

원본 `004391f0`은 0500의 type/error/count/UTF-16를 읽고 `004ba2b0`의 0500 분기는 `world+448600`에 복사한 뒤 원래 화면 로그 이벤트 0x17을 전달하고 대기 요청을 정리한다. `00516bf0`은 문구를 원래 채팅/시스템 로그에 추가한다. 이 분기에 직접 접속 종료는 없으며 0501은 디버그 출력 경로다. **별도 오류 모달이나 편지 전용 NG 플래그를 발견한 것은 아니다.** reader 허용 count는 128이지만 dispatch가 count 뒤에 NUL을 하나 더 쓰므로 송신 count는 NUL 포함 최대 127(실제 문구 126단위)로 제한한다. `evidence:client`

`MailMessages.rejected`는 type에 거절한 opcode, error에 0을 쓴다. 예를 들어 제목/본문 오류는 평문 `00000000 0500 0f10 00 03 c2e4 d328 0000`(“실패” 문구의 최소 예) 형태이며 기존 세션 암호화로 전송한다. **type/error의 원래 enum 의미는 미확정**이고 위 값으로 송신 요청을 식별하는 것은 서버/DLL 정책이다. 일반 원본에도 문구와 대기 큐 정리 경로는 있지만 이 값의 실기 수용은 미확인이다. `evidence:guess`

잘못된 수신자·내용·전술 중 상대·보관함/전체 용량·읽음/삭제 불가·요청 키 충돌은 인증 검증 뒤 0500 목록을 반환한다. 저장/배달/성공 ACK는 만들지 않아 기존 pending-world 정상 완료 경계에서 연결을 유지한다. 인증된 계정/인물 불일치·옛 연결/세대·직무 주소 위조·손상/잘림/길이 형식을 어긴 패킷은 계속 예외다. 원자 저장 I/O 실패 역시 정상적인 게임 거절로 숨기지 않는다. Unicode로 파싱할 수 있는 제목의 허용 밖 제어 문자는 내용 거절이며 잘린 UTF-16/NUL 계약 위반은 손상 패킷이다.

DLL의 `004fd32f`(편지 UI tick), `004b8a78`(decode 뒤 원본 dispatch), `004b4c93`(원본 송신) 세 CALL을 전체 바이트 대조 후 연결한다. `mail_delivery.h`는 UI 스레드에서 개인 송신 한 건만 대기시키고 제목/본문/수신인을 보존한다. 원래 송신 직후의 두 모드 전환을 지연하고 편집·수신인 변경·송신 버튼을 잠근다. 실제 0f10 성공 ACK의 송신자/수신자/ref 일치 때만 기존 완료 전환을 호출한다. 대응하는 0500은 같은 작성창이 열려 있을 때 두 wide 편집기에 초안을 되넣고 입력을 허용한다. 창을 닫았으면 자동 재열기/다른 초안 덮어쓰기를 하지 않는다. 다른 opcode/세션/요청의 성공 통지는 무시한다. 로그인 주체가 바뀌면 대기를 해제하고 자동 재송신하지 않는다. 송신 전 CP949·127/511 경계와 BMP/NUL/제어 문자·수신인 ID도 검사한다.

추가 C++ 상태 검사는 대기 중 중복 차단·엉뚱한 세션/상대/ref 무시·거절 뒤 한국어 초안 보존·다음 작성과 성공 전환을 대상으로 **작성만 했다**. 실제 x86 ABI, 잠금/취소/닫기, 한국어 로그·초안 복귀·재편집과 같은 연결의 정상 재송신은 빌드/실기 담당이 확인해야 한다. **예전 연결 종료 문제의 후보 코드를 수정했지만 실행 검증 완료로 표시하지 않는다.**

run-342는 직전 월드·편지를 복사하고 시험 프로필과 주소록 별칭만 `김 하나`/`이 둘`로 바꿨다. 앞서 L7M2로 저장한 답장의 얼굴·제목·본문이 실제 두 원본 재시작 후 유지됐다. 이 결과로 앞 단락의 새 형식 네이티브 재접속 미확인을 갱신한다. 원본 게임 데이터나 일반 계정 파일을 변경한 시험은 아니다.

첫 친구 이름 보완은 Unicode 셀을 한 번만 고쳤다. run-342의 친구 목록과 수신인 칸에는 CP949를 CP932로 해석한 반각 가나가 남았다. run-343 진단에서 원래 캐시와 ctor/row helper 인수는 정확한 한글이었고 새 호출도 설치돼 있었지만, 이후 실제 셀 풀은 다시 반각 가나였다. 원본 `00577660`이 보관된 ANSI CString으로 전체 0열을 재작성하는 것을 확인했다. `evidence:client`

`office_labels.h`는 원래 CString·길이·인물 ID를 그대로 보존하고, 일반 셀 설정 `00576b05`와 전체 재표시 `005776a9`에서 정확한 list/root/table, 현재 행의 인물 ID, 원래 CString 바이트가 일치할 때만 현재 친구 캐시의 UTF-16 이름을 표시한다. 목록 시작에서 결합을 비우므로 닫기/재개방과 다른 목록에 이름을 전용하지 않는다. run-344의 두 원본에서 `이 둘`/`김 하나`와 초상, 행 선택 후 및 재개방 후의 이름 유지를 확인했다. 실제 선택 송신은 ID10000→10001과 한글 제목/본문, 서버 ACK도 대조했다.

이 송신에서 얼굴·나이가 들어간 개인 주소를 DLL의 기존 즉시 갱신 관찰자가 직무 주소로 오인하는 회귀도 발견했다. `personalMailAddress`는 서버와 같이 `+120..123` 주소 구분만 확인하며 `+118` 얼굴과 `+11c` 나이 계산값을 개인 주소 거절 근거로 쓰지 않는다. guard에 얼굴·나이가 0이 아닌 개인 주소 및 주소 구분 네 바이트 각각의 거부 검사를 추가했다. run-345에서 두 원본의 송신 후 상대가 편지함을 다시 열지 않은 상태로 005→006통과 새 한국어 제목이 표시되는 것을 확인했다. 두 원본의 정상 종료·Job0·원본 해시 보존도 확인했다. 송신자 열과 수신인 칸의 이름은 별도 미완료다.

직무 그룹명/장소명도 원래 트리 CString과 들여쓰기 계산을 유지하는 표시 보완을 통합했지만 실기는 미완료다. run-343의 직무 탭은 `1200`, character10000/search15/flags0/role175/그 외0을 보냈고, 서버가 이를 일반 임명 후보 검색으로 넘겨 미지원 검색 require에서 접속을 끊었다. 직무 받는 이 조회를 실제 조직 데이터와 연결해야 한다. 원본 이름표의 `120e`는 `NotifySimpleInformationOrderSuggestCharacter`다. 연속 가상 함수 표와 기존 1202/120c 처리기 대조로 `00563c20`을 그 읽기 함수로 추적했다. 최대10 바깥 묶음, 각 묶음의 u16 종류·최대10 인원과 인원 앞 별도 값, 인물/카드/소속/얼굴·나이 필드를 읽는다. search15와의 정확한 응답·앞 값 의미는 더 대조해야 하며 임명용 1202나 빈 목록으로 대체 연결하지 않았다. `evidence:client`(요청/실패/이름표/읽기 경계), `evidence:guess`(처리기 대응과 아직 미확정인 필드 의미).

직무행의 두 종류 접미어는 날짜가 아닌 OrderSuggestType 분기였다. 설치본 문자열과 실행파일의 인덱스 차이를 보정해 제안/명령 후보를 넣었으나, 값0/1과 발신 동작의 대응 실기는 아직 없다. 수신인 칸·편지 송신자 열·HUD 성명의 나머지 ANSI 경계와 물리 IME·이미지 전수도 미완료다. 진단 logging은 시험 DLL에만 넣고 제품 소스에서는 제거했다.
