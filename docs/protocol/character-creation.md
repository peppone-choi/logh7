# 캐릭터 생성·원작 캐릭터 응모

작성자: 최병호 · 2026-10-08 · 상태: 로컬 생성·응모·추첨·전략 진입 구현, LOGH-25

## 확인한 흐름

로비의 세션 선택·게임 세션 인증 뒤 클라이언트가 진영(2/3), 성별(0/1), 출신을 선택하고 성·이름을 입력한다. 생성 메뉴에는 [CD판의 명시적 메뉴 호환 패치](../ops/background-client.md#cd판-생성-메뉴-호환-패치)를 쓴다. `evidence:client`

`CommandGenerateCharacterCharge`는 양방향 opcode 0x1008이며 일반 세션 헤더를 쓴다. 첫 실제 요청의 category=0, ID=0, 진영=2, 출신=0, 성별=0과 합성 이름을 복호했다. 서버가 ID=10000·check=1로 응답하자 나이·생일·얼굴 선택으로 진행하고 category=1을 보냈다. 얼굴 예시는 ID 1000001이다. 이 요청은 `work/logh25-host-20261008/gateway-01`에서 확인했다. `evidence:client`

정적 UI `0x00594f20`, `0x00595de0`와 실제 생성 요청에서 다음 단계를 확인했다.

| category | 클라이언트 시점 |
|---|---|
| 0 | 성·이름 입력 후 중복 확인 |
| 1 | 나이·생일·얼굴 선택 후 초기 능력 요청 |
| 2 | 보너스 능력 배분 후 |
| 3 | 기함 이름 입력 후 |
| 4 | 등록 확인 후 최종 저장 |

## wire 필드

출력 코덱 `0x00405a50`, 길이 계산 `0x00405720`, 디버그 구조 표시 `0x00405ea0`을 대조했다. 모든 정수는 BE다. 고정 부분은 opcode를 제외하고 37바이트이며 문자열 코드 단위 수에 따라 늘어난다. 메모리 객체의 128바이트 크기는 wire 길이가 아니다. `evidence:client`

| 순서 | 필드 |
|---|---|
| 1 | category:u8, character_id:u32, power:u8, origin:u8, gender:u8 |
| 2 | surname_count:u8, surname:u16[N], given_count:u8, given_name:u16[N] |
| 3 | age:i32, birth_month:u8, birth_day:u8, face:i32 |
| 4 | abilities:u8[8], bonus:u8, special:u8, title:u8, rank:u8 |
| 5 | flagship_type:u8, flagship_kind:u16, name_count:u8, flagship_name:u16[N], check:u8 |

문자열 count는 최대 13이며 비어 있으면 0, 값이 있으면 마지막 NUL 코드 단위를 포함한다. age는 출생연도가 아니다. UI에서 나이 18~59·월 1~12·일 1~30을 고른다. 진영 2의 출신 값은 0/1/2/4, 진영 3은 3/4다. `evidence:client`

## 로컬 서버 정책과 제한

이름 중복 금지는 매뉴얼 W p.14–15, 한 세션에서 한 진영만 담당하는 규칙은 W p.8을 따른다. 로컬 구현은 성(표시명)을 NFKC·대소문자 정규화해 예약·등록 기록 전체에서 비교한다. 계정당 로컬 세션의 캐릭터 1개를 허용해 양 진영 동시 생성을 막는다. 요청의 ID·진영·성별·출신·이름은 같은 예약에 묶이며 서버가 부여한 초기 능력을 줄이거나 보너스를 초과할 수 없다. `evidence:manual`(제약), `evidence:guess`(정규화·예약·단일 슬롯 구현)

현재 초기 능력 8개 각각 50, 보너스 10, 특별 능력·작위 없음, 계급 인덱스 20, 기함 종류 인덱스 3·형식 0을 로컬 시험값으로 쓴다. 계급 20=이등병·기함 종류 3=구축함은 CD 문자열 테이블로 확인했다. **이 수치와 배분 조합이 원 서비스의 생성 공식이었다는 근거는 없다.** 원작 공식 복원 전의 가정으로 관리한다. `evidence:client`(인덱스), `evidence:guess`(초기 정책)

`LOGH7_CHARACTERS_FILE`을 지정하면 category=4의 전체 생성 데이터를 properties 파일에 원자적으로 교체 저장하고 재시작 때 읽는다. 환경변수가 없으면 메모리 시험 저장소다. 파일은 `work/` 아래에 두고 커밋하지 않는다.

## 전략 화면 초기화

등록 뒤 `0x0205 → 0x0206`으로 게임 로그인을 처리한다. 정적 카탈로그 요청 후 `0x0f00 → 0x0f01`(월드), `0x0f02 → 0x0f03`(그리드) 초기화가 이어진다. 각 완료 응답 **앞에** `0x0204` 캐릭터 ID, `0x0323` 캐릭터 상세, `0x0325` 기함 유닛을 보낸다. 클라이언트는 그리드 요청 직전에 캐릭터 수를 0으로 비우므로 두 단계 모두 상세를 전달해야 한다. 초기화 완료만 보내면 전략 UI `0x0058f83a`가 없는 캐릭터 객체를 참조한다. `evidence:client`

`BootstrapMessages`는 `0x00417390`(캐릭터), `0x00419ca0`(유닛), `0x0040ee80`(카드) 입력 코덱의 순서·폭을 따른다. 메모리 구조의 패딩을 wire에 넣지 않는다. 캐릭터의 이름·얼굴·생일·능력은 저장한 생성 결과에서 복원한다. 초기 유닛 ID는 캐릭터 ID+1000000, 그리드는 2550(표시 좌표 51,26), PCP/MCP·스태미나는 100을 쓴다. **이 배치와 자원 값은 로컬 접속 시험의 가정**이며 원 서비스의 초기 시드를 복원한 값이 아니다. `evidence:client`(코덱), `evidence:guess`(배치·자원)

모든 캐릭터의 개인·함장 카드 두 장은 매뉴얼 W p.27을 따른다. CD `constmsg.dat` 그룹 3의 개인=0, 제국 함장=59, 동맹 함장=195를 초기 kind로 사용한다. 정적 카드 레코드의 나머지 권한 값은 최소 로컬 값이고 커맨드 목록은 비어 있다. 원작의 권한·CP 비용·명령 실행 전체를 구현한 것은 아니다. `evidence:manual`(두 장), `evidence:client`(표시 인덱스), `evidence:guess`(최소 레코드)

카드 외 정적 카탈로그의 가변 목록은 0건, 고정 표는 코덱이 요구하는 길이의 0값을 보낸다. 시간은 임시 epoch=0, 메일·메신저 목록은 비어 있다. 실제 시드·시계·명령 처리는 P3에서 이어간다.

## 원작 캐릭터 응모

응모 메뉴의 실제 요청은 `0x1000 → 0x1001` 계정 정보, `0x1200` search=0x13 후보 전송, `0x1004 → 0x1005` 선택 후보 상태, `0x1006` 희망 순위 접수 순이다. 후보 전송에는 요청과 같은 `0x1200`, 후보 레코드 `0x120f`, 빈 완료 `0x1201`을 순서대로 보낸다. 일반 게임 화면의 월드 초기화와 별개다. `evidence:client`

계정 정보 `0x00407920`은 state u8·fame u32·이월 캐릭터 수 u8·캐릭터 요약 배열·id u32·희망 후보 수 u8·ID u32 배열이다. 로컬 시험은 이월 캐릭터 0건이다. 후보 `0x00565d60`은 power/camp u8·필요 계급 u16·필요 명성 u32 뒤 ID·표시명·계급·ladder·카드·조직·기지·얼굴·시작 나이를 읽는다. `0x00409b60`은 상태 u8·ID u32·최대 5개의 u32 상태 배열이다. 신청 `0x00405480`은 최대 5개의 ID이며, 서버도 같은 형식으로 접수를 확인한다. `evidence:client`

서버는 계정당 한 캐릭터, 담당 중인 후보 제외, 서버 명성 조건, 1~5개의 중복 없는 희망 순위를 검사한다. 생성 도중인 계정은 응모할 수 없고, 접수 중인 계정은 제너레이트를 생성할 수 없다. 매뉴얼의 담당 조건 심사·경합 시 추첨은 W p.11 근거다. 원작 조건의 정확한 수치는 없으므로 로컬 계정 명성과 기본 후보 조건은 0이다. `evidence:manual`(조건·추첨), `evidence:guess`(수치·접수 정책)

로컬 추첨은 첫 접수부터 60초 동안 신청을 모은다. 만료 뒤 다음 계정·후보·캐릭터 조회에서 신청 계정 순서를 무작위로 섞고 각 계정의 남은 최상위 희망을 하나 배정한다. 탈락자는 캐릭터를 받지 않고 재응모할 수 있다. 이는 **원 서비스의 추첨 알고리즘 복원이 아닌 로컬 정책**이다. 신청·마감과 당첨 캐릭터를 기존 캐릭터 파일에 원자적으로 저장하므로 서버 재시작 후에도 접수와 결과가 남는다. 로비는 당첨 캐릭터를 generated=0으로 반환한다. `evidence:guess`

기본 후보 둘의 성명은 매뉴얼 초기 담당자 목록에 나오는 키르히아이스·양을 사용한다. **ID=1001/1002, 나이·능력·계급·얼굴·함선·초기 배치는 접속 시험용 잠정값**이다. 실제 원작 캐릭터의 능력·CG·역할 카드를 복원한 카탈로그로 간주하지 않는다. 전체 원작 데이터와 담당 조건 수치, 이월·복귀 제한은 후속 복원이 필요하다. `evidence:manual`(성명), `evidence:guess`(시험 데이터)

## 저장 캐릭터의 로비 목록

`0x2003 → 0x2004`는 계정 소유 캐릭터가 있으면 세션 1건과 캐릭터 요약 1건을 반환한다. 없으면 기존 0건 응답이다. `0x0043fd60`의 세션 정보는 `0x2006`과 같은 필드 순서이고, 뒤에 다음 세션 수·entry_state·캐릭터 수·요약이 이어진다. `0x0051f1c0`에서 세션 상태 1/2, entry_state=2, 캐릭터 수>0일 때 계속하기가 활성화됨을 확인했다. `evidence:client`

생성 `0x1008.age`는 UI가 고른 연 단위지만, 로비 요약 `age`는 `0x0051f310`에서 31536000으로 나누어 표시한다. 서버는 저장된 나이를 이 초 단위로 변환한다. 전략 상세의 `begin_session_age`에도 같은 변환을 적용한다. 로컬 시험의 게임 시간은 여전히 epoch=0이므로 성장 시계를 구현한 것은 아니다. `evidence:client`(로비 나이), `evidence:guess`(전략 상세의 동일 단위 적용)

## 실행 확인

`work/logh25-host-20261008/run-06`에서 정상 UI의 0~4 단계로 생성 ID=10000을 등록하고 파일 저장을 확인했다. 서버 재시작 뒤 `run-14`에서 같은 계정의 명령행 접속으로 얼굴·능력·PCP/MCP·현재 그리드가 표시되는 1024×768 전략 화면을 확인했다. 해당 실행은 접속을 유지하고 오디오 세션 음소거 중 활성 출력, 원본 해시 보존, 소유 프로세스 종료를 통과했다. 정적 카탈로그·완료 응답만 보낸 실패와 캐릭터·유닛 전달 후 성공을 구분했다. `evidence:client`

`run-15`에서는 새 합성 계정으로 일반 로그인 UI → 생성 메뉴 호환 패치 → 제너레이트 0~4 → ID=10001 등록·저장 → 전략 화면 진입을 한 실행에서 통과했다. `gateway-08`에 등록·월드 초기화 로그와 실제 요청이 있다. 소유 프로세스 메모리를 한 번 읽어 캐릭터 ID=10001, 카드 수=2, kind=0/59와 정적 카드 목록 수=3을 확인했다. 카드 명령 실행·완전한 원작 지도·일본어 표시 정상화까지 검증한 것은 아니다. 실행기 성공, 음소거 중 활성 출력, 원본 보존, 소유 프로세스 정리를 확인했다. `evidence:client`

서버를 재시작한 `run-17`에서는 생성 메뉴 패치 없이 일반 로그인 → 계속하기 → 저장된 Beta 캐릭터 선택 → 전략 화면 재접속을 통과했다. `gateway-10`에 같은 ID=10001의 게임 로그인·초기화가 있다. 실행 결과의 활성 오디오 음소거·원본 보존·소유 프로세스 정리도 통과했다. `evidence:client`

`run-20`에서 일반 로그인 → 응모 메뉴 → 후보 선택 → ID=1001 신청과 서버 접수 확인을 통과했다. `gateway-13`에 `0x1000/1200/1004/1006` 실제 요청과 접수 로그가 있다. 서버 재시작 후 `run-21`에서 저장 신청의 추첨 → generated=0 로비 캐릭터 선택 → ID=1001 전략 화면 진입을 확인했다. `gateway-14`에 추첨 1명 배정과 월드 초기화 두 단계가 있다. 두 실행 모두 원본 보존·음소거 중 활성 출력·소유 프로세스 종료를 통과했다. 다인 실제 경쟁은 실행하지 않았으며 경쟁·조건 거절·중복 방지·재시작은 단위 테스트로 확인했다. `evidence:client`
