$env:LOGH7_BIND_ADDRESS='127.0.0.1'
$env:LOGH7_WORLD_FILE='E:\logh7\work\local-world.properties'
$env:LOGH7_ACCOUNTS_FILE='E:\logh7\work\accounts.properties'
$env:LOGH7_CHARACTERS_FILE='E:\logh7\work\characters.properties'

이 환경변수로 빌드한 앱 배포본을 실행한다. `LOGH7_NAVIGATION_FILE` 미지정 시 캐릭터 파일 옆 `.navigation` 파일을 사용한다. 실행 중인 배포본의 JAR을 빌드로 덮어쓰지 말고 별도 런타임 디렉터리에 복사한다.

- 매뉴얼 추출의 80개 성계 위치와 287개 거점 명칭·소속 성계를 연결한다. `evidence:manual`
- `0313` 지형 종류, `0315` 100×50 RLE 지도, `031d` 정적 거점을 초기 카탈로그로 전송한다. 클라이언트 입력기의 필드 순서를 따르고 네이티브 구조체 패딩은 넣지 않는다. `evidence:client`

CD판 매뉴얼 PDF p.31(인쇄 p.30)은 모든 함선·기함의 완충 워프 항속거리를 1,000광년으로 설명한다. 후기 웹판 PDF p.32(인쇄 p.31)은 항속 100 미만 워프 불가만 명시하며 완충값을 재명시하지 않는다. 현재 1000은 CD판을 보조 근거로 채택한 값이고 후기 사양에서의 유지 여부는 미확인이다. 범위 3칸·거리와 무관한 항속 소비 100은 임시 정책이다. `evidence:guess`(초기 위치·CP·범위·소비·후기 상한 채택), `evidence:manual`(CD 완충 거리·후기 MCP·항속 하한)

## 워프 처리

함장 카드의 명령 43을 활성화한다. 실제 목적지 선택·확인에서 `0b01` 33바이트 요청을 관찰했다. 성계 목적지에는 거점 ID도 포함된다. 서버는 인증된 캐릭터·카드·세션 세대·연결과 목적지/거점 관계를 검사하며 요청에 들어 있는 CP·시간·범위 값은 신뢰하지 않는다. `evidence:client`(요청), `evidence:guess`(검증 정책)

월드 액터에서 이동을 판정하고 파일 내용 강제 저장과 원자 교체를 마친 뒤 ACK·캐릭터·유닛·현재 그리드·이동 통지를 보낸다. 저장 실패 시 새 위치를 공개하지 않는다. 재접속 때 저장 위치·CP·항속을 복원한다. 단일 클라이언트 로컬 동작이며 전술 중 워프·예약 실행·오차·다중 유닛 동행·완전한 초기 세력 배치는 아직 연결하지 않았다. Windows의 디렉터리 전원 장애 내구성까지 보장하는 저장소는 아니다.

## 성계 표시와 클라이언트 호환 모듈

CD 클라이언트 `004d68d0`은 정적 거점 수와 궤도 필드를 사용하지 않고 임시 행성 4개를 고정 배치한다. 지도 표시 모드 4에서만 이를 켠다. 정적 거점 수신 성공만으로 성계 표시가 완성되는 것은 아니다. `evidence:client`

[호환 모듈](../../client-compat/README.md)은 원본 EXE 파일을 바꾸지 않고 성계 렌더링과 HUD 호출을 보완한다. 수신 후 소비된 정적 거점에서 현재 표시 성계에 속하는 행성 수·모델 번호·반지름·각도·직경을 읽는다. 성계 도착·재접속 때 성계 표시로 전환하고, 그리드 표시에서도 가리킨 성계의 배치를 그린다. 이름표·선택/기항 동작 전체를 구현한 것은 아니다. `evidence:guess`(호환 표시 정책)

3D 외형은 CD의 저해상도 모델 표 `00775310`에서 수신 모델 번호를 조회한다. 표의 가상 루트 `/../`를 전략 로더의 상대 경로 `../`로 변환하고, 원본 관리자 `00982fb0`의 리소스 로더 `004d1db0`과 인스턴스 연결 `004d1710`을 사용한다. 같은 표시 슬롯을 다시 연결하므로 워프마다 표시 인스턴스를 추가하지 않는다. HUD도 같은 모델 번호에서 아틀라스 셀을 고른다. 이 대응은 모델 외형의 일치이며, 실제 개별 행성의 원작 타입 배정을 입증하지 않는다. `evidence:client`(주소·모델 표), `evidence:guess`(보완 구현)

`NO DATA`는 데이터 부재만 뜻하지 않는다. 이 CD 실행본의 전략 HUD는 문자열 그룹 104를 조회하지만 해당 파일의 전략 문자열은 그룹 99에 있다. 원래 그룹 104는 세 항목뿐이어서 뒤 인덱스는 `NO DATA`로 반환된다. 호환 모듈은 확인된 HUD 호출 지점만 그룹 99로 고치며 항속의 double/int 서식 불일치도 보정한다. 다른 창의 문자열 누락·CP932/CP949 깨짐까지 해결한 것은 아니다. `evidence:client`

HUD는 지도 선택 대상이 아닌 현재 위치를 따른다. 거점은 공전 반지름 순으로 정렬하고, 원본 배경의 세로 궤도선 x=426·449·472·496 위에 아이콘 중심을 맞춘다. 성계→우주공간 이동 때 아이콘을 비우고, 다른 성계 진입·재접속 때 해당 성계의 개수·타입으로 다시 그린다. 원본 HUD가 수용하는 거점은 최대 4개다. `evidence:guess`(위치·정렬 정책)

## 행성 타입 입력

`tools/assets/prepare_world.py`는 추출 JSON의 `model_file`·`physical_class`·`orbit` 값이 제공되면 보존한다. `orbit`의 키는 `radius`, `cycle`, `direction`, `angle`, `diameter`이며 생략된 값만 기존 로컬 기본값을 사용한다. 원래 배정이 없는 행성을 임의로 확정하지 않는다. 기존 추출 파일은 이 값들이 `null`이므로 기본 모델 0이 표시된다.

별도 외형 지정 파일은 `--appearance-map <외부 JSON>`으로 읽는다. 형식은 `schema: 1`, `source: 출처`, `bases: [...]`이고 각 행은 `grid`, `name`, `planet_type`, 선택 `variant`로 대상을 지정한다. 이름만으로 매칭하지 않는다. 존재하지 않는 대상·중복·기존 모델과의 충돌은 거부한다. 각 결과의 `appearance-source`에 출처를 남긴다.

`planet_type` 0–10은 CD의 외형 모델 계열이며 모델 번호는 `type * 10 + variant`이다. 변형은 0·1, 계열 10만 2도 지원한다. 예를 들어 계열 6/변형 0은 모델 60과 해당 아틀라스 행을 선택한다. 이것은 원작 지상전 규칙의 `physical_class`와 별개다. 시각적으로 암석·가스·지구·빙결형 등으로 구분되는 외형이지, 각 실제 행성에 어느 타입이 배정됐는지를 입증하는 자료는 아니다. `evidence:client`(모델·이미지 계열), `evidence:guess`(입력 형식)

로컬 검증은 `work/world-warp-20261024/appearances-local-preview.json`과 `world-hud-types.properties`의 7개 명시적 시험 배정을 사용했다. 출처는 `local-preview-unverified-planet-types`로 표시했다. 나머지 미확정 행성 배정과 원래 공전 수치 복원은 남아 있다. 타입·변형·표시 좌표 검사는 x86 빌드에, 입력 값 보존·대상 검증 검사는 자산 도구 검사에 포함된다.

## 행성·시설 초기 설계와 이동

매뉴얼 두 판과 CD의 모델·문자열에서 개별 행성의 실제 타입 배정표는 발견하지 못했다. 추가 자료가 없으면 설계해 구현하라는 사용자 지시에 따라 `--design-fallback`을 추가했다. 이 옵션은 미지정 행성만 결정적으로 배정하며 출처를 `design-fallback-v1`로 남긴다. 제공된 원본 값과 별도 지정 값은 보존한다. 두 수도는 생명체 거주 가능 외형으로 고정하고, 거주 가능하지 않은 수도를 초기화하면 거부한다. 물리 종류·경제·환경 수치는 원작 복원이 아닌 초기 설계다. `evidence:guess`

매뉴얼 지도 주석 색은 제국 39개·동맹 40개·중립 1개 성계로 해석해 `system.N.power`에 연결했다. 근거는 `manual-map-annotation`이다. 그 성계의 행성·요새가 같은 초기 소유 세력을 상속한다. 이는 함대의 점령으로 소유권이 변하는 구현까지 포함하지 않는다. `evidence:manual`(지도 주석), `evidence:guess`(초기 상속)

`031f`에는 거점 ID·세력·진영·그리드·인구·세율·물자·환경을, `0321`에는 거점→시설→스폿의 ID와 배경 파일 번호를 보낸다. 클라이언트의 소비 캐시에 실제 값이 들어간 것도 확인했다. `1204`는 거점 이름 목록이며 소유 세력을 담지 않는다. `power`의 제국 2·동맹 3과 `camp`의 정규군 0·반란군 1을 구분한다. 캐릭터·카드·로비에도 정규군 0을 보내도록 고쳤다. `evidence:client`

W p.32의 장거리 워프 오차를 연결했다. 목표가 공간 그리드이고 체비셰프 거리가 2 이상이면 한 칸마다 10%(2칸 10%, 3칸 20%) 확률로 목표의 8방향 인접 공간 그리드 중 하나에 도착한다. 성계는 인접 그리드에서만 진입할 수 있으므로 오차가 없고, 출발 그리드·성계·지도 밖·진입 규칙(진영 수·유닛 수·독행함)을 통과하지 못한 칸은 후보에서 뺀다. 후보가 없으면 목표에 도착한다. 항속은 원래 목표 거리로 소비한다. 판정은 세대·인물·이동 횟수·출발·목표로 만든 결정론적 값이라 별도 난수 상태를 저장하지 않으며, 거부된 요청을 다시 보내도 결과가 바뀌지 않는다. 오차 확률과 후보 선택은 원래 공식을 찾지 못한 설계값이다. `evidence:manual`(오차 존재·인접 공간 도착), `evidence:guess`(확률·선택)

게이트웨이는 워프 ACK와 `0b07` 이동 완료에 요청 목적지가 아니라 서버가 확정한 도착 그리드를 넣는다. 함대 동행은 지휘관의 실제 도착 그리드와 항속 감소량을 그대로 사용한다. 워프 확인창의 항속 안내도 고정 100에서 "100광년당 100 소비 · 2칸 이상은 오차 가능"으로 바꿨다. 확인창은 선택한 목적지를 읽지 않으므로 구체적 소비량을 미리 표시하지 않는다. 그리드 선택 중 좌상단에 나오던 EXE 고정 영문 `Please choose the grid.`(VA `0x78bca4`, `00570a68`에서 CString 대입)는 기존 정적 문구 치환 경로에 `그리드를 선택하세요.`를 추가했다. 이 안내는 `004d8f1f`(그림자)·`004d8f36`(본문)에서 `004ce410`으로 그리는데, 하위 `004af380` 텍스처 글꼴은 0x20 미만과 0x80 이상 바이트를 건너뛰는 ASCII 전용이라 처음에는 사설 글리프의 뒷바이트만 `xly .`처럼 찍혔다. 같은 지도에서 한글 성계 이름을 그리는 `004ce350`이 같은 cdecl(x, y, 문자열, 색, 배율) 형식이므로, 0x80 이상 바이트가 있는 안내만 그쪽으로 보내고 배율은 이름 표시와 같은 1.0을 쓴다(`client-compat/warp_prompt.h`). ASCII 안내는 원래 경로를 유지한다. 디버그 HUD용 글리프 관리자 `[0xc514d0]`는 이 빌드에서 생성 코드가 없어 쓰지 않았다. 선택 화면의 `380 LY` 같은 거리 표시는 클라이언트가 커서 위치로 계산하는 연속 거리로 보이며, 서버의 그리드 중심 거리와 다를 수 있다. `evidence:client`(문자열 참조·기존 캡처)

검사: 엔진 753개(새 `WarpCourseTest` 포함)·게이트웨이 267개와 한글 카탈로그 검사, x86 호환 모듈 빌드와 guard 검사를 통과했다. 별도 포트(47950~)의 시험 서버와 비활성 데스크톱의 원본 한 개(동맹, 바라트 2015 출발)로 실제 확인했다. 좌상단 `그리드를 선택하세요.`와 확인창 안내의 한글 표시, 3칸 워프 2015→2018의 항속 1000→700·MCP 1000→960을 확인했다. 오차 도착은 서버와 같은 결정 함수로 미리 고른 2018→2016 요청이 1916에 도착(항속 700→500)했고, 1916→1919 요청도 1819에 도착(500→200)했다. 화면의 그리드 좌표는 1부터 센다(1916=`17, 20`). 서버와 원본을 모두 재시작한 뒤 1916·MCP 920·항속 500을 복원했다. 항속 200에서 3칸(300) 요청은 위치·MCP·항속·이동 횟수를 바꾸지 않고 거부됐고, 이어 2칸 워프 1819→1821로 항속이 정확히 0이 됐다. 3칸 직선에서 클라이언트 거리 표시 `300 LY`는 서버 소비량과 같았다. 원본 EXE 해시 보존과 소유 프로세스·Job 정리를 확인했다. 실행 기록과 화면은 Git 제외 `work/warp-20261030/`에 둔다. 거리 비례 대기 시간, 지형(플라스마 폭풍·사르가소) 데이터, 전술 중 예외, 함대 동행의 실제 오차 도착은 계속 미완료다.

### 규칙과 현재 구현의 구분

매뉴얼 W p.31의 한 진영당 300유닛과 최대 두 진영은 **그리드 진입 제한**이며 지도 숫자의 단위 근거가 아니다([규칙 요약](../manual/04-strategy-core.md#6-그리드-evidencemanual-w-p31)). 공식 사이트는 전략 색적 뒤 적아 함선 수를 확인한다고 설명한다. 여기서 앞서 사용한 `about_units`는 로컬 해석에서 붙인 필드명으로, 원본 수신 필드가 유닛 수를 뜻한다는 증거가 아니다. 수신 폭 `u16`과 그 값의 게임상 의미도 구분한다. 원래 서버의 색적 범위·정확도·적 병력 보고 시점은 여전히 미확정이다. `evidence:manual`(진입 제한·공식 설명), `evidence:client`(수신 폭)

**수정 전 버그 구현의 숫자**는 같은 세대·같은 세력 정규군의 배치 유닛 합계였다. [GridForces](../../server/engine/src/main/kotlin/org/logh7/engine/GridForces.kt)는 저장된 인물의 기함을 각각 1유닛, 현역 일반 함정은 잔존 척수가 1 이상인 ID마다 1유닛으로 센다. 현역 ID가 없는 구형 자료는 편성의 유닛 수를 사용한다. 육전대도 부대/주둔 그리드에 합산한다. 이 진입 정원용 집계를 지도에 재사용해 한 함대 4유닛을 숫자 4로 보내고 300→1척 손실에도 숫자를 유지한 것이 버그다. 육전대도 함선 수에 포함할 수 없다. 이 절은 기존 구현을 설명하는 기록이며, 수정 방향과 검증 상태는 끝의 정정 절을 따른다. `evidence:guess`(기존 대체 서버 구현)

**적군 표식은 현재 서버가 보고에서 제외한다.** [GridForceReport](../../server/gateway/src/main/kotlin/org/logh7/gateway/GridForceReport.kt)는 `Camp(viewer.power, false)`만 선택하므로 같은 그리드에서 전투 중인 적도 전략 병력 보고에 포함하지 않는다. 원래 색적을 수행해 미발견으로 판정한 결과가 아니라 적 색적/보고 기능 자체가 미구현인 상태다. 전술의 적 모델 생성·피해 통지와 전략의 적 표식 표시는 따로 확인해야 한다. `evidence:guess`
