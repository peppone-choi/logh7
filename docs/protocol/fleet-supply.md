# 부대 완전보급의 연결

작성: 최병호 · 2026-10-27

## 근거와 메시지

매뉴얼 병참 명령 표(`gin7manual.pdf`, PDF p.71)는 완전보급의 MCP 160, 대기·소요 0, 임의 부대 군수물자 보급을 명시한다. `evidence:manual`

원본 생성기 `005841e0`은 부대 선택·확인·송신 단계를 구성한다. `00573e50`의 분기 7은 현재 기함 소속과 선택 부대를 송신기 `004b4da0`에 넘긴다. `00551340`/`00555530`의 `0c01` 본문은 시각·인물·PCP·MCP·보급원 부대·대상 부대·대상 결과 물자(u32 7개), 보급원 결과 수(u8, 최대 26)와 `(unit:u32, supplies:u32)` 목록, 대상 결과 수(u8, 최대 70)와 같은 목록이다. 패딩은 없다. `evidence:client`

서버는 인증된 인물과 저장된 지휘관·세력·위치·재고·함정 ID를 사용한다. 요청의 시각·CP·결과 물자·개별 유닛 결과는 결과 상태로 신뢰하지 않는다. 잘린 목록·초과 개수·후행 바이트와 동일 부대 이전은 거부한다.

## 현재 구현 범위와 미완료

수송부대 지휘관의 같은 아군 행성 부대 간 보급을 월드 액터에 연결했다. 적재 여유와 보급원 잔량 중 작은 양만 이전하며 이전량이 0이면 비용을 청구하지 않는다. CP는 공통 MCP/PCP 대용 규칙을 사용한다. 물자 두 잔고와 CP를 같은 월드 커밋으로 저장한 뒤 공개한다. 할당 예약과 양쪽 창고의 재편성 예약이 있으면 거부하고, 만료·접속 종료된 예약은 해제한다. `evidence:guess`(같은 행성 제한·잔량 부족 시 부분 공급·무변경 무과금)

개별 함정 조회 `0331`과 완전보급 응답은 부대의 저장된 총량을 같은 함수로 분배한다. 현재는 함정 ID 오름차순으로 각 함정 유닛의 적재 상한까지 채우는 벌크 적재 정책이다. 개별 함정의 별도 잔고를 추가해 총량을 이중 저장하지 않는다. 함정의 상한은 기존 성능 자료를 사용한다. 함정이 없는 지상 부대의 상한은 기존 설계값이다. 이 분배를 원작의 적재 공식으로 단정하지 않는다. `evidence:guess`

기함 자체의 군수물자·이동 중 부대 보급·지원함별 조건·전술 소비와 개별 함정 손실 때의 물자 처리는 전체 완료 조건에 남는다. 수송부대에 물자를 싣고 돌려주는 전체 경로도 별도 연결 대상이다. 아래 제한된 실행만으로 체크리스트의 완전보급 전체를 완료 처리하지 않는다.

## 확인

규칙·프로토콜·저장·암호화 접속 검사에서 물자 보존, 적재 상한, 무변경/재전송 무과금, PCP 대용, 위조 결과 무시, 권한·위치 거부, 저장 실패 전후 두 잔고/CP 보존, 서버 재개방·재접속과 `0331` 재조회 일치를 확인했다. 변경 범위 검사는 프로토콜 84개·엔진 21개·게이트웨이 11개·저장 1개에서 실패/오류/건너뜀 0이었다. x86 호환 모듈의 경고 오류화 빌드와 가드 검사도 통과했다.

원본 한 개의 첫 UI 시험에서 완전보급 대상 선택 전 `00571a1d`의 접근 위반을 재현했다. 선택 단계 `00571870`은 검색 모드 14에 `TARGET_SELECT_S_BASE` 선행 선택값을 자동 추가하지만 완전보급은 이 선택이 첫 단계라 값이 없다. 호환 모듈은 해당 명령/수송 지휘관 문맥의 필터 추가만 현재 기함 그리드를 사용하는 기존 분기로 연결한다. 원본 실행 파일은 수정하지 않는다. `evidence:client`

이어 실제 검색 요청 `1200`의 종류 14·플래그 124·그리드 필드를 확인하고 `1200→120b→1201` 거래를 연결했다. `120b`는 최대 300행의 u16 개수와 물자·적재 여유·부대 ID·번호/종류·거점 레코드다. 원본 한 개(`native-08`)의 동맹 수송부대 카드 180→대상 제1함대→확정에서 실제 `0c01` 요청의 보급원 134·대상 133을 확인했다. 응답 MCP는 840(이전 1000), 두 부대의 저장 물자는 50,000/100,000에서 0/150,000으로 바뀌었다. 이후 시간 회복으로 화면 MCP가 915가 된 것을 160 결제 누락으로 해석하지 않는다. `evidence:client`

선택창의 정보와 확인 문구를 한국어 보급 대상/물자/적재 여유·상한과 대상 이름으로 연결했다. 첫 실행에서 목록 항목을 물자 레코드로 잘못 읽는 표시 오류를 발견했으며, 소유 프로세스에서 목록 항목 +0x10의 실제 `120b` 레코드 포인터를 확인해 수정했다. 최종 x86 /WX 빌드·가드 검사 후 `native-14`에서 제1함대 물자 150,000·적재 여유 3,930,000·상한 4,080,000과 확인창의 제1함대 이름을 확인했다. `evidence:client`

서버를 다시 띄운 뒤 `native-13/14`에서 원본 로그인→전략 화면→같은 수송부대 카드→보급 대상 재조회를 확인했다. `native-13`의 보급원 잔량 0에서 같은 명령을 확정한 실제 `0c01` 응답은 대상 150,000·MCP 1000을 유지했다. 이후 수정 모듈로 재실행한 `native-14`에서도 150,000을 조회하고 확인창 취소를 수행했다. 이는 같은 행성 부대 보급 경로의 확인이며 앞서 남긴 기함/이동 중 보급/적재·반환의 완료를 뜻하지 않는다. 소유 Job 0·프로세스 종료·원본 실행 파일 보존을 확인했다. 실행 자료는 Git 제외 `work/fleet-supply-20261027/`다.
