- `run-24`: 전술 화면의 합류/퇴장 알림을 원본 `0f1f` 재진입 경로로 바꾼 뒤 두 원본 모두 전술 HUD에 진입했다. 메모리에서 두 인물·기함 ID와 82개 전술 유닛의 함종·진영·지휘 인물을 확인했다. 함정 위치 조회가 반복되는 것도 확인했다. 이 시험만으로 장시간 안정성이나 전투 완료를 판정하지 않는다.
- 검사는 엔진 458개·프로토콜 94개·게이트웨이 160개 통과. 추가 회귀 검사는 두 번째 계정의 합류 시 재진입 알림과 전체 전장 목록 보존, 전장 밖 ID 배제, 압축된 전술 레코드의 바이트 위치를 확인한다.

캡처·실행 결과는 `work/native-multiplayer-20261028/`와 작업 트리의 같은 이름 디렉터리에 보관한다. 전체 전술 완료 체크는 유지하지 않는다.

## 이어서 해결할 사항

1. HUD의 `NO TABLE`, 초기화되지 않은 패널과 명령 비활성 상태. 아래의 지휘·방어막·조함 배분 연결 외에 충전·전술 명령 표와 배분의 실제 성능 적용을 계속 연결해야 한다.
2. 원본에서 에너지 배분·이동·공격·철수 명령을 실행하고 두 클라이언트가 같은 결과를 받는지 확인한다.
3. 임시 배치를 영속 전술 인스턴스로 옮기고 지휘권·CRC·색적·서버 시계·NPC·손상·격침·점령·복귀를 연결한다.
4. 전략에서 실제 접촉→전술 진입→종료→전략 복귀, 동시 참가·재접속·서버 재시작 시험을 완료한다.

현재 코드는 전술 연결 작업 브랜치에 보관하며 정상 플레이용 런타임에는 적용하지 않는다. 전술 화면 도달을 게임 플레이 완성으로 취급하지 않는다.

## 지휘 상태와 기함 에너지 연결 (2026-10-28)

`evidence:client` `033f`는 인물 ID로 지휘 상태를 전달한다. `00422d80`의 레코드는 wire 55바이트·native 60바이트이며 임무·대상·CRC·최고사령관·대형·에너지 11개·빔/건 충전·방어막 6면의 충전/손상을 담는다. `004c32a0`은 유닛의 지휘 인물과 이 레코드를 대응시킨다. `run-25`에서 두 원본의 조함 패널에 동맹 표준전함 제원의 방어막 용량 20을 표시했고, 인물의 제어 구조에 잔여 출력 400이 설정된 것을 확인했다.

`evidence:client` `040c` 조함 요청/응답은 시간·대기·인물 ID·기함 ID `u32` 네 개, 잔여 출력 `u16`, 빔/건/방어막 6면/엔진/워프/센서 `u8` 11개로 총 29바이트다(`00495b70`, `0049eac0`, `004c1700`). 서버는 요청의 시간·대기·잔여 출력을 신뢰하지 않고 현재 게임 시각과 인증된 함종의 출력으로 응답한다. 두 정적 카드 표에 함장용 조함 명령 53을 연결했다.

인증된 본인 기함·함장 권한·현재 전술 상태를 확인하고, 배분값 0~100과 합계가 함선 출력을 넘지 않는지 검사한다. 배분 11개를 NAV-8의 마지막 열에 저장하며 NAV-1~7은 배분 미설정으로 읽는다. 재초기화의 `033f`에도 저장된 배분을 사용한다. 배분 자체는 CP를 차감하지 않는다. 초기 미설정 배분은 0이며 출력은 예비로 둔다. 배분 즉시 적용·기본 배분 정책은 `evidence:guess`이고, 이동·충전·공격 성능 적용과 지연·CRC·손상 처리는 아직 연결하지 않았다.

원본 `run-27`의 실제 ENGINE 슬라이더를 드래그해 53으로 변경했다. `040c` 처리 뒤 서버 NAV-8에 엔진 53을 저장했고, 원본 화면도 53을 표시했다. 원본 인물 제어 구조의 잔여 출력은 400에서 347로 바뀌었으며 PCP/MCP 1000/960·위치 2017은 유지했다. 일반 클릭만으로 값을 바꿨다고 기록하지 않는다. 시험용 드래그는 소유 비활성 창 안의 가상 위치·버튼 상태만 사용한다.

서버와 두 원본을 모두 종료한 뒤 `run-28`에서 재시작했다. 본인 화면 ENGINE 53과 잔여 출력 347을 복원했고, 다른 계정의 ENGINE 0·잔여 출력 400은 유지했다. NAV-8 배분·위치·CP도 유지했다. 코드 검사는 엔진 459·프로토콜 96·영속화 89·게이트웨이 160개를 통과했고, 전대장 0 변경 후에는 관련 프로토콜 검사도 다시 통과했다. GUI 시험 그룹 검사 7개는 실제 원본 시험이 끝나 잠금이 해제된 뒤 통과했다.

## 전술 이동 메시지 복원 (2026-10-28)

`evidence:client` 이동 `0400`의 요청 작성기 `00492930`, 응답 판독기 `0049a5d0`와 로그 함수 `00492c10`·`0049ad60`을 대조했다. 본문은 시간·대기·인물 ID `u32` 세 개, 유닛 수 `u8`, 유닛별 ID `u32`·방향과 xyz `float` 네 개, 속도와 도착 방향 `float` 두 개, 경유점 수 `u8`, 경유점별 xyz `float` 세 개다. 본문 크기는 `22 + 20 × 유닛 수 + 12 × 경유점 수`이며 native 구조체의 정렬 패딩은 포함하지 않는다. 양쪽 배열의 원본 상한은 각각 32개다. `004be8f0`은 응답의 시간+대기를 이동 시작 시각으로 사용한다.

이 계약의 요청 파서와 응답 작성기를 추가했다. 요청의 시간·대기는 버리며, 실제 실행 경로에서는 서버가 검증한 원점·속도·시각으로 응답해야 한다. 실행 가능한 요청을 대상으로 배열을 1~32개로 제한하고, 중복/비양수 유닛 ID·비정상 인물 ID·NaN/무한 좌표·음수 속도·잘린 배열·뒤에 붙은 바이트를 거부한다. 관련 프로토콜 검사 3개에서 실제 바이트 오프셋·최대 크기·경계와 변형된 요청을 확인했다.

후속 서버 연결의 현재 범위는 아래와 같다. `0423` 이동 통지는 후처리 필드와 의미를 더 확인해야 하므로 이번 작성기에 포함하지 않았다. 원본 두 클라이언트의 이동 성공으로 기록하거나 전체 전술 체크를 완료로 바꾸지 않는다.

## 전술 배치 축 교정과 기함 이동 서버 연결 (2026-10-28)

`evidence:client` `004c1d20`은 `033b`의 첫 두 좌표를 native world x/z 평면에 배치한다. 거점의 `004c4240`도 첫 두 좌표 사이에 수직 0을 넣어 모델 좌표를 구성하며 세 번째 수신 좌표는 사용하지 않는다. 서버가 배치 간격과 행성의 궤도 sin 값을 세 번째 좌표에 넣던 것을 두 번째로 옮겼다. `run-29`에서 두 원본 모두 82개 유닛을 서로 다른 모델 좌표에 배치했고, 예를 들어 제국 함정 1·2는 `(700,0,-180)`·`(700,0,-140)`, 동맹 기함 두 척은 `(-580,0,-180)`·`(-580,0,-140)`이었다. 화면에서도 적 표식이 격자로 나뉘었다. HUD의 `NO TABLE`과 겹친 초기 패널은 이 수정으로 해결되지 않았다.

기함 이동 요청은 인증된 본인 인물·기함·함장 카드·전술 상태를 검사한다. 요청에 들어 있는 출발 좌표·시각은 사용하지 않고 현재 서버 위치에서 경로를 만든다. 속도 비율은 ENGINE 배분/100을 넘을 수 없고, 경유점은 1~32개·평면 좌표 ±100,000 범위다. 현재 연결은 개인 기함 한 척이며 부대 함정의 지휘권/CRC는 아직 연결하지 않았으므로 다른 유닛 지정은 거부한다. 이동 중 ENGINE을 낮추면 당시 서버 위치에서 속도를 낮추거나 정지시키고 양쪽에 새 경로를 알린다. 이미 시작한 이동을 늦추기 위해 다시 대기를 부과하지 않는다.

`evidence:guess` 현재 이동은 서버 게임 시계 기준 5초 대기 뒤 선형 경로를 진행하는 임시 계산이다. `run-29`의 모든 모델에서 관측한 기준 속도 1에 요청 비율을 곱한다. 함종별 매뉴얼 최고 속도·좌표 거리 환산·가속/선회·발령 처리 지연과 원본 전술 시계의 기준 시각은 계속 맞춰야 한다. 원본 `run-30`의 조함 요청 대기는 120으로 관측됐으므로 매뉴얼의 초와 wire 대기의 환산을 확정했다고 쓰지 않는다.

이동 원점·접수 시각·속도·도착 방향·경유점을 NAV-9 마지막 열에 제한된 바이너리의 Base64로 저장한다. 이동이 없는 파일은 NAV-8로 쓰며 NAV-1~8에는 경로를 만들지 않는다. 위치 조회는 저장 경로의 현재 위치를 계산하고, 전술 초기화 응답 뒤에는 남은 경로를 보낸다. 저장 완료 뒤 같은 전장의 다른 참가자에게도 `0400`을 전달한다. 서버 시뮬레이션 검사에서 대기·경유점·도착 후 정지·재발령 원점·ENGINE 감소를, 파일 검사에서 재열기 후 같은 시간의 위치를 확인했다. 암호화된 두 접속 검사에서는 출발 좌표 위조 무시·동일 응답 수신·다른 기함/과속 거부·재초기화 후 경로 복원을 확인했다.

`run-30`의 두 원본은 교정된 배치로 진입했고 실제 ENGINE 드래그로 100을 저장했다. 기함 명령 탭→이동 아이콘→화면 목적지를 클릭했지만 캡처에 `0400` 요청이 발생하지 않았다. 따라서 실제 원본 UI의 이동 발령·도착·재접속/재시작 복원은 **미확인**이다. 다음은 HUD/명령 활성 조건과 전술 시계 초기화 경로를 추적해 이 막힘을 해결하는 작업이다. 두 시험 모두 원본 해시·호스트 활성 창/커서를 보존하고 종료 정리를 완료했다. 정상 플레이 서버는 runtime-70으로 복귀했으며 이 작업 브랜치를 적용하지 않았다.

이 변경 후 엔진 461·프로토콜 99·영속화 90·게이트웨이 160개, 합계 810개 검사를 통과했다. 이 수치는 원본 UI 이동 성공을 대신하지 않는다.
