## 근거와 메시지

매뉴얼 병참 §7.5는 지휘관의 같은 함종 보충, 부대 창고의 정확히 같은 타입 사용, 승조원 자동 보충과 상선의 승조원 예외를 설명한다(`gin7manual.pdf`, PDF 44~45쪽). 명령 표(PDF 71쪽)의 MCP는 160이며 대기·소요는 0이다. 원본 명령 이름은 constmsg 그룹 18의 64다. `evidence:manual` `evidence:client`

원본 `00552610`/`00556b10`의 `0c05` 본문은 시각·인물(u32), 모드(u8), PCP·MCP·거점·부대(u32), 종류(u8), 보충 함종 수(u8, 최대 99)와 각 함종(u16)·함정 ID 수(u8, 최대 99)·ID(u32) 목록이다. 이후 승조원 이동 수(u8, 최대 24)와 `(kind:u16, grade:u8, units:i16)`, 물자 이동(i32), 결과 함선/병력 목록, 결과 물자·승조원 상한·물자 상한(u32)이 온다. 배열이 비어 있는 요청은 opcode 포함 48바이트다. 요청의 CP·이동 승조원·결과 편성·상한은 서버의 상태로 신뢰하지 않는다. `evidence:client`

보충 화살표는 검색 34의 `1200`을 보내며, 함종은 요청 오프셋 23의 u16이다. 원본 `0055f1f0`/`0055f580`은 `1207`의 u16 개수(최대 600)와 `(id:u32, kind:u8, destroyed:u16)`를 읽는다. 인증된 지휘관의 아군 부대에서 해당 함종의 손실 유닛만 반환하고 `1200→1207→1201`을 마친다. `evidence:client`

## 구현

모드 0은 비용·편성 저장 없이 미리보기를 반환하고 모드 1은 현재 서버 상태로 다시 검증해 확정한다. 한 함종의 중복 없는 실제 부대 ID만 허용한다. 창고의 같은 함종에서 부족한 척수만 꺼내며, 유닛 ID와 기존 숙련도는 보존한다. 포장을 해제하고 남은 함선은 창고에 별도로 보존한다. 기존 할당/재편성 예약과 공유 창고가 겹치면 거부한다. CP·함정 생존 척수·창고 잔여 척수·승조원·군수물자를 같은 월드 커밋으로 저장한 뒤 공개한다. 저장 실패 시 이전 상태를 유지하고 쓰기를 차단한다.

복원 설계는 다음과 같다. 창고의 낮은 숙련도부터 같은 함종을 사용하되 현역 숙련도는 바꾸지 않는다. 승조원 필요량은 생존 척수에 비례해 유닛마다 올림하며, 창고에서 가능한 만큼 자동 보충하고 필요량이 있는데 승조원 총량이 0이면 거부한다. 군수물자의 양수 적재와 음수 반환은 부대/창고 양쪽 잔고와 기존 적재 상한 안에서 허용한다. 무변경은 무과금이다. 개별 함선 전투 손실·승조원 효율의 원작 공식으로 단정하지 않는다. `evidence:guess`

`LOGH7-STOCK-13`은 현역 레코드의 `id.kind.grade.boats`와 창고의 포장되지 않은 함선 `kind.grade.boats`를 저장한다. 12 이하의 기존 3필드 현역 ID는 원래 서버가 저장하던 온전한 유닛으로 읽는다. 13에서는 생존 척수 누락을 거부해 손실이 조용히 복구되지 않도록 한다. 손실 유닛을 재편성으로 반환할 때에도 실제 잔여 척수만 창고에 들어간다. 구버전 프로그램으로 되돌릴 때는 새 저장 형식을 읽을 수 없으므로 해당 배포 전 백업을 함께 사용한다.

## 끝수 함선의 재편성 연결

보충 후 창고에 남는 끝수 함선은 온전한 함선 유닛 수와 별도 척수로 저장한다. 재편성 조회가 이 끝수를 한 유닛으로 표시하면서 실제 선택은 온전한 유닛만 허용하던 불일치를 수정했다. 한 숙련도에서 온전한 유닛을 먼저 이동하고 마지막 끝수 유닛을 실제 척수로 취역시키며, 기존 현역 ID·숙련도·생존 척수를 유지한다. 반환하는 현역 ID는 폐기하고 실제 생존 척수만 창고에 합쳐 온전한 유닛/끝수로 다시 나눈다. 이 우선순위와 ID 정책은 서버 복원 설계다. 승조원 미리보기와 확정 검사는 보충과 같은 생존 척수 비례 올림 정책을 사용한다. `evidence:guess`

원본 `native-08`은 수송부대 전투함 정원을 넘지 않는 별도 시험 월드(기존 현역 280척·승조원 4, 창고 300+290척·승조원 94)를 사용했다. 카드→재편성→함선 2유닛/승조원 8유닛 선택→확정으로 280·300·290척을 저장했다. MCP 905→745, 창고 함선 0·승조원 86, 부대 승조원 12를 확인했고, 같은 카드의 보충 화면에서 현역 870척·창고 0척을 재조회했다. 이어 재편성에서 함선 1유닛·승조원 4유닛을 반환해 현역 580척/승조원 8, 창고 끝수 290척/승조원 90과 MCP 745→585를 확인했다. 서버와 원본을 모두 재시작한 `native-09`에서도 같은 보충 화면에서 현역 580척·창고 290척을 재조회했다. 원본 EXE 보존과 소유 프로세스 종료·오디오 복원을 확인했다. 일반 월드에는 시험용 편성을 복사하지 않았다. `evidence:client`

엔진 전체 441개, 관련 게이트웨이 7개, 저장 트랜잭션 7개가 통과했다. 마지막 중복 반환 보조 코드 제거 뒤 보충/끝수 재편성 6개도 재검사했다. 반복 이동의 총 척수 보존·부족 재고 거부·실제 필요 승조원/미리보기·암호화 접속 재개방 후 반환·파일 재개방 후 척수/CP/폐기 ID 보존을 포함한다. 전체 병참, 편집창 전체 예약·전술 손실 연결·두 원본 동시 재편성은 아직 미완료다.

## 행성 창고와 끝수 함선의 할당 왕복

할당의 `0c0b`는 기존과 같이 부호 있는 유닛 수를 사용한다. 끝수 유닛도 한 선택 단위로 취급하되, 실제 척수·숙련도를 옮기며 같은 숙련도의 목적지 끝수와 합쳐 온전한 유닛/끝수로 정규화한다. 숙련도가 다르면 합치지 않는다. 생산 진행 시간·다른 함종·병력은 그대로 보존하고, 조회·확정 응답은 계산된 실제 척수를 보낸다. 양쪽 재고와 CP를 한 월드 교체로 저장하며 새 현역 ID를 만들지 않는다. 이는 물리 수량 보존을 위한 서버 설계이며, 원작이 끝수 유닛을 포장하는 내부 공식으로 단정하지 않는다. `evidence:guess`

현재 저장 형식 `LOGH7-STOCK-14`는 `P` 행의 마지막 필드에 행성 창고 끝수 `kind.grade.boats` 또는 `-`를 추가한다. 기존 1~13 읽기를 유지하며 13 이하에서 존재하지 않던 행성 끝수는 빈 값으로 이관한다. 14의 필드 누락·잘못된 범위·중복은 거부한다. 13의 현역 생존 척수와 부대 창고 끝수는 그대로 보존한다. 이전 바이너리는 14를 읽지 못하므로 배포 전 백업을 유지해야 한다.

별도 제국 병참 담당자 시험 월드의 `native-02`에서 카드→할당→오딘→제1수송부대→전함Ⅰ 반환 1유닛→결정으로 끝수 123척을 부대 창고에서 행성 창고로 반환했다. 원본 `00558b70` 해독 결과는 성공·전함Ⅰ 1유닛/123척·부대 창고 함선 0이었다. 저장값도 같은 숙련도 2의 123척을 행성으로 옮겼고 MCP 990→830을 확인했다. 서버와 원본을 모두 재시작한 `native-03`에서 행성 1유닛·부대 창고 0을 재조회한 뒤, 같은 카드·슬라이더로 다시 할당했다. 원본 해독 결과와 저장 파일 모두 부대 창고 전함Ⅰ 1유닛/123척·숙련도 2를 유지했고 MCP 905→745를 확인했다. 두 실행의 원본 EXE 보존·소유 프로세스 종료·오디오 복원을 확인했다. 시험 자료는 Git 제외 `work/base-remainders-20261027/`에 보존하며 일반 월드에 시험 재고·직책을 복사하지 않는다. `evidence:client`

엔진 전체 442개, 병참 게이트웨이의 기존 경로와 추가 끝수 왕복 검사, 저장 전체 이관/재개방 검사와 추가 원자 저장 실패 검사를 통과했다. 행성/부대 창고 사이의 부족 재고 거부·같은 숙련도 끝수 합산·다른 숙련도 보존·재접속/파일 재개방 후 역방향 이동·저장 실패 시 CP/양쪽 재고 유지와 쓰기 차단을 포함한다.
