# 업데이터 제어 프로토콜

작성자: 최병호 · 2026-09-27 · 상태: **candidate**, 동적 미검증.
근거: `evidence:client`, E-303. 대상 `Gin7UpdateClient.exe`, 주소는 VA.

## 외부 opcode와 오류 상태값 분리

`0x0041fe60`의 실제 수신 switch는 **0x6811/6812, 0x6821/6822/6823, 0x6831/6832/6833, 0x6840**이다. 기존 초안의 0x8000/8001/8010/8020은 `0x0041e910`에서 처리하는 **오류 응답 본문의 u16 값**이다. 요청 0x68xx에 외부 opcode 0x80xx로 답하는 구현은 이 디스패처와 맞지 않는다. `evidence:client`

TCP framing은 `[u16 BE payload_len][u16 BE opcode][body]`. `0x0041d370`은 payload에서 첫 u16만 opcode로 읽고 나머지 payload_len-2를 본문으로 복사한다. 게임의 6바이트 응용 헤더/암호 봉투를 여기에 붙이지 않는다. `evidence:client`

## 요청과 응답

| opcode | 방향 | 본문/동작 | 함수 |
|---|---|---|---|
| 0x6810 | C→S | 설정된 인증/식별 blob 원시 바이트, 길이 this+0x4c; 0이면 없음 | 0x0041ea60 |
| 0x6811 | S→C | 본문 읽지 않음. 0x6820 송신으로 진행 | 0x0041ff30 |
| 0x6812 | S→C | BE16 오류값, 나머지는 callback 전달 가능. 실패 종료 | 0x0041ff50 |
| 0x6820 | C→S | BE32 로컬 버전값(this+0x44) | 0x0041eae0 |
| 0x6821 | S→C | BE16 N 후 N쌍의 NUL 종료 문자열(서버 이름/기본 URL 후보). 이후 0x6830 | 0x0041ffd0 |
| **0x6822** | S→C | **본문 없음. 업데이트 없음/완료 경로**, state=8, 제어 연결 종료 | **0x00420240** |
| 0x6823 | S→C | BE16 오류값, 실패 종료 | 0x00420550 |
| 0x6830 | C→S | 본문 없음. 다음 파일 항목 요청 | 0x0041eb50 |
| 0x6831 | S→C | 아래 파일 항목 1개. 성공 파싱 뒤 다시 0x6830 | 0x00420260/0x00422800 |
| 0x6832 | S→C | BE32 서버 버전값(this+0x44). 목록 수신 완료, HTTP/파일 처리 단계 | 0x004204c0 |
| 0x6833 | S→C | BE16 오류값, 실패 종료 | 0x00420550 |
| 0x6840 | S→C | 별도 알림 처리; 세부 본문 미분석 | 0x004205a0 |

이 표의 문자열 역할과 파일 필드의 의미 중 “후보”는 소비 코드로 추정한 이름이며 원본 서버 명세가 아니다. 정수 폭·읽는 순서는 정적 코드 관찰이다. `evidence:client`

## 업데이트 없음 최소 교환

클라이언트의 0x6810을 받은 뒤 `00 02 68 11`, 이어 0x6820을 받으면 **`00 02 68 22`**를 보내는 후보 경로다. 0x6822 처리 함수는 본문을 읽지 않고 즉시 완료 상태 8로 간다. 오류값 0x8000을 보내는 방식과 다르다. 이 두 패킷은 코드로 도출한 합성값이며 실행 성공을 주장하지 않는다. `evidence:client`

## 오류값

| body offset 0의 BE16 | 내부 결과 |
|---|---:|
| 0x8000 | 2 |
| 0x8001 | 3 |
| 0x8010 | 4 |
| 0x8020 | 5 |
| 기타 | 11 |

이 값의 사람용 오류 문구는 별도 매핑이 필요하다. 최소 오류 응답은 예를 들어 `[00 04][68 23][80 10]`이다. `evidence:client`

## 0x6831 파일 항목

입력 `0x00422800`. 이름 문자열 길이를 L(종료 NUL 포함)로 두면 아래와 같다. 숫자는 BE다. `evidence:client`

| offset | 형식 | 파싱 대상 |
|---|---|---|
| 0 | NUL 종료 문자열 | 상대 파일명 후보 |
| L | u16 operation | 객체 +0x10 |
| L+2, operation=0일 때만 | u32×3 | 객체 +0x14/+0x18/+0x1c; 뒤 둘은 로컬 파일 크기/검사값 비교에 사용 |
| 앞 필드 다음, operation이 1/3/4가 아닐 때 | u16 | 객체 +0x20; 값 2이면 HTTP 대상 경로를 추가 데이터에서 읽음 |
| 다음 | u16 K | 추가 데이터 길이 |
| 다음 | K raw bytes | 추가 데이터 |

operation=0의 세 u32 중 첫째의 정확한 의미와 검사값 알고리즘, operation별 파일 처리 의미 전체는 아직 미확정이다. 함수가 실행하는 읽기 순서까지만 구현 가능한 후보 명세다. `evidence:client`

## 확인 범위

Ghidra `t2update` export와 기존 `upd` export에서 dispatcher→body reader→state 전이를 확인했다. 원본 파일 및 시스템 설정은 변경하지 않았다. VM 부재로 `00 02 68 22` 수용 및 런처 진행은 미실행이며 LOGH-11 종료 조건으로 남는다. `evidence:client`
