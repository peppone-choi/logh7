## 정적 그리드 0x0315

파서 `0x004134e0`, 필드명 덤프 `0x00413870`, RLE 해제 `0x004abbb0`. `evidence:client`

| 본문 offset | 타입 | 필드 |
|---|---|---|
| 0 | u8 | width |
| 1 | u8 | height |
| 2 | u16 BE | compressed_size, 최대 5000 |
| 4 | compressed_size 바이트 | `(count:u8, value:u8)` 반복 |

해제기는 각 value를 count번 반복하여 일차원 배열에 쓰며 누적 길이가 width×height를 넘으면 실패, 마지막 길이가 정확히 일치하면 성공한다. 원본 함수는 size=0을 거부하며 홀수 마지막 바이트 처리도 느슨하므로 서버 생성기는 짝수 size와 정확한 합계를 요구하는 것이 안전한 후보 구현이다. `evidence:client`

수신 디스패처 `0x004ba2b0`은 0x0315 객체를 게임 상태 객체 상대 `+0x3f4448`에 복사하고 **+0x3f444c**부터 RLE 해제 결과를 쓴다. 이 오프셋은 VA가 아니라 런타임 객체 상대값이다. width/height 뒤의 5000바이트 저장 영역을 재사용한다. `evidence:client`

소비 함수 `0x004c8b70`은 `0≤x<100`, `0≤y<50`를 검사하고 런타임 지도 `+0x2c03cc+y×100+x`의 1바이트 값으로 종류 테이블 `+0x2c1755+value×3`을 참조한다. `0x004c8bc0`도 5000셀을 같은 순서로 순회하여 값 3..88의 성계→셀 역색인을 만든다. 이 배열은 수신 보관 영역 `+0x3f444c`와 다른, 소비용 상태이다. `evidence:client`

좌표 변환 `0x004d3540`은 셀 `(x,y)`를 렌더 좌표 **(x−49.5, 0, 24.5−y)**로 바꾼다. 원점은 셀 중심이며 y가 증가하면 렌더 z가 감소한다. `0x004d3bd0`은 경계선 x=−50..50, z=−25..25를 생성한다. 이는 화면 픽셀 좌표와 별개의 월드 좌표다. `evidence:client`

## 행성·거점 정적 정보 0x031d

파서 `0x004142e0`, 필드명 덤프 `0x00414a30`. 본문 첫 BE16은 항목 수(최대 350). 각 항목은 다음 순서로 이어진다. 항목 시작을 offset 0, 이름 코드 단위 수를 N이라 한다. `evidence:client`

| 10 | u8 | N, 최대 13 | +10 |

항목 wire 크기는 `29+2N`, 메모리 크기는 정렬/고정 이름 배열 때문에 60바이트다. 응답 객체는 4바이트 정렬 헤더 + 최대 350×60 = **21004(0x520c)바이트**이며 상태 객체 `+0x3f5ae8`에 복사된다. `evidence:client`

float 입력 `0x00611bc0`은 u32에 **ntohl을 적용한 뒤 float로 해석**한다. 기존 초안의 “float raw little-endian”을 이 경로에 적용하면 잘못된다. 공전 반경·초기 각도·방향·주기와 소속 grid가 존재하므로 행성 위치를 재현할 재료는 있으나, 거리 단위·각도 영점·시간 기준·class 값별 모델 관계는 아직 미검증이다. `evidence:client`

전술 객체 생성 `0x004c32a0`에서는 diameter를 2로 나누어 반경으로 사용하고, 초기 각도에 `0.017453292`를 곱한다. 따라서 수신 초기 각도는 도(degree)이며 렌더링에는 라디안으로 전달된다. kind=1 요새는 이 행성 공전 설정 분기를 건너뛴다. 반경의 실제 거리 단위·주기의 시간 기준·개별 원본 값은 계속 미확인이다. `evidence:client`

행성 모델은 `p000`/`p001`, `p010`/`p011`, …, `p100`/`p101`/`p102`를 참조한다. 파일명·모델 번호만으로 물리 class나 개별 행성 이름을 정하지 않는다. 특히 **요새 6이름과 존재하는 모델 6종의 개수 일치만으로 대응을 확정하지 않는다.** 외형·텍스처·당시 화면과의 대조가 필요하다. `evidence:client`

### Null_galaxy의 위치 키

이 파일은 LE32 직렬화 포인터를 포함한다. 파일 offset 0의 포인터에서 `0x50`을 뺀 값을 기준 주소로 삼으면, 헤더의 노드·채널 포인터와 각 노드의 모션 바인딩·키 포인터가 모두 파일 범위 안으로 대응한다. 추출기는 범위를 검사하며 일반 MDX 변종이나 움직이는 노드는 지원하지 않는다. `evidence:client`

| 위치 | 읽는 값 |
|---|---|
| 헤더 +0/+4 | 노드 포인터/수, 노드 stride 0xe8 |
| 헤더 +0x10/+0x14 | 채널 포인터/수, 채널 stride 28 |
| 노드 +8 | NUL 종료 ASCII 이름, 최대 128바이트 |
| 노드 +0x90/+0x94 | 모션 바인딩 포인터/수(각 1) |
| 바인딩 +12 | 9개 채널 인덱스 |
| 채널 +8/+12/+16 | 키 포인터/수/채널 종류(0..8) |
| 36바이트 키 +4/+8 | 시간/float32 값 |

모든 노드의 위치 채널 0..2에는 시간 0의 키가 하나씩 있고, 회전은 0·배율은 1이다. 이름은 `star_01_G`..`star_79_G`, `bh_01`..`bh_03`, `ns_01`..`ns_03`이며 모든 위치의 y는 0이다. `star_` 뒤 문자는 O/B/A/F/G/K/M 중 하나지만 서버 모델 번호와의 대응은 확정하지 않았다. `evidence:client`

모델 위치를 2배 확대하면 85개 전부 위 셀 중심 좌표에 정확히 맞는다. 변환은 `grid_x=2×model_x+49.5`, `grid_y=24.5−2×model_z`이며, 중복 셀도 없다. **항성 79개는 매뉴얼 지도와 대조하여 이름·좌표 대응까지 확인했다.** 나머지 `bh_`/`ns_` 각 3개는 자산의 위치는 확보했으나 지도 주석에 이름이 없다. `Null_galaxy.mdx` 자체를 런타임 지도 입력으로 읽는 직접 참조는 아직 발견하지 못했다. 이 자료만으로 전체 셀의 종류나 소유권을 복원한 것은 아니다. `evidence:manual`, `evidence:client`

```powershell
python -X utf8 -B tools/assets/planet_models.py <client> work/map/planet-models.json
python -X utf8 -B -m unittest discover -s tools/assets -v
```

`0313`/`0315`/`031d` 모드는 복호화한 메시지 **본문만** 받는다(프레임·opcode 제외). 빈/홀수 RLE, 길이 불일치, 잘린 이름, 범위 밖 포인터, 동적 키·변환은 거부한다. 합성 입력 테스트 10개 통과. 실제 입력에서는 모델 85위치·문자열표 86이름과 매뉴얼 80성계·287거점을 추출하고 항성 79개를 모두 대조했다. 모델 경로 33슬롯도 추출했다. 결과 JSON은 이름표의 kind와 모델 번호를 따로 보존하고 거점별 물리 클래스·모델·공전값을 `null`로 남긴다. 서버 표시와 초기 월드 적재는 LOGH-28에서 이어간다. 원본 서버의 모든 개별 수치를 복원했다는 의미는 아니다.
