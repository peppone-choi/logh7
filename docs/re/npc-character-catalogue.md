# 원작 NPC의 이름·얼굴·능력 대응과 로컬 편집 도구

작성자: 최병호 · 2026-10-27

## 확인한 결론

**이름이 출력되는 UI는 있으나, 현재 확보한 CD 자산에서 이름·얼굴·능력의 완전한 대응표를 찾지는 못했다.** 서버가 보낸 인물 정보를 표시하는 경로와 설치본에 들어 있는 얼굴 이미지의 번호 체계는 확인할 수 있다. 원 서비스 DB가 모두 복원됐다는 뜻도, 모든 이름이 소실됐다는 뜻도 아니다.

| 항목 | 확보한 단서 | 남은 부분 |
|---|---|---|
| 이름·진영·초기 직책 | 매뉴얼 초기 담당자 75행을 동일 진영·동일 보유자 표기로 묶으면 70개 항목(제국 31, 동맹 39) | 전체 등장인물 목록은 아님. 약칭·계급 표기의 인물 동일성은 추가 대조 필요 |
| 얼굴 이미지 | `oem.tcf` 158장, `oam.tcf` 108장, `o.tcf` 25장, 합계 291장 | 이미지에 이름이나 능력치가 들어 있지 않음 |
| 얼굴 ID | 제국 남성 슬롯 n → n, 동맹 남성 슬롯 n → 100000+n. 일부 여성·기타 원작 얼굴도 로더에서 대응 가능 | 특정 이름이 어느 슬롯인지 연결하는 자료는 별도로 필요 |
| 능력 8종 | 매뉴얼에 능력의 의미, 클라이언트에 전송·표시 형식이 있음 | 전체 인물의 원래 초기 수치표는 미확보 |

이름·직책은 `evidence:manual`, 이미지·번호·표시 경로는 `evidence:client`다. 얼굴만 보고 인물을 추정한 결과는 별도의 `evidence:guess`로 기록해야 한다.

## 이름이 나타나는 곳과 데이터의 출처

- **원작 캐릭터 응모 목록**: `0x120f` 후보 레코드에 서버가 이름·계급·얼굴·나이를 보낸다. CD 수신기 `00565d60`과 기존 [생성·응모 분석](../protocol/character-creation.md#원작-캐릭터-응모)에 근거한다. `evidence:client`
- **인물 정보·월드 인물 목록**: `0x0323` 인물 상세에는 이름·얼굴·능력들이 들어 있다. 변경 전달 `0x0356`도 같은 인물 레코드를 사용한다. 서버의 `BootstrapMessages.character`가 이를 구성한다. `evidence:client`
- **스폿의 얼굴 이름표·인물 명단**: 보유 인물 객체의 이름·계급·얼굴로 표시한다. 이름을 얼굴 파일에서 역으로 조회하는 구조가 아니다. 기존 [스폿 배경 인물 분석](../protocol/world-navigation.md)을 참고한다. `evidence:client`

현재 서버의 `OriginalCharacterMessages.localCandidates`는 키르히아이스·양 두 명에 얼굴 1000001, 능력 각각 50을 사용하는 접속 시험 자료다. 이 값을 원작 NPC 데이터로 확대하면 안 된다.

CD의 MsgDat 22개를 기존 파서로 읽어 매뉴얼 담당자 이름과 대조했다. 검색에 걸린 항목은 훈장명·함선 설명·일반 메시지의 언급이었으며 이름→얼굴→능력 목록은 확인하지 못했다. EXE의 라인하르트 언급도 샘플 메시지 문맥이다. 알려진 이름의 문자열 검색으로 전체 데이터의 부재를 증명할 수는 없다. 공식 추가 데이터의 모든 바이너리를 새로 역분석하거나 클라이언트를 실행한 조사는 아니다.

## 얼굴 파일에서 확인한 내용

기존 정적 내보내기 `work/spot-background-20261025/static/`의 다음 함수를 다시 읽고 CD 원본 파일을 읽기 전용으로 대조했다.

- `00592c30`: 얼굴 ID의 자릿수에 따라 원작/제너레이트·진영·성별과 슬롯을 선택한다.
- `005924c0`: 해당 `.tcf` 파일을 열고 `tcf.hed`의 offset/size로 이미지를 읽는다.
- `005933e0`: 제너레이트 얼굴은 나이 20·40을 경계로 세 변형 중 하나를 선택한다. 원작 얼굴은 그 분기를 사용하지 않는다.

`evidence:client`

`.tcf`는 50바이트 머리말 뒤 **비압축 8비트 인덱스·32비트 BGRA 팔레트 TGA**가 연속된 파일이다. 관찰한 이미지는 높이 80, 폭 62~64였다. `tcf.hed`는 10,840바이트다. 원작 계열은 다음 영역을 쓴다.

| 파일 | HED 시작 레코드 | 슬롯 수(빈 슬롯 포함) | 실제 이미지 수 |
|---|---:|---:|---:|
| oem.tcf | 0 | 200 | 158 |
| oam.tcf | 200 | 150 | 108 |
| o.tcf | 350 | 100 | 25 |

각 레코드는 LE `offset:u32, size:u32`다. **빈 슬롯을 제거하고 순번을 다시 매기면 얼굴 ID가 틀린다.** 특히 `o.tcf`는 원작 여성·기타 인물과 제너레이트의 공용 변형을 함께 담는다. 291장을 모두 서로 다른 이름의 NPC 291명으로 셀 수 없다. `evidence:client`

`o.tcf`의 원작 얼굴 대응은 슬롯 1~6 → 10001~10006(제국), 11~14 → 110001~110004(동맹), 21~23 → 200001~200003(기타)다. 나머지 12장은 편집기에서 공용으로 표시하고 임의의 고유 얼굴 ID를 부여하지 않는다. `evidence:client`

추가 네 파일의 TGA 연속 레코드도 읽어 `gem` 270장·`gef` 54장·`gam` 45장·`gaf` 9장을 확인했다. 이것은 제너레이트의 나이 변형을 포함하는 별도 계열이며 이번 NPC 편집기는 이 378장을 가져오지 않는다. 이 계열의 HED 구조는 원작의 단순한 레코드 순번과 섞지 않는다.

## 복원 경로

1. 매뉴얼의 이름·진영·초기 직책을 출발점으로 삼는다. 이미 확보한 `initial-card-holders.csv`를 다시 만든 별도 명부로 교체하지 않는다.
2. VII 당시 응모 목록·인물 상세·플레이 기록의 **이름과 얼굴이 함께 보이는 화면**이 있으면 CD 이미지와 대조해 얼굴 ID를 연결한다. 외형만 알아본 경우는 추정으로 둔다.
3. 능력 수치가 보이는 화면은 세션 날짜·패치 버전·인물 나이도 확인한다. 성장 후의 현재 수치를 초기 수치로 옮기지 않는다.
4. 확인되지 않은 능력치는 `null`로 유지한다. 운영에 필요한 설계값은 출처/이유를 적고 추정으로 저장한다. 다른 시리즈의 능력 수치를 VII의 원래 수치로 확정하지 않는다.

당시 공개 자료의 추가 검색에서도 전체 대응표는 찾지 못했다. [2004-02-27 테스트 모집 기사](https://www.4gamer.net/news/history/2004.02/20040227203229detail.html)는 오프레서·라인하르트·파에타·호우드의 이름·진영·당시 계급을 제공한다. [당시 플레이어의 VII 안내](https://toshichan.my.coocan.jp/fcgamem2/gin7/index.html)는 검색 색인에 남아 있으나 이번 웹 열람은 403으로 본문·이미지를 확인하지 못했다. 따라서 여기에서 얼굴·능력 수치를 복원했다고 기록하지 않는다. 검색일: 2026-10-27.

## 로컬 편집 도구

`tools/assets/npc_catalogue.py`가 읽기 전용으로 게임 얼굴을 추출하고 독립 HTML 편집기를 생성한다. 기본 명단은 **450개 인물 후보 항목**이다. 매뉴얼 초기 담당자 70항목의 직책·진영은 유지하고, 위키의 본편·외전 제국/동맹/페잔 인물 380항목을 추가했다. 역사 속 인물·동물·함선·이름 없는 직종은 제외했다. 추가 후보의 VII 등장·시나리오 시작 당시 생존·소속·배치는 확인된 것이 아니다. 확인 대기인 약칭·이역 표기가 있어 항목 수를 서로 다른 VII NPC 수로 해석하지 않는다.

이름과 출처는 `l10n/npc-roster.ko.json`, 매뉴얼 원어→한글 대응은 `l10n/npc-names.ko.json`을 사용한다. 기존 `initial-card-holders.csv`가 초기 직책의 원천이다. 내려받은 위키 본문과 모든 이미지·생성 HTML/JSON은 Git 제외 `work/`에만 쓴다. 두 도구 모두 Python 표준 라이브러리만 사용한다.

```powershell
$faceRoot = (Get-ChildItem -LiteralPath E:\logh7-original\extracted\install -Directory |
  Where-Object { Test-Path (Join-Path $_.FullName 'data/image/Face/tcf.hed') } |
  Select-Object -First 1).FullName
python tools/assets/npc_wiki.py `
  --output work/npc-catalogue-20261027/wiki-cache
python tools/assets/npc_catalogue.py `
  --face-dir (Join-Path $faceRoot 'data/image/Face') `
  --references work/npc-catalogue-20261027/wiki-cache `
  --output work/npc-catalogue-20261027/review-new
```

생성한 `index.html`을 로컬 브라우저에서 연다. 이름·진영·얼굴·계급·능력 8종·배치 메모·AI 프로필 메모를 편집하고 **변경 적용 → JSON 저장**으로 파일을 받는다. 나중에 JSON 불러오기를 쓰거나, 생성 명령에 `--catalogue <저장한 JSON>`을 추가해 다른 출력 폴더에 다시 만든다.

편집기는 인물 추가/삭제·진영/이름/직책 검색·초기 담당자/추가 후보 필터·참고 이미지 유무 필터·얼굴 미리보기, 중복 얼굴 배정과 진영 불일치 차단, 얼굴/능력의 근거 분류·출처 저장을 지원한다. 빈 능력치와 0을 구분한다. 얼굴을 고르면 육안 대조 추정으로 시작한다. 원작 전체 이름을 자동으로 붙이는 기능은 없다.

### 위키 이미지 비교

`npc_wiki.py`는 명단에 적힌 인물 문서의 이미지 후보를 인물당 기본 3장까지 내려받는다(`--per-person 1..6`). 병렬 요청은 3개로 제한하고 페이지 4 MiB·이미지 2 MiB 제한과 캐시를 사용한다. 원문에서 관찰한 지연 로딩 `data-src`와 미러의 `data-original`을 읽으며 국기·국장·아이콘·서명·비트맵이 아닌 파일을 걸러낸다. 이는 얼굴 검출·인물 식별이 아닌 문서 이미지 후보 추출이다. 다운로드 실패, 이미지 후보 없음, 캐시 성공은 구분해 기록한다.

‘기타 등장인물’ 문서의 인라인 이미지는 **그 이미지를 포함한 이름 항목에만** 연결한다. 여러 사람이 함께 있는 그림은 해당 항목에 적힌 인물들이 참고할 수 있으며 단독 얼굴로 확정하지 않는다. 예를 들어 클라젠 항목은 단체 이미지이므로 원문 주석을 함께 확인해야 한다. 문서 전체 이미지를 모든 단역에 공통 배정하지 않는다.

2026-10-27 수집 결과 **268개 항목에 참고 이미지 554건**을 확보했다(공유 이미지 포함). 참고 이미지가 없는 182항목도 이름으로 관리할 수 있다. 매뉴얼 명단의 코나리/추가 후보 코널리, 첸/찬 같은 표기는 인물 동일성을 확인하기 전까지 자동 병합하지 않는다. 이미지의 OVA·만화·DNT 차이와 단체/함선 그림 포함 가능성도 육안 확인 대상이다.

인물을 선택하면 게임 얼굴과 위키 이미지를 나란히 표시한다. 참고 썸네일을 누르면 비교 이미지를 바꾸고, 원문 출처 링크에서 문맥을 확인한다. 목록의 얼굴이 미지정이면 위키 참고 썸네일을 보여주며, 이는 게임 얼굴 배정을 뜻하지 않는다. 참고 이미지를 가져오는 것만으로는 얼굴을 연결하지 않는다. 이미지 선택과 게임 얼굴 선택은 별개다.

생성 폴더의 `reference-images/`를 `index.html`과 함께 보관한다. UI는 로컬 파일만 읽고 네트워크 요청을 하지 않는다. 캐시를 갱신한 뒤 새 출력 폴더에 다시 생성하면 새 이미지를 반영할 수 있다. `--references`를 생략하면 이미지 없이 명단과 게임 얼굴만 생성한다. 참고 자료 원천은 [등장인물](https://namu.wiki/w/은하영웅전설/등장인물)·[기타 등장인물](https://namu.wiki/w/은하영웅전설/기타%20등장인물)이며 [이름별 분류](https://namu.wiki/w/은하영웅전설/등장인물%20이름별%20분류)는 명칭 대조에 참고했다. 개별 문서 URL은 명단 및 로컬 참고 이미지 캐시에 보존한다.

### OVA와 직접 비교한 1차 얼굴 연결 — 2026-10-27

사용자 요청에 따라 게임 얼굴 전체를 살펴보고 주요 인물의 위키 그림과 확대 대조했다. 선택한 참고 그림이 위키 표의 **OVA 열**에 있는지도 저장된 원문 HTML에서 확인했다. 만화판·DNT 그림은 이번 연결 근거로 사용하지 않았다. 머리 모양·색, 눈매, 수염, 얼굴 윤곽 등 여러 특징이 함께 맞는 **19명(제국 9·동맹 9·기타 1)**을 먼저 연결하고 나머지 431항목은 비워 두었다. 모든 능력치는 계속 `null`이다.

연결의 원천은 `l10n/npc-face-matches.json`이다. 이름·얼굴 ID·OVA 그림 URL·그림 표제·판본 캡션·닮은 특징을 보존한다. 예: 라인하르트 112, 키르히아이스 26, 오베르슈타인 20, 로이엔탈 124, 양 웬리 100074, 율리안 100069. 외형을 직접 확인한 결과이므로 `confidence=high`이지만, 원작 서버 DB나 이름과 얼굴이 함께 뜬 VII 화면으로 확정한 것은 아니므로 **`face_evidence.status=guess`**를 유지한다. `evidence:guess`

새 기본 명단에는 이 연결을 적용한다. `--catalogue`로 다시 불러온 사용자의 JSON에는 기본 연결을 덮어씌우지 않는다. 편집기에서 ‘얼굴 연결 → OVA 대조한 인물’을 고르면 19명을 모아 볼 수 있고, 해당 인물은 대조에 사용한 OVA 그림을 처음부터 보여준다. 얼굴을 해제하거나 다른 얼굴로 바꾸면 종전 OVA 대조 표시는 제거한다. 비슷해 보이는 다른 후보나 OVA 그림만으로 구분하기 어려운 인물은 연결하지 않았다.

### 성·이름과 전체 표시명 분리 — 2026-10-27

게임 생성 패킷 `0x1008`은 **성(`surname`)과 이름(`givenName`)을 별도 문자열**로 보낸다. 현재 서버의 `CharacterMessages.Generate`와 저장소도 별도 필드를 사용한다. 문자열은 필드마다 마지막 NUL을 포함해 최대 13 UTF-16 코드 단위이며, 현재 코덱은 NUL을 제외한 BMP 문자 최대 12자를 허용한다. [생성 패킷](../protocol/character-creation.md#wire-필드), `CharacterMessages.kt`의 실제 검사에 근거한다. `evidence:client`

대조실의 `name`은 목록용 **전체 표시명**으로 보존하고, 별도로 `name_parts.surname`, `given_name`, `prefix`, `order`, `status`, `source`, `note`를 저장한다. `given_name`은 서버 `givenName`에 대응하는 편집 필드다. `prefix`는 성 앞에 붙이는 표시용 접두사로, 시스템 성·이름에는 넣지 않는다. wire 전송 순서는 성→이름이지만 전체 표시 순서는 문화권에 따라 따로 둔다. 양 웬리는 성=양·이름=웬리·성 먼저, 지크프리트 키르히아이스는 성=키르히아이스·이름=지크프리트·이름 먼저다.

`l10n/npc-name-parts.ko.json`에 검토한 **47명**의 분리값을 넣었다. 나머지 **403항목은 미확인 부분을 null**로 남기며, 공백만으로 모든 인물의 성·이름을 자동 추정하지 않는다. 예를 들어 빌리바르트 요아힘은 두 단어 모두 이름에 속한다. 사용자 결정에 따라 **14명의 ‘폰’을 별도 접두사로 분리**했다. 라인하르트는 성=로엔그람·이름=라인하르트·접두사=폰으로 저장하고 전체 표시명은 라인하르트 폰 로엔그람으로 조합한다. 이는 이 프로젝트의 성명 관리 정책이며 원작 서버가 모든 인물의 접두사·중간 이름을 어떤 문자열에 넣었는지 복원한 것은 아니다. `evidence:guess`

입력칸에서 성과 이름을 각각 편집하고 표시 순서를 고른 뒤 ‘성·이름을 전체 표시명에 반영’으로 표시명을 갱신할 수 있다. 부분 미확인과 검토 완료를 구분하며 완료 표시는 두 필드·순서·출처가 있어야 한다. 12자 초과·NUL·비 BMP 문자는 거절하고 문자열을 잘라 저장하지 않는다. 기존 JSON에 분리 필드가 없으면 미확인으로 표시하며 사용자의 표시명과 얼굴을 유지한다. 서버에 자동 반영하는 기능은 여전히 연결하지 않았다.

접두사는 별도 입력칸에서 최대 40자로 편집하며 성·이름의 12자 제한에 합산하지 않는다. 접두사 필드가 없는 구형 JSON의 성이 ‘폰 ’으로 시작하면 불러올 때 접두사를 분리한다. 기존 표시명·얼굴·능력치·사용자 메모는 유지하고, 이미 접두사가 명시된 데이터는 자동 변경하지 않는다. 새 데이터에서 성에 ‘폰 ’을 다시 넣으면 분리 입력을 안내한다.

### 옛 성과 시나리오의 이름 — 2026-10-27

라인하르트의 옛 성은 **뮈젤(Müsel, ミューゼル)**이며 로엔그람 백작가 계승 뒤 로엔그람을 쓴다. [나무위키 인물 문서](https://namu.wiki/w/라인하르트%20폰%20로엔그람)([열람한 미러](https://namu.moe/w/라인하르트%20폰%20로엔그람))의 옛 이름과 [공식 인물 소개](https://www.gineiden-neuesaga.com/character/)의 출생 가문·백작 칭호 설명을 대조했다. 공식 소개는 다른 게임의 원작 인물 설정을 확인하는 자료이며 VII의 시나리오나 OVA 얼굴 근거로 사용하지 않는다. 한글 기본 표기는 프로젝트 방침에 따라 뮈젤로 두고, 뮤젤은 검색용 변형으로 보존한다.

VII 웹 매뉴얼 p.60의 초기 담당자는 이미 **로엔그람 중장**이다(`initial-card-holders.csv`). 따라서 기본 NPC 명단의 현재 성은 로엔그람을 유지한다. `evidence:manual` 현재 서버의 795-01-01은 [잠정 시작값](../server/session-clock.md)이며, 이 날짜만으로 원작 인물의 성을 뮈젤로 일괄 교체할 수 없다. 매뉴얼 계급과 이름만으로 원작 연표상의 개성 날짜를 역산하지 않는다. 정확한 계승 날짜와 VII의 개명 이벤트 존재는 이번 자료로 확정하지 않았다.

대조실에는 `name_parts.aliases`에 라인하르트 폰 뮈젤·라인하르트 폰 뮤젤을 넣었다. 화면에서 옛 이름을 보고 두 성 모두 검색할 수 있으며 같은 항목·얼굴 112로 연결된다. 별칭은 검색과 출처 보존용이며 시스템 성·이름이나 현재 표시명에 자동 합치지 않는다. 사용자가 불러온 JSON의 현재 성·메모·별칭은 기본 명단으로 덮어쓰지 않는다.

향후 시나리오가 계승 이전으로 확인되면 그 시나리오의 현재 성을 뮈젤로 지정하고, 이후로 확인되면 로엔그람으로 지정하는 방안을 제안한다. 인물 식별자는 유지하며 얼굴·능력·직책·플레이어 담당 연결을 새 인물로 만들지 않는다. 현재 대조실의 `key`는 편집용 식별자이고 원작 인물 ID를 복원한 값은 아니다. 게임 중 개명을 지원할지는 원 서비스 자료와 시나리오 규칙을 확인한 뒤 결정하며 원작 연표 날짜에 따른 강제 개명은 구현하지 않았다. 이 단락은 복원 완료가 아닌 설계 제안이다. `evidence:guess`

사용자 요청에 따라 기본 명단 70명의 이름과 계급을 한글로 표시한다. 이름 대응의 단일 파일은 `l10n/npc-names.ko.json`이며 기존 용어집과 나무위키 등장인물·기타 인물 표기를 따른다. 매뉴얼 원어·출처는 별도로 보존하고 한글·일본어 모두 검색할 수 있다. 나무위키 본문은 직접 열람이 되지 않아 미러의 표시를 대조했으며 각 출처 URL과 조회일을 대응 파일에 남겼다. 표기·인물 대응이 미확정인 7명은 한글 임시 표기를 넣고 화면과 JSON에서 확인 대기로 표시한다. 목록은 [용어집](../l10n/glossary.md#npc-초기-담당자-명단-70명)을 따른다.

인물 상세 패킷의 능력 본값은 u16이고, 제너레이트 생성 요청의 능력은 u8이다. 이 도구는 인물 상세의 표현 범위 0..65535를 허용한다. 이는 게임 규칙의 능력 상한이나 제너레이트 생성 허용 범위를 복원한 것이 아니다. 수치가 하나라도 있으면 입력한 능력 전체에 대한 근거 분류·출처가 필요하다. 서로 다른 근거가 섞인 경우 출처란에 능력별로 나눠 적는다.

출력 JSON은 **편집 초안**이다. 서버 시드 로더·세션의 NPC 생성·플레이어 담당 전환·중복 방지·행동 AI는 연결하지 않았다. 배치와 AI 프로필도 실행 설정이 아닌 메모다. 원본 게임 파일·서버 설정·실행 중인 게임은 수정하지 않는다.
