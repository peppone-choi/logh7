# 설계안: 제안과 명령(提案と命令)·직무 주소 편지

작성: Peppone Choi · 2026-11-01 · 상태: 승인(사용자 2026-11-01, 제안대로)

## 1. 근거

- `evidence:manual` CD판 p.28~29 「提案と命令」(웹판에는 독립 절 없음, 커맨드 표에 존속)
  - 모든 명령은 요직에 있는 사관이 최종 결정한다. 요직이 없어도 명령과 제안으로 게임에 참여할 수 있다.
  - **명령**은 상관→부하, **제안**은 부하→상관. 명령·제안으로 실행한 명령은 공동 실행이며 **CP를 50%씩 분담**한다.
  - 제안은 결정권자에게 명령을 입력하는 형태이며, 결정권자가 「承認」하면 실행되고 「拒否」·「拒絶」하면 철회된다.
  - 같은 그룹의 직무 카드를 가진 인물끼리만 가능하다. 예외로 황제·정치가·반란군 맹주는 모든 직무 카드에 명령할 수 있다.
  - 위치: 전술이 벌어진 그리드의 인물은 불가. 전략 중이면 같은 공간 그리드, 시설 안이면 같은 스폿이어야 한다.
  - 절차: 직무 권한 카드 탭의 명령/제안 버튼 → 대상 인물(또는 직책) 선택 → 실행할 명령 입력 → 실행. 실행 시 낸 사람의 CP와 「영향력」을 쓴다. 영향력이 모자라면 낼 수 없다.
- `evidence:manual` 패치: 2004-06-11 발탁·강등·임명·파면·사임·할당의 명령/제안 도입(09-patch-history). 부재 중 제안 메일 처리 대행(~2004-12, U-16)은 별도.
- `evidence:client` 원본 직무 편지함은 일반 편지(0f0a)를 표시하지 않고 제안·명령 편지(0f13/0f14와 뒤따르는 명령 패킷 한 쌍)만 읽는다. 행은 개인 편지 뒤에 카드별로 붙고 직무 아이콘(행 종류 10~14·20~24)을 쓴다. 항목: 읽음, 두 주소, 시각, 제안 종류(0 제안·1 명령으로 추정), 회신값. [분석](../protocol/personal-mail.md#원본-직무-편지함은-제안명령-편지만-표시한다-2026-11-01-정적-분석)

## 2. 제안(초안)

### 2.1 흐름
1. 낸 사람이 카드 창의 명령/제안에서 대상 인물과 명령을 고르고 실행한다. 서버는 범위·위치·영향력·CP(절반)를 검사하고, 받는 직책의 편지함에 제안(또는 명령) 편지를 넣는다.
2. 받는 사람은 편지함 직무 행에서 그 편지를 열어 승인·거부·거절한다.
   - 제안 승인: 결정권자가 나머지 CP 절반을 내고 명령을 실행한다. 실패하면(조건 불충족) 양쪽 CP를 돌려준다.
   - 명령 수신: 부하가 승인하면 실행, 거부하면 철회.
   - 거부·거절: 철회하고 낸 사람에게 회신 편지(0f14)를 넣는다. 거부와 거절의 차이(설계 추정: 거절은 같은 사람의 같은 제안을 하루 막음).
3. 대상 명령은 2004-06-11 패치 범위부터 시작한다: 발탁·강등·임명·파면·사임·할당.

### 2.2 수치(설계 추정, 결정 필요)
- 영향력 소모: 제안 1·명령 1(설계 추정). 영향력이 0이면 낼 수 없다.
- 제안 유효 기간: 게임 24시간. 지나면 자동 철회하고 CP를 돌려준다.

### 2.3 통신 (`evidence:client`, 읽기 전용 정적 분석 `work/mailbox-re/`)
- 이름표: 0x0f13 CommandOrderSuggestMail, 0x0f14 CommandReplyOrderSuggestMail, 0x0f15 NotifyCommandMail.
- 0x0f13 (디코더 `004799c0`): u32 id, u32 refer_id, u8 status, 주소 SIC 보낸 이, 주소 SIC 받는 이(개인 편지와 같은 주소 형식, 끝 u32 3개 중 셋째가 카드 번호), u32 time, u16 command, u8 order_suggest_type, u8 influence, u32 pcp, u32 mcp.
- 0x0f14 (디코더 `0047ce40`): 같은 순서이되 pcp·mcp가 없고 u8 회신값으로 끝난다.
- 편지함 표시: 0x0f08 직무 조회 응답 안에서 편지마다 [0x0f13 또는 0x0f14 + 그 명령의 원래 패킷]을 보낸다. 명령 패킷 처리기가 world+0x3579cc를 보고 실행 대신 `004c2920`으로 편지 본문을 확정한다. 이렇게 처리되는 명령: 0c00·0b03·0c0b(할당)·0709(임명/사임 계열)·0706·0704·0705·0708·0900·0901·0902·0c05·0c02·0b04·0b05·0b06·0b02·0b0c·0707·0903·0906·0b00·0c01, 그리고 0f15·0f1f.
- 송신: 카드 창 명령/제안(`004f8ce0`→`004b4af0(card)`)이 대상의 카드와 다른 소유자일 때 0x0f13(디스패처 선택자 0x4f)을 보낸다. 레코드에는 보낸 이 ID·받는 이 ID·받는 이 카드만 채운다. 실제 명령 내용이 뒤따르는 명령 패킷으로 함께 가는지는 추정이다.
- 회신: 편지함의 세 버튼(`0053b820`, 선택값 0/1/2)이 선택한 0x0f13 행으로 0x0f14(선택자 0x50)를 보낸다. refer_id=원 제안 id, 두 주소를 뒤바꾸고 회신값=선택값. 0/1/2가 承認/拒否/拒絶인지는 추정이다.

### 2.4 구현 단계(제안)
1. 서버: 제안·명령 저장(직책 편지함, 이미 만든 직책 귀속 저장 구조를 재사용), 0x0f13 수신과 다음 명령 패킷의 묶음, 승인 시 기존 명령 실행 경로 호출, CP 절반 분담·영향력 소모.
2. 서버→원본: 직무 조회 응답을 [0x0f13/0x0f14 + 명령 패킷]으로 보내 편지함 직무 행 표시를 확인한다.
3. 원본 실기: 할당(0c0b)이나 임명(0709) 한 가지로 제안→승인→실행, 거부 회신을 확인한다.

## 4. 진행 기록 (2026-11-01)

- 원본 카드 창의 `명령 / 제안` 탭은 열릴 때 0x1200 검색 29를 보낸다(다음 u16 0x0984는 초기화 안 된 notify_type 칸, `evidence:client`). 서버가 이 검색을 몰라 접속이 끊기던 것(체크리스트 run-343의 search 끊김과 같은 계열)을 고쳤다.
- 탭 목록은 0x120e(NotifySimpleInformationOrderSuggestCharacter: 카드별 최대 10, 카드마다 인물 최대 10, 인물마다 명령 0/제안 1 구분+0x1202 인물 레코드)로 채워진다(정적 분석). 서버는 범위 안(시설 안이면 같은 스폿, 아니면 같은 그리드)의 같은 진영 인물 중, 자기 직무 카드와 같은 기관 카드를 가진 사람을 묶어 보낸다. 상대 계급이 높으면 제안, 아니면 명령이고, 황제 카드는 모두에게 명령이다(`evidence:guess`).
- 원본 확인(`work/chat8-20261101/run-12`): 응답 뒤 원본 메모리 world+0x58c6f4에 개수 1·카드 1·인물 10004(Epsilon)가 저장됐다. 그러나 탭 화면에는 행이 그려지지 않았다. 화면이 이 목록을 그리는 조건은 다음 분석 대상이다.
- 0x0f13/0x0f14를 받으면 지금은 내용만 기록하고 처리하지 않는다.
- 원인 확인(정적 분석 `work/mailbox-re/osc-*.decomp.txt`, `evidence:client`): 이 탭(창 모드 2, `005912e0`)은 0x1201 뒤 0x120e 목록을 모델 8번(`0056a590`→`0056d040`, world+0x58c6f8 개수·+0x58c6fc 항목)으로 받아 필터 없이 복사한다. 그러나 행을 만드는 루프(0x591401~0x591428)는 `004c8700()` 한 번만 부르고 결과를 버리며 행 개수(this+0xa20)를 늘리지 않는다. 따라서 보유 CD에서는 서버 값과 무관하게 행이 그려지지 않는다. 명령·제안은 2004-06-11 패치 기능이라 2004-04 빌드에 화면이 미완성으로 남은 것으로 본다(추정).
- 다음 단계 후보: 다른 누락 창처럼 호환 DLL이 이 루프(0x591422)를 대신해 world+0x58c6fc 항목으로 행을 만들거나, 별도 재구성 창(대상 선택 → 명령 선택 → 대행 모드에서 0x0f13+명령 패킷 송신)을 만든다. 행 추가 방식은 모드 3~5의 `00591450`을 참고한다.
- **받는 쪽 표시 확인(원본, `work/chat8-20261101/run-14`)**: 카드 25 직무 받은함 조회 응답 안에 [0x0f13 + 사임 0x0709]를 넣었다. 처음에는 행이 생기지 않았다. 원인은 원본 수신 큐가 명령 패킷의 첫 u32(time) 순서로 처리해 0x0709가 0x0f09 뒤로 밀린 것이었다(정적 분석, `rxqueue.decomp.txt`). 확정 플래그(world+0x3579cc)는 0x0f13/0x0f14 직후 한 패킷에만 켜진다. **명령 패킷의 time을 0으로 보내자** 편지함에 `Gamma Pilot · ✉ 명령 · 날짜` 행이 나타났고(보관 001/100), 행을 열면 `답변 대기 중...` 상태와 `거부`·`거절`·`답장` 버튼이 나왔다. 따라서 구분값 1은 명령, 0은 제안이다(앞의 추정과 반대). 본문 칸은 `NO TABLE`이라 명령 설명 표 연결이 남아 있다.
- 행을 열면 원본이 0x0f11(읽음)을 보낸다. 이때 직무 주소 칸 값은 카드 번호가 아니라 채워지지 않은 값(36173)이다. 서버는 이 요청을 받으면 확인 응답만 보낸다(접속 끊김 수정). 0x0f13 인코더와 검사를 추가했다.
- 남은 일: ① 제안·명령 저장과 0x0f13+명령 패킷(time 0) 송신을 실제 데이터로, ② 원본의 거부·거절·답장 버튼 회신(0x0f14) 처리와 승인 시 명령 실행, ③ 보내는 쪽 화면(보유 CD의 명령/제안 탭은 행 생성 코드가 비어 있음)의 DLL 재구성, ④ 본문 `NO TABLE`.
- **회신 버튼(원본, `work/chat8-20261101/run-17`·`run-r510`·`run-r537`)**: 제안 행 상세의 세 버튼은 모두 0x0f14 CommandReplyOrderSuggestMail을 보낸다. refer_id=원 제안 번호, 두 주소를 뒤바꾸고, time·command·type은 0이다. 회신값은 `거부` 0·`거절` 1·`답장` 2다. 화면 결과 문구는 constmsg 22번 그룹의 78+회신값(78 이 명령을 거부했습니다·79 거절했습니다·80 그대로 답장)이고, 한 번 회신하면 버튼이 사라진다. 22/77 `이 명령을 수락했습니다`는 버튼 회신이 아닌 다른 경로로 보인다. 툴바 다섯째 버튼(한국어 표시 `승인`)은 0x0f12 CommandDeleteMail을 보내 목록에서 지운다. 원작의 승인(承認)이 어떤 송신으로 이뤄지는지는 정적 분석 중이다.
- **승인 경로 분석(`approve.decomp.txt`)**: 편지함에서 보낼 수 있는 것은 세 버튼의 0x0f14뿐이다(`0053b820`). 버튼은 아직 회신하지 않은 받은 제안 행에서만 켜진다. 명령을 대행 모드로 다시 보내는 경로는 없다(대행 모드는 명령 창 대상 선택 `004fd437`에서만 켜진다). 결과 문구는 행 종류 %10이 0일 때 22/77, 1~4일 때 22/78~81이다. 회신하면 행 종류가 +회신값+1 되므로, 버튼 0·1·2의 결과 문구는 78 拒否·79 拒絶·80 オウム返し(원문)이다. **보유 CD의 받는 쪽에는 承諾 버튼이 없다.** 22/77 `この命令については承諾しました`는 미회신 행이나 회신값 0인 회신 행에 나온다. 제안자에게 결과를 보여 줄 0x0f14는 +0x25b에 '받은 회신값+1'을 넣고, 짝 패킷(0x0f15 NotifyCommandMail 또는 명령, time 0)을 바로 뒤에 보내야 행이 생긴다. 툴바 다섯째 버튼의 `승인` 표시는 0x0f12(삭제)이므로 번역 오류로 보인다.
- **사용자 결정(2026-11-01)**: 승인은 호환 DLL이 제안 행 상세 창에 `승인` 버튼을 더해 0x0f14 회신값 3으로 보낸다. 서버는 3을 승인으로 처리해 명령을 실행한다. 기존 세 버튼(拒否 0·拒絶 1·オウム返し 2)은 원문 의미대로 둔다.

## 5. 서버 구현 (2026-11-01)

- 엔진: `Proposals`(편지 한 통: 보낸·받는 사람과 카드, 짝 명령, 명령/제안, 생성·만료, 회신 -1~3, 보낸 사람 CP)와 `ProposalActions`(사교 처리 경로). 열기(98)는 보낸 카드 보유, 같은 진영·범위(시설 안 같은 스폿, 그 밖은 같은 그리드, 전술 제외), 받는 사람의 대상 카드 보유, 같은 기관(황제 카드는 전체), 영향력 1을 검사한다. ## 정치가의 직무 명령 (2026-11-10)
