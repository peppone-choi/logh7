# 함선·병력 자동 생산과 창고

작성: 최병호 · 2026-10-25 · 관련: LOGH-33, 실제 플레이 완성 체크리스트 §5

행성별 자동 생산표를 일일 경제 정산과 연결한다. 결과는 함선·승조원·육전병의 창고 재고이며, 함대 배속·재편성·보충·전투 사용은 후속 범위다.

## 원자료와 설계 구분

- 행성별 품목: 매뉴얼 PDF p.76–78의 기존 `initial-deployment.csv`. 원본 216행을 수정하지 않는다. 함종·병종 정의와 생산 기간은 기존 함선/병원 시드를 사용한다. `evidence:manual`
- 일반 함선 106종의 종류 번호는 원본 constmsg 그룹 85, 병력 11종은 그룹 86에 맞춘다. 제국 전함Ⅰ은 종류 32, 동맹 전함Ⅰ은 119이며, 기함 종류 0과 구별한다. 숙련도 Green은 그룹 117의 값 0이다. `evidence:client`
- 생산 기간 수치를 게임 시간으로 해석하고 1G일마다 24시간씩 공정을 진행한다. 생산표의 같은 품목 반복은 한 배치의 수량으로 해석한다. 완전히 같은 중복 행만 한 번 적용하고, 동일 행성의 서로 다른 행은 합친다. 이 시간 단위·수량 해석은 확정된 원작 공식이 아니다. `evidence:guess`
- 원표의 상륙정/상륙함 표기 차이는 품목 조인에서 명시적으로 대응한다. 에인헤리야르 행의 함선 칸에 들어 있는 함대 승조원은 실제 병종 정의에 따라 병력으로 취급한다. CSV 자체는 보존한다. `evidence:guess`

지도 이름과 생산표의 표기 차이 18쌍은 `UnitProduction.names`에서만 명시적으로 대응한다. 유사도에 의한 자동 연결은 하지 않는다. 니더빈딩게/니더빈덴보른 등을 포함한 대응은 설계 추정이며 원본 복원 확정값이 아니다. 현재 로컬 지도에서 생산표의 213개 거점이 모두 연결됨을 확인했다. 새 지도나 원자료 대조 결과가 나오면 이 대응과 시험을 함께 수정해야 한다. `evidence:guess`

## 현재 생산 정책

아래 비용과 인원 규모는 소실된 서버 로직을 대신하는 설계값이다. `UnitProductionPolicy`에 모아 둔다. `evidence:guess`

| 대상 | 한 유닛 완료 시 비용 |
|---|---|
| 함선 | 생산 기간 × 광물 10, 생산 기간 × 군수물자 5 |
| 승조원·육전병 | 식량 100, 광물 10, 군수물자 20, 성인 인구 1000 |

성인 인구의 모병은 전체 인구에서도 같은 수를 차감한다. 재고 숙련도는 Green으로 시작한다. 정규 제국/동맹 소유, 식량 충족, 성인 인구가 있어야 공정이 진행하며 함선은 조병공창(시설 종류 10)이 필요하다. 생산표에 함선 품목이 있는 요새 6곳도 이 조건을 충족하도록 요새 기본 시설에 조병공창을 추가했다. 원표의 생산 가능 근거와 달리 구체적인 시설 배치는 설계값이다. 점령지에서 적 진영의 기존 품목을 생산하지 않는다. 점령 후 생산표 전환 규칙은 아직 없다.

비용을 전부 지불할 수 있을 때만 한 배치를 입고한다. 자원 부족·창고 상한이면 비용을 차감하지 않고 완료 직전 공정으로 보존한다. 각 종류/숙련도 수량은 wire의 u16 상한 65535이며 배치가 상한을 넘으면 남는 자리만 생산한다. 최대 함선 99스택·병력 24스택이다. 공정이 진행되지 않는 날을 나중에 소급 생산하지 않는다.

경제의 식량·인구 정산 다음에 함선/병력 생산을 적용한다. 동일 월드 액터에서 같은 날짜 watermark를 사용하므로 조회·재접속 횟수로 생산이 늘어나지 않는다. 병종별 노동 배분, 병영/훈련소 가동 상태, 선착순 주문, 생산 예약·취소, 수동 건조는 미연결이다.

## 저장과 표시

`LOGH7-STOCK-3`는 기존 STOCK-2의 10열 뒤에 함선·병력·공정 세 부분을 담은 한 열을 추가한다. 예: `S32.0.3;T3.0.5;S32.48,T3.96`. 물자·인구·완성품·미완성 공정은 같은 파일을 force한 뒤 원자적으로 교체한다. 저장 실패 전에는 결과를 공개하지 않는다.

STOCK-1/2를 읽을 수 있으며, 기존 물자·인구·정산 일자는 유지하고 유닛 재고는 비어 있는 상태로 시작한다. 이미 정산한 날짜의 유닛을 소급 생성하지 않는다. **이전 서버 바이너리는 STOCK-3을 읽지 못하므로 이관 전 파일 백업이 필요하다.** 새 세대에서는 재고·공정도 초기화한다.

`0326→0327` 창고 응답에 종류:u16·숙련도:u8·수량:u16 목록을 전송한다. 원본은 한 행을 패딩 포함 6바이트로 보관한다. 호환 모듈의 전용 행성 조회 화면은 ‘창고’ 탭에서 최대 8행씩 표시하고 이전/다음 재고 버튼으로 페이지를 바꾼다. 행성은 왼쪽 목록에서 별도로 선택한다. 이름은 원본 품목 이름을 사용하며 새 조회에서는 개요로 돌아온다. 후속 [생산 유닛의 성능 목록](unit-specifications.md)에서 일반 함선/병력 정의와 유닛당 척수 표시를 연결하고, 병력 통신 종류를 원본의 1000 기반으로 수정했다. 저장 번호 0 기반은 유지한다. 전투 사용과 세부 형식별 정확한 모델 복원은 남아 있다.

## 검증

관련 엔진·저장·프로토콜·암호화 TCP 시험은 생산 기간, Green 수량, 비용·모병 인구 차감, 자원 부족·상한·적 소유·기아 중단, 저장 실패, 반복 조회, 여러 날 정산과 재시작 분할 결과의 일치를 확인했다. 제국/동맹의 자기 함종 생산과 적 소유 시 중단, 요새 조병공창 조건을 검사했고 엔진·게이트웨이 회귀 검사와 x86 경고 오류 처리 빌드도 통과했다.

로컬 가속 시계(1000배속)의 원본 클라이언트 한 개에서 오딘의 2일째 구축함Ⅰ 2·구축함Ⅱ 1을 표시했다. 양쪽을 종료·재시작해 3일째 재고와 미완성 공정을 복원한 뒤, 5일째 전함Ⅰ 1·고속전함Ⅰ 1·순양함Ⅰ 1·구축함Ⅰ 8·구축함Ⅱ 3, Green 육전병 4·함대 승조원 5를 확인했다. 클라이언트의 디코딩 재고와 서버 파일의 종류·숙련도·수량·세 물자가 일치했다. 재고 뒤 다음 행성, 닫기·재열기 동작도 확인했다. 원본 보존·대상 프로세스 정리·오디오 복원을 확인했다. `evidence:client`

캡처·읽기 전용 캐시 검사·재시작 전 저장 사본은 `work/unit-production-20261025/`에 보존한다. 실제 두 클라이언트 동시 생산 조회, 10행 이상 페이지 전환, 전투정·함대 배속/보충·생산품 전투 사용은 이번 확인 범위에 포함하지 않았다.

## 할당·재편성 연결 진행

원본 출력 함수 `00551a80`(재편성 `0c02`)·`00553fc0`(할당 `0c0b`)를 따라 패딩 없는 요청 리더 `LogisticsMessages`를 추가했다. 재편성 단계 값은 u8, 할당의 같은 위치 값은 32비트다. 빈 요청 길이는 opcode를 포함해 각각 42·45바이트다. 종류:u16·등급:u8·수량:u16 목록은 함선 최대 99행·병력 최대 24행이며, 할당에는 이동 두 목록 다음에 행성 결과 두 목록·부대 결과 두 목록도 있다. 수량의 16비트 패턴을 보존하며, 반출입 방향·메타데이터 의미를 아직 확정하지 않은 필드는 불투명 값으로 유지한다. `evidence:client`

엔진 `UnitTransfer`는 종류·숙련도별 양방향 이동을 두 재고에 함께 계산한다. 잔고 부족·수량 또는 행 수 상한이면 결과를 만들지 않고, 생산 공정은 유지한다. 클라이언트 결과 잔고를 입력으로 받지 않는다. 후속 `OutfitLogistics`가 아래 권한·예약·저장을 묶지만, 원본 할당/재편성 메시지를 실제 변경 명령으로 연결한 것은 아니다.

필드 순서·두 단계 값의 폭·여섯 목록·모든 잘림 길이·초과 목록·후행 바이트 거부와 재고 보존·역방향 이동·후반 실패 시 원본 불변·수량/행 수 한도·호출자 맵 변경 차단 검사가 통과했다. 분석 출력은 `work/fleet-logistics-20261025/`에 있다.

### 부대 상태와 예약·저장

`PlanetStocks`에 부대·부대 창고·병참 담당 직책을 추가했다. 창고는 거점에 고정되며, 함대/수송함대의 사설 창고에는 소유 부대도 기록한다. 부대가 이동하더라도 이전 거점의 재고가 따라 이동하지 않는다. 순찰대·지상부대의 부대별 구분 없는 공유, 사설 창고의 다른 부대 사용 제한과 할당 직책은 웹 매뉴얼 PDF p.42–44(인쇄 p.41–43), §7.3–7.5에 근거한다. 현재는 같은 진영·거점의 순찰대와 지상부대가 같은 창고를 공유한다. 매뉴얼의 공유 설명과 원본 이름 그룹 91의 결합 분류를 함께 반영했다. 원본 종류 번호는 함대 0·수송함대 1·순찰대 2·지상부대 3이다. 기존 별도 공유 창고 두 개를 가진 파일은 임의 합산하지 않고 참조 검사에서 거부한다. `evidence:manual`(공유·직책·거점 내 재편성), `evidence:client`(그룹 83·91)


월드 액터의 `WorldCommand.Logistics`는 접속·세대·서버에 저장된 인물/진영, 할당 담당 직책 또는 부대 지휘권을 확인한다. 준비는 재고를 바꾸지 않고 예약 번호를 발급하며, 확정은 그 번호와 접속을 다시 확인한다. 할당과 재편성은 전역 상호 배제, 공유 창고를 쓰는 재편성끼리는 창고 단위 상호 배제를 적용한다. 최종 함선 수가 요구하는 승조원 유닛 수와 실제 승조원 수가 같아야 편성한다. 상선의 필요 승조원은 매뉴얼 값 0이다. 군수물자 할당도 양쪽 잔량을 함께 검사한다.

현재 예약 만료는 현실 시간 120초, 할당 원천은 대상 부대가 있는 거점, 재편성은 지휘관이 같은 거점에 있고 이동·보급·전술 중이 아닐 때로 제한한다. 이 구체적인 시간·위치 정책은 복원된 원작 규칙이 아닌 서버 설계값이다. 취소·만료·접속 종료·서버 재시작 뒤에는 예약을 재사용하지 않는다. 실패한 재고/승조원 검사는 수정 후 재시도할 수 있고, 저장 I/O 실패 뒤에는 월드 변경을 차단한다. `evidence:guess`

`LOGH7-STOCK-6`은 부대별 함정 유닛 ID와 다음 ID를 초기 배치 표식·부대 번호·휴대 물자에 추가한다. `P` 행성·`O` 부대·`W` 부대 창고·`A` 병참 직책을 **한 파일**에 저장한다. 종류별 수량·군수물자·유닛 ID를 함께 계산한 뒤 파일 내용을 force하고 원자적으로 교체해야 새 상태를 공개한다. 행 수 불일치·중복·참조 소실·잘못된 공유 관계·수량과 ID 불일치는 빈 상태로 대체하지 않고 기동 실패로 처리한다. STOCK-1~5를 읽어 기존 재고·공정·정산 일자를 유지한다. 이전 형식에 유닛 ID가 없으면 아래 절차로 한 번 부여하며 병력 수량을 복구하거나 보충하지 않는다. **이전 서버는 STOCK-6을 읽지 못하므로 전환 전 백업이 필요하다.**

조회 `0326→0327`는 저장된 부대 창고를 사용할 수 있다. 요청 거점·부대·진영이 맞고, 그 창고를 쓰는 지휘관이나 해당 분류의 할당 담당 직책이어야 한다. 응답의 부대 ID는 요청한 부대를 유지하며 내부 공유 창고 ID를 노출하지 않는다. 행성 재고와 부대 재고를 섞지 않는다.

검사: 할당→재편성 수량/군수물자 보존, 저장 후 재개, 위조 접속·세대·인물·진영 및 잘못된 직책 거부, 서로 다른 접속 ID의 액터 요청 경합, 취소/만료 예약의 재사용 거부, 저장 실패 시 양쪽 불변과 월드 변경 차단이 통과했다. STOCK-3 이관·STOCK-4 재개·잘린 파일과 잘못된 공유 관계 거부, 암호화 TCP의 자기 부대 창고 조회도 통과했다. 관련 엔진·저장·프로토콜·게이트웨이 회귀 검사를 통과했다.

원본 한 개의 조회 확인: 시험용 거점 1049·부대 1·창고 101과 시험 계정의 지휘권을 사본 데이터에 설정했다. 원본 조회 로더/UI를 소유 게임 스레드에서 호출해 `0326→0327`을 실행했다. 최종 거점 고정 구조의 서버·클라이언트를 모두 재시작한 뒤 함선 종류 32·등급 1·3유닛, 병력 종류 1003·등급 0·15유닛, 군수물자 54321·식량 123·광물 456이 원본 디코딩 결과와 파일에서 일치했다. 원본 창의 부대 창고 열에 승조원 15유닛을 표시했다. 제목·상대 창고/대상 편성 정보는 아직 비어 있거나 기본 이름이며, 정식 카드 진입·편집·확정 시험이 아니다. 이 시험 데이터를 일반 월드에 복사하지 않았다. 기록·화면은 `work/fleet-logistics-20261025/native-03/`, `native-04/`에 있으며 원본 해시 보존·소유 프로세스 종료·음향 복원도 확인했다. 실제 원본 두 개의 동시 편성은 미확인이다. `evidence:client`

매뉴얼 초기 배치와 `032b` 정의·그리드 부대 조회는 [초기 배치 런타임](initial-deployment-seed.md#런타임-초기-배치-연결-2026-10-25)에 연결했다. 아래 후속 변경은 개별 유닛 ID와 무지휘관 편성 조회를 지원한다. 남은 연결은 직책 임명/부대 가입, 지휘관/부대원 응답과 편성 명령 문맥, 원본 명령 준비·취소·확정 메시지와 공통 CP/시간 파이프라인, 공유 분류 범위의 원본 대조, 끝수 유닛 합산·손상·보충, 원본 UI에서의 실제 편집·확정이다. 지금의 예약/저장 검사만으로 플레이 완료를 체크하지 않는다.

### 상비 함정 유닛의 식별자와 편성 조회

작성: 최병호 · 2026-10-25

`ActiveShipUnit`은 함종/숙련도 스택의 함정 **1유닛**을 식별한다. 일반 함정 1유닛의 300척을 각각 ID로 만들지 않는다. 행성/부대 창고는 계속 종류별 합산 재고이며, 부대 편성 시 활성 유닛을 만든다. 기존 수량에서 최초 한 번 ID를 부여하고, 재편성에서 유지되는 같은 종류/숙련도 유닛은 ID를 보존한다. 창고로 돌아간 유닛의 ID는 폐기하고 다시 편성하면 새 ID를 받는다. 이 수명 규칙은 합산 창고와의 연결을 위한 서버 설계이며 손상/끝수 합산의 원작 복원은 아니다. `evidence:guess`

ID는 세대 안에서 1~999999를 사용하고 개인 기함의 `1000000+인물 ID`와 분리한다. 다음 ID도 같은 저장 파일에 기록하므로 재시작 후 폐기된 ID를 재사용하지 않는다. 고갈·중복·부대별 수량 불일치·다음 번호 역행은 거부한다. 원본 `032f`의 함정 목록 60행, 행마다 유닛 ID 70개라는 구조 상한도 초기화/재편성 전에 검사한다. 이는 원작의 직책별 편성 정원 확정값이 아니다. `evidence:client`(통신 상한), `evidence:guess`(ID 구간·수명)

`032e→032f` 편성 조회는 실제 부대 ID·거점·통신 종류·번호, 함종별 유닛 수·척수·ID 목록, 병종별 숙련도·수량·휴대 군수물자를 사용한다. 현재 연결은 mode 0의 상비 편성 조회이며 다른 모드는 거부한다. 패키지와 분리 편성은 아직 없으므로 그 목록은 비어 있다. 지휘관/부대원 응답은 미연결이므로 지휘관이 이미 지정된 부대는 빈 인물 목록으로 위장하지 않고 거부한다. 무지휘관인 초기 부대의 조회만 지원하며 인증된 자기 세력으로 한정한다.

`0330→0331`의 요청은 **유닛 ID와 거점 ID**이고 opcode 포함 10바이트다. 원래 송신기로 시험하면서 최초 ID만 처리하던 오류를 수정했다. 응답은 count:u8와 42바이트 유닛 기록이며 저장된 ID·함종·부대·그리드·거점을 연결한다. 유닛별 탑승 병력 인스턴스·군수물자·동원·항속은 아직 배정하지 않아 0이다. 초기 사기 100·손상/격침 0도 초기 상태의 설계값이며, 전투·수리·보급 구현 완료를 뜻하지 않는다. `evidence:client`(필드·폭), `evidence:guess`(미배정 자원·초기 상태)

편성의 군수물자 상한 표시는 함종 성능표의 물자 탑재량을 물리 척수에 곱한다. 지상부대는 병력 1유닛당 1000으로 표시한다. 이 환산과 지상부대 수치는 설계값이며, 실제 보급/적재 명령의 제한까지 연결한 것은 아니다. `evidence:guess`

검사: 기존 수량·숙련도·정산 일자 보존, ID 한 번 생성, 반납/재편성 후 재사용 금지, 외부 목록 수정 차단, 번호 고갈·중복·잘못된 수량/상한 거부, STOCK-5 이관과 STOCK-6 재개를 확인했다. 암호화 접속에서 편성 ID 목록과 같은 유닛을 조회하고 반대 세력·잘못된 거점은 거부했다. 기존 저장 I/O 실패 시험도 같은 유닛 ID와 재고가 공개되지 않음을 검사한다.

실제 원본 한 개의 읽기 전용 시험에서는 이미 전함 1유닛이 차감된 STOCK-5 사본을 이관했다. 원래 송신기/디코더로 전함 9·순양함 10·구축함 20유닛(각 2700·3000·6000척), 승조원 95유닛, 휴대 물자 99999를 읽었다. 첫 ID 1과 마지막 ID 39의 상세에서 같은 종류·부대 1·거점 1049·그리드 2487을 확인했다. 지상부대 1은 함정 목록 없이 경장육전병 5유닛으로 읽혔다. 서버 재시작 전후 264개 부대의 ID 목록과 다음 번호가 같았고 차감 유닛도 채우지 않았다. 이는 실제 전투 손실·가입·편성 편집 UI 시험은 아니다. 기록은 `work/outfit-roster-20261025/native-02/`에 두며 원본 해시 보존·소유 프로세스 종료·음향 복원을 확인했다. 일반 서버는 백업 후 새 형식으로 재개했다. `evidence:client`
