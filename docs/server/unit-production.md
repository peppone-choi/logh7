# 함선·병력 자동 생산과 창고

작성: 최병호 · 2026-10-25 · 관련: LOGH-33, 실제 플레이 완성 체크리스트 §5

행성별 자동 생산표를 일일 경제 정산과 연결한다. 결과는 함선·승조원·육전병의 창고 재고이며, 함대 배속·재편성·보충·전투 사용은 후속 범위다.

## 원자료와 설계 구분

## 현재 생산 정책

아래 비용과 인원 규모는 소실된 서버 로직을 대신하는 설계값이다. `UnitProductionPolicy`에 모아 둔다. `evidence:guess`

| 대상 | 한 유닛 완료 시 비용 |
|---|---|
| 함선 | 생산 기간 × 광물 10, 생산 기간 × 군수물자 5 |
| 승조원·육전병 | 식량 100, 광물 10, 군수물자 20, 성인 인구 1000 |

성인 인구의 모병은 전체 인구에서도 같은 수를 차감한다. 재고 숙련도는 Green으로 시작한다. 정규 제국/동맹 소유, 식량 충족, 성인 인구가 있어야 공정이 진행하며 함선은 조병공창(시설 종류 10)이 필요하다. 생산표에 함선 품목이 있는 요새 6곳도 이 조건을 충족하도록 요새 기본 시설에 조병공창을 추가했다. 원표의 생산 가능 근거와 달리 구체적인 시설 배치는 설계값이다. 점령지에서 적 진영의 기존 품목을 생산하지 않는다. 점령 후 생산표 전환 규칙은 아직 없다.

비용을 전부 지불할 수 있을 때만 한 배치를 입고한다. 자원 부족·창고 상한이면 비용을 차감하지 않고 완료 직전 공정으로 보존한다. 각 종류/숙련도 수량은 wire의 u16 상한 65535이며 배치가 상한을 넘으면 남는 자리만 생산한다. 최대 함선 99스택·병력 24스택이다. 공정이 진행되지 않는 날을 나중에 소급 생산하지 않는다.

경제의 식량·인구 정산 다음에 함선/병력 생산을 적용한다. 동일 월드 액터에서 같은 날짜 watermark를 사용하므로 조회·재접속 횟수로 생산이 늘어나지 않는다. 병종별 노동 배분, 병영/훈련소 가동 상태, 선착순 주문, 생산 예약·취소, 수동 건조는 미연결이다.

## 저장과 표시

`LOGH7-STOCK-3`는 기존 STOCK-2의 10열 뒤에 함선·병력·공정 세 부분을 담은 한 열을 추가한다. 예: `S32.0.3;T3.0.5;S32.48,T3.96`. 물자·인구·완성품·미완성 공정은 같은 파일을 force한 뒤 원자적으로 교체한다. 저장 실패 전에는 결과를 공개하지 않는다.

STOCK-1/2를 읽을 수 있으며, 기존 물자·인구·정산 일자는 유지하고 유닛 재고는 비어 있는 상태로 시작한다. 이미 정산한 날짜의 유닛을 소급 생성하지 않는다. **이전 서버 바이너리는 STOCK-3을 읽지 못하므로 이관 전 파일 백업이 필요하다.** 새 세대에서는 재고·공정도 초기화한다.

`0326→0327` 창고 응답의 함선 행은 종류:u16·유닛 수:u8·척수:u16이며 병력 행은 종류:u16·숙련도:u8·유닛 수:u16이다. 원본은 한 행을 패딩 포함 6바이트로 보관한다. 호환 모듈의 전용 행성 조회 화면은 ‘창고’ 탭에서 최대 8행씩 표시하고 이전/다음 재고 버튼으로 페이지를 바꾼다. 행성은 왼쪽 목록에서 별도로 선택한다. 이름은 원본 품목 이름을 사용하며 새 조회에서는 개요로 돌아온다. 후속 [생산 유닛의 성능 목록](unit-specifications.md)에서 일반 함선/병력 정의를 연결하고, 병력 통신 종류를 원본의 1000 기반으로 수정했다. 저장 번호 0 기반은 유지한다. 전투 사용과 세부 형식별 정확한 모델 복원은 남아 있다.

## 창고 응답의 함선 수량 교정 (2026-10-26)

원본 디버그 출력 `0041aff0`와 수신 `0041a870`은 함선 행의 두 번째 값을 유닛 수, 세 번째를 척수로 사용한다. 종전 서버는 이 자리에 숙련도·재고 유닛 수를 보내고, 전용 조회창은 이를 다시 환산했다. 자체 조회창의 숫자가 맞아 보여도 원본 창고 표에는 0유닛처럼 보이는 원인이었다. 함선과 병력의 행 타입을 분리하고 행성/부대 창고 양쪽을 교정했다. `evidence:client`

저장 재고의 함종·숙련도별 스택은 바꾸지 않는다. 조회 응답에서 같은 함종을 합산하고 현재 완전 유닛의 척수를 성능표로 계산한다. 함선 창고 응답에는 숙련도 필드가 없으므로 전용 조회창의 함선 등급은 `—`이고 병력 숙련도는 그대로다. 클라이언트가 척수를 다시 곱하지 않도록 서버와 호환 DLL을 함께 적용한다. 끝수 함정·숙련도별 개별 편성은 별도 미완료다.

한 함종의 유닛 수 255 또는 척수 65535를 넘는 저장 재고는 현재 응답에 표현하지 못한다. 이를 자르거나 하위 비트로 보내지 않고 거부하며, 대용량 재고의 원본 index/분할 응답 규칙은 미확인이다. 이는 저장/생산 수량 상한을 새로 줄인 것이 아니다. 해당 경계를 넘어선 조회의 정상화도 남은 작업이다.

원본 사본 한 개의 기존 창고 로더·표를 열어 오딘의 전함Ⅰ 1·고속전함Ⅰ 1·구축함Ⅰ 8·구축함Ⅱ 3유닛 표시를 확인했다. 수신기에는 별도로 순양함Ⅰ 1도 포함됐고 구축함Ⅰ은 8유닛·2400척이었다. 시험은 준비 명령 없이 창고 로더를 호출한 조회다. 표의 상대 창고는 여전히 미정이며 임명·편성 명령을 완료한 것이 아니다. 재시작 직후 활성 저장 재고는 전과 바이트 단위로 같았다. 두 번째 원본 접속에서는 실제 정보 메뉴→오딘→창고 탭으로 전함·고속전함·순양함 각 1유닛/300척, 구축함 8유닛/2400척과 구축함Ⅱ 3유닛/900척을 확인했다. 병력 4·5유닛의 그린 표시와 세 물자도 저장값과 같았고, 닫기·재열기 후 유지됐다. 이는 기존 정상 재고의 조회이며 새 할당이나 생산 명령을 실행한 것은 아니다. 프로토콜·게이트웨이 검사와 app 빌드, 혼합 숙련도 스택 합산/상한 거부 추가 검사, x86 `/W4 /WX`와 잘못된 EXE 변경 거부 검사가 통과했다. 원본 보존·소유 프로세스 종료·음향 정리를 확인했다. 자료는 Git 제외 `work/logistics-command-20261026/`에 둔다. `evidence:client`

## 할당·재편성 연결 진행

원본 출력 함수 `00551a80`(재편성 `0c02`)·`00553fc0`(할당 `0c0b`)를 따라 패딩 없는 요청 리더 `LogisticsMessages`를 추가했다. 재편성은 시각·인물 ID 뒤에 모드 u8과 PCP/MCP가 있다. **할당에는 이 모드가 없으며**, 시각·인물 ID·PCP·MCP·거점·부대·종류 순서다. 빈 요청 길이는 opcode를 포함해 각각 42·45바이트다. 시각·인물·잔고·결과 재고는 수신 필드일 뿐 권한이나 확정 잔고로 신뢰하지 않는다. `evidence:client`

두 명령의 이동 목록은 함선 최대 99행·병력 최대 24행이다. 함선 행은 종류:u16·이동 유닛 수:i8·척수:u16이고 병력 행은 종류:u16·숙련도:u8·이동 유닛 수:i16이다. 함선의 가운데 바이트를 숙련도로 해석하지 않는다. 할당의 결과 목록은 이동 목록과 달리 유닛 수가 부호 없는 u8/u16이며, 이동 두 목록 다음에 이동 군수물자:i32·행성 결과 두 목록·행성 결과 군수물자:i32·부대 결과 두 목록·부대 결과 군수물자:i32가 온다. 이전 코드의 `phase`, `baseMetadata`, 결과 목록 뒤 `outfit` 이름은 필드를 잘못 설명했으므로 교정했다. `evidence:client`(디버그 출력 `00551dd0`·`00554770`, 수신 `00555eb0`·`00558b70`)

재편성 끝의 정수 세 개는 병력 상한·승조원 상한·군수물자다. `LogisticsMessages.encode`는 opcode부터 시작하는 같은 원본 형식만 만든다. 세션 프레임·성공/실패 상태를 붙이거나 이 값으로 실제 월드를 변경하는 기능은 아니다. 실제 부대 지휘권·명령 준비·확정·CP/시간·끝수 함정 처리 연결은 아래 미완료 범위를 유지한다.

2026-10-26 비활성 데스크톱의 원본 사본에서, 게임 상태에 전달하지 않는 별도 입력 버퍼를 원본 디코더 두 개로 읽었다. 헤더의 거점 1049·부대 700·PCP 33·MCP 44, 함선 -1유닛/300척, 병력 -1유닛과 할당의 군수물자 -55를 구분했다. 결과 목록의 유닛 수 255/65535·척수 65535·행성 군수물자 77·부대 군수물자 66도 유지했고, 50/73바이트를 남김없이 읽었다(opcode 제외). 합성 입력 버퍼의 필드 검증이며 원본 UI에서 재고 이동을 실행한 시험은 아니다. 자료는 Git 제외 `work/logistics-ui-20261026/native-codecs.json`과 같은 폴더의 분석 출력에 둔다. `evidence:client`

엔진 `UnitTransfer`는 종류·숙련도별 양방향 이동을 두 재고에 함께 계산한다. 잔고 부족·수량 또는 행 수 상한이면 결과를 만들지 않고, 생산 공정은 유지한다. 클라이언트 결과 잔고를 입력으로 받지 않는다. 후속 `OutfitLogistics`가 아래 권한·예약·저장을 묶지만, 원본 할당/재편성 메시지를 실제 변경 명령으로 연결한 것은 아니다.

### 부대 상태와 예약·저장

`PlanetStocks`에 부대·부대 창고·병참 담당 직책을 추가했다. 창고는 거점에 고정되며, 함대/수송함대의 사설 창고에는 소유 부대도 기록한다. 부대가 이동하더라도 이전 거점의 재고가 따라 이동하지 않는다. 순찰대·지상부대의 부대별 구분 없는 공유, 사설 창고의 다른 부대 사용 제한과 할당 직책은 웹 매뉴얼 PDF p.42–44(인쇄 p.41–43), §7.3–7.5에 근거한다. 현재는 같은 진영·거점의 순찰대와 지상부대가 같은 창고를 공유한다. 매뉴얼의 공유 설명과 원본 이름 그룹 91의 결합 분류를 함께 반영했다. 원본 종류 번호는 함대 0·수송함대 1·순찰대 2·지상부대 3이다. 기존 별도 공유 창고 두 개를 가진 파일은 임의 합산하지 않고 참조 검사에서 거부한다. `evidence:manual`(공유·직책·거점 내 재편성), `evidence:client`(그룹 83·91)

검사: 네 부대 종류의 상한 수량 허용·한 유닛 초과 거부, 숙련도가 다른 추가 재고의 합산, 실패 뒤 반환으로 수정, 암호화 요청의 미리보기/확정·CP/재고/저장 횟수 보존과 서버 재개방 뒤 정상 반환을 확인했다. 엔진 411개·게이트웨이 127개에서 실패/오류 0(게이트웨이 조건부 5개 제외), 앱 배포 빌드를 통과했다. 자료는 Git 제외 `work/outfit-formation-limits-20261026/`에 둔다. 그리드 전체 300유닛·육전 병력/수송 정원·새 결성/합류 및 전술 편성은 별도 미완료다.

실제 원본 한 개에서는 시험 사본의 함대 60/60·창고 전함 1유닛을 조회하고, 원래 수량 조작으로 61유닛을 요청했다. 모드 0 거부 뒤 결정 단계로 진행하지 못했고 MCP 1000과 저장 편성 60·승조원 300·물자 100,000을 유지했다. 수량을 60으로 수정하면 정상 미리보기·결정 가능 상태와 물자 표시를 복원했다. 초과 편집의 원본 경고 문구에는 `NO DATA`가 남아 있으며 이번 서버 상한 검사로 해결한 것으로 처리하지 않는다. 나머지 세 종류는 암호화 접속 검사 범위이며 실제 원본 입력을 완료한 것은 아니다.

기존 상한 초과 저장 편성을 시작 시 자동 삭제하지 않고, 정상 한도까지 반환하는 내부 확정 회귀 검사도 추가로 통과했다.

두 원본 실행의 원본 보존·대상 프로세스 종료·작업 프로세스 0·음향 복원을 확인했다. 정상 반환의 실제 입력은 확인창까지 진행했고 실행 시한 전에 마지막 결정이 처리되지 않아 저장은 그대로였다. 이 정상 확정/재개방은 위 암호화 접속 검사 범위이며 이번 원본 실행 성공으로 세지 않는다. 일반 월드는 새 서버 런타임으로 다시 열고 시험용 60유닛 배치를 이식하지 않았다.
