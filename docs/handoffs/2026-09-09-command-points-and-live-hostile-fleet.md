### 남은 사격 차단점 (v266에서 더 좁힘)

`0050D3D7 mov ecx,0xc515f0`으로 **픽 매니저가 전역 0x00C515F0**임을 확정했고,
라이브에서 게이트를 전부 읽었다: `+0xA758=0`, 마스크 `0xA75C=0x1181`,
사거리 레코드 수 `0xA764=1`, sector ends `[0,0,5,0,5,5]`, sector 5, 거리 4.0.
플래그 0x1101도 004F12B0의 0x0001/0x0100/0x1000 검사를 모두 통과한다.
**즉 v262의 pick flag 가설은 기각됐고, E071/E074가 지목한 게이트는 전부 통과한다.**

실제 실패 원인은 **클릭 좌표**였다. 픽 레코드(0x00C51638, stride 0x3c)는
각 후보의 투영 화면좌표를 `+0x0C/+0x10`에 담고 있으며, 적함은 화면
**(555.87, 384.55)** 에 투영된다. 스프라이트가 보이는 (620,384)는 64px 떨어져
있어 004EF910의 8/16/32px 임계값 밖이다. 투영 좌표에 클릭한 뒤에도
`0x007CA550`이 2(자기 유닛)로 남아 있으므로, 射撃 표적 클릭이 지나는
004EF910 호출 지점(0050D99B / 0050D9F6 / 0050E1CD / 0050E1F2 / 0050FB93 중 하나)과
그 마스크·플래그 인자를 먼저 특정해야 한다.

**방법 규칙: 스프라이트가 아니라 픽 레코드의 투영 좌표를 클릭한다.**

### 해결 (v274) — 플레이어 사격 라이브 성공

정렬된 디스어셈블 004EF1BB..004EF221이 실제 구조를 보여줬다:

```
[node+0x2f]==0                 -> kind 0
[node+0x1c](투영 스케일) > K1  -> record 검사를 건너뜀
  아니면 [record+9]!=0         -> kind 0
[manager+4]==0 / [renderer+0xb20]>=3 -> kind 0
그 외에는 스케일에 따라 kind 1/2/3
```

즉 `[record+9]` 게이트는 **화면에 작게 그려질 때만** 적용된다. 자기 함은 그 바이트가
0이라 어느 배율에서도 선택되지만, 함대 NPC는 1이라 충분히 확대해야 선택된다.
그동안의 모든 시도는 그 임계값 아래 배율에서 클릭했기 때문에 0x0406이 나가지 않았다.

줌인 후 픽 노드가 kind 1로 바뀐 좌표(610,385)를 클릭하자:

```
0x0406 Success  tactical-command-accepted;name=shoot-ship;unit=2;
  target-unit=2113929477;target-damage=50;target-destroyed=0
```

PostgreSQL에 `2113929477/.../3/50/0/...` (피해 25→50, revision 10→11) 기록.
도발된 적함이 반격해 플레이어 기함을 격침(이벤트 89~92: 피해 25→50→75→100 →
부상 귀환 → 기함 재취득, grid 102 base 2). **진입·조준·사격·양방향 피해·격침·귀환**이
원본 클라이언트에서 한 세션에 모두 닫혔다.

**운영 규칙**: 표적 클릭 전에 픽 노드의 `kind != 0`을 확인하고, 그 노드가 게시한
`screenX/screenY`를 클릭한다. kind가 0이면 그 배율에서는 절대 선택되지 않는다.

### 撤退(0x0404)를 실제 이탈로 구현

전술 명령 패널 3행의 **撤退**(「戦術から離脱する」, 실행대기 48G초 / 소요
1800G초, 좌표 (791,699))는 **0x0404**를 보낸다. 지금까지 서버는 이 타입을
받아들이고 0x0425만 돌려줄 뿐 유닛을 움직이지 않았다.

이제 0x0404는 실제 귀환이다.

- 목적지는 캐릭터 자신의 귀환 기지(`ReturnBaseId`)를 정적 기지 카탈로그로 푼
  격자이며, 아군·같은 진영 기지여야 한다. 요청 자체는 유닛 ID만 담는다.
- 두 격자를 ID 순으로 임대한 뒤, 전략 0x0B01과 **같은** 권한 전이와 **같은**
  내구·멱등 기록을 사용한다. 따라서 항속 1이 워프와 동일하게 소모된다.
- 이미 그 격자에 있거나 카탈로그에 기지가 없으면 예전처럼 수락만 하고 아무것도
  움직이지 않는다.

라이브 영수증: `0x0404 tactical-warp-retreated;unit=2;source-cell=101;
destination-cell=102;authority-version=103`. DB `2/2/102/0/6/0/0/8/100/11`
(격자 102, mode 6, 무손상, 항속 9→8).

의미: 전술 화면에는 職務権限カード가 없으므로, 이길 수 없는 전투에 워프해
들어간 플레이어는 그동안 **빠져나올 방법이 전혀 없었다**. v280이 이를 lock-out
으로 기록하며 "클라이언트가 전술 격자에서 전략으로 나가는 경로를 제공할
때까지"라고 단서를 달았는데, 그 경로가 바로 撤退다.

1. **鼓舞 0x0409가 세션을 끊었다.** 네이티브 아이콘(896,628)이 보내는 몸체는
   `040908D24738000000020000000200000002`. 서버가
   `original.session-server.unexpected-application-type`로 거절하자 클라이언트가
   切断 / サーバーから切断されました。ゲームを終了します。를 띄웠다 — 旋回

## 후속 (v62) — 클라이언트가 말한 워프 비용 320MCP를 실제로 청구

### 원본 텍스트

> 通常はコマンドポイント320MCP消費、指示されている作戦目標に近接する場合は80MCP。

이것은 커맨드 포인트 경제에 대한 **원본 데이터**다. 지금까지 이 권한 서버는
포인트를 소비하지도 회복하지도 않았고, HUD의 1600/1600은 마이그레이션 초기값일

  추측하지 않는다.
- **비용은 원본**, **잔액·회복·상한은 승인된 저작 정책** 그대로다.

### 이동과 같은 트랜잭션에서 청구

`OriginalMoveGridWrite.Points`가 청구를 싣고, `MoveOriginalGridUnitAsync`가
같은 커넥션·같은 트랜잭션·같은 권한 버전에서 동일한 정책 코드로 적용한다.

- 청구가 거절되면 이동 전체가 롤백된다. 유닛은 움직이지 않고 포인트도 줄지
  않으며 클라이언트는 `コマンドポイントが足りません`을 본다.
- **한 플레이어 행동 = 한 권한 버전 = 한 도메인 이벤트.** 청구는 별도 이벤트를
  쓰지 않고 `OriginalGridUnitMoved`가 `commandPointCost`/`pcp`/`mcp`를 싣는다
  (`domain_event`의 `(account_id, authority_version)` 유니크 인덱스가 두 번째
  이벤트를 즉시 거부했다).
- 이동의 리플레이 가드가 청구도 덮는다. 원장 행이 이동의 지문으로 기록되므로
  같은 요청은 두 번 이동하지도, 두 번 청구되지도 않는다.
- 상태 해시가 유상 이동과 무상 이동을 구분한다. 청구 없는 이동의 해시는 종전과
  완전히 동일하다.

## 후속 (v66) — 항구에서 나가면 못 돌아오던 일방통행 문 닫기

### 클라이언트가 스스로 거절한 문장

후방 격자에 미도킹 상태로 있는 상태에서 職務権限カード → 出港을 누르면
**서버로 프레임이 가지도 않고** 로컬에서 거절하며 다음을 출력한다
(constmsg 2982, `client-refuses-stance-change-away-from-base-v320.png`):

> ※ 拠点から離れているため態勢変更できません。
> 宇宙空間にいる場合は、まず星系グリッドの拠点に向かって航行してください。

거절당한 그 상태는 **이 권한 서버가 만든 것**이다. `Transition`이 모든 격자
이동에서 `BaseId`를 0으로 지웠기 때문에, 한 번 워프한 유닛은 영구히 "기지에서
떨어진" 상태가 된다 — 주둔도, 재보급도, (v310 이후로는) 무한한 이동도 불가능.
저작 월드에는 메시지가 말하는 성계 내 항행이 존재하지 않으므로 이것은 난이도가
아니라 **일방통행 문**이었다.

### 추가한 규칙 2개

**전략 도착은 목적지 격자의 자기 기지에 소속된다.** 세션이 목적지 격자 콘텐츠
에서 (자기 진영·자기 캠프·실제 공용 기함 부두를 가진) 기지를 찾아
`OriginalMoveGridWrite.DestinationBaseId`로 넘기고, 전이는 운반만 한다 —
발명하지 않는다. 그런 기지가 없는 격자는 여전히 우주공간 도착이고, 타 진영은
그 기지가 자기 것이 아니므로 역시 우주공간 도착이다. 撤退도 같은 방식으로
캐릭터의 귀환 기지에 소속된다(어차피 그리로 가는 명령이다).

**자기 기지에 주둔하면 재보급된다.** 항속은 워프만 소비하는 저작 카운터이므로
보충이 없으면 월드가 편도다. 재보급은 태세 변경과 **같은 트랜잭션**에서
일어나므로 거절된 태세 변경은 아무것도 보급하지 않고, 출항은 아무것도 채우지
않는다.

## 후속 (v67) — 미구현 커맨드가 스스로를 기록하게, 그리고 태세 4종 회수

### 스윕이 싸졌다

거절된 操艦 커맨드가 자기 몸체를 응답 메타데이터에 실어 와이어 로그에 남긴다:

```
command-reject=TACTICAL_COMMAND_NOT_IMPLEMENTED;type=0x0409;
payloadHex=040908C1A738000000020000000200000002;design=new
```

鼓舞의 몸체가 선행 캡처와 틱(`08C1A738` vs `08D24738`)만 빼고 완전히 일치 →
형태 확정: `[u16 0x0409][u32 tick][u32 2][u32 2][u32 2]` 18바이트. 뒤의 세 워드는
모두 이 캐릭터/유닛 id와 같아 서로 구분할 수 없으므로 **필드명을 주장하지 않는다.**

그리고 세션이 살아남아 클라이언트가 권한 서버의 사유를 그대로 출력한다:
**「このコマンドはまだ使用できません」**. 예전에는 미구현 커맨드 하나가 게임을
끝냈다.

### 態勢変更의 네 가지 태세 (클라이언트 원문)

| 태세 | 클라이언트 설명 | 권한 mode |
| --- | --- | --- |
| 駐留 | 惑星／要塞に駐留・自陣営に限る | 4 |
| 航行 | 通常モード | 6 |
| 戦闘 | 攻撃性重視、機動性低下 | **아직 없음** |
| 碇泊 | 惑星／要塞軌道上に碇泊 | 5 |

이미 쓰던 mode 번호(4 주둔 / 5 궤도 / 6 항행)를 확인해 주고, 권한 서버에 값이

## 후속 (v70) — 完全修復(0x0C00)에 권한이 생겼다

### 없던 것

0x0C00은 코덱(`OriginalCompletenessRepairCodec`)과 일반 유닛용 저장소 프리미티브
(`RepairOrdinaryUnitsAsync`)는 있었지만 **권한이 없었다**: 아무도 명령을 인가하지
않았고, 아무것도 청구하지 않았고, 플레이어 자신의 기함을 수리하지 않았으며,
타입 자체가 디스패치되지 않았다.

### 규칙

- **160 포인트.** 매뉴얼 커맨드 표가 完全修復을 160으로 매긴다. 어느 풀에서
  빠지는지는 **INFERRED**(함대 수리는 군사 행위)이며 코드에 그렇게 표시했다.

- **격침된 것은 되살리지 않는다.** damaged를 destroyed까지만 내린다. 테이블
  CHECK가 모든 기록 행에 `result_damaged = destroyed`를 강제한다.
- **군수물자 전량 소비** — 기존 일반 유닛 프리미티브와 동일.
- **한 트랜잭션.** 수리·포인트 청구·이력 행이 한 권한 버전에서 함께 커밋되고

  롤백되어 청구 시도가 건드린 포인트까지 흔적을 남기지 않는다.
- **리플레이 안전.** 마이그레이션 0037의 `original_flagship_repair_command`가
  요청 지문으로 키를 잡아 재전송은 첫 결과를 돌려주고 두 번 수리·청구하지 않는다.

거절은 화면에 보인다: 宇宙港に駐留してください / 修復する損害がありません /
