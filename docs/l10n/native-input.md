# 원본 입력란의 코드페이지와 IME 확정 결과

작성자: 최병호 · 2026-10-27

## 수정 경로

원본 편집 버퍼는 ANSI CString이고 포커스를 얻을 때 MFC의 Windows ANSI 변환을 사용한다. 반면 `00507f20`의 표시/편집값 반영 두 곳(`00508092`, `00508137`)은 일본어 CRT 변환 `004eac60`을 호출한다. ACP 949인 시험 호스트에서는 한글 입력 바이트를 일본어로 잘못 해석한다. 두 호출만 Windows ACP→UTF-16으로 바꾸고, 같은 함수의 일본어 IME 상태 문구 호출(`005080c0`)과 원본 리소스 변환은 유지한다. `evidence:client`

편집기의 한/두 바이트 구분 `004fff60`도 일본어 CRT의 출력 가능 문자 판정을 사용한다. 해당 호출 한 곳을 현재 ACP의 DBCS 선행 바이트 판정과 Unicode 문자 분류로 바꿔 CP949 한글의 중간 바이트를 커서/삭제 경계로 사용하지 않게 한다. 호스트 로캘이나 키보드 설정은 바꾸지 않는다. `evidence:client`

`004ff820`의 조합 문자열 없는 확정 분기는 새 IME 이벤트인지 확인한 뒤 결과를 읽지만, 일본어 전각 공백만 인정하고 실제 결과 대신 리터럴 공백을 삽입한다. 이 분기를 실제 확정 문자열 삽입으로 바꿨다. 반환 길이가 양수이며 1,024바이트 임시 버퍼보다 작은지 확인한 뒤 NUL을 쓴다. `004ffb84`에서는 새 IME 이벤트만 처리하고 소비한 이벤트 플래그를 지워 보존된 결과를 다시 넣지 않는다. 처리한 `GCS_RESULTSTR` 메시지는 기본 처리기로 다시 넘기지 않는다. `evidence:client`(원래 분기·호출) / `evidence:guess`(이벤트 소비 보완).

호환 모듈은 기존 EXE 해시 확인과 변경 위치의 원바이트 확인을 모두 통과한 사본에만 설치된다. 원본 EXE·MsgDat는 수정하지 않는다.

## 확인 범위

- x86 빌드와 다른 EXE의 후킹 거부 검사 통과. CP949의 현대 한글 11,172음절 변환 왕복, CP932 일본어, 영문, 잘못된 미완성 바이트의 strict 거부 검사 통과. 이 검사는 전체 글리프의 실제 렌더 확인이 아니다.
- ACP 949 호스트의 비활성 데스크톱에서 실제 CD 클라이언트 하나로 로그인·전략 진입과 기존 일본어 지도/HUD 표시를 확인했다.
- 실제 채팅 입력란에 `한글테스트 ABC 日本`을 한 번 반영하고, 왼쪽 이동·Backspace로 일본어 한 글자를 삭제한 뒤 영문을 추가했다. 이어 한글을 중간에 넣고 같은 조작으로 한 음절을 삭제했다. 네 단계의 실제 CString 내용과 바이트 커서 위치를 대조했고 화면에서도 확인했다.

마지막 검증은 **입력란 구성요소 시험**이다. 소유 프로세스의 UI 스레드에서 `ImmSetCompositionStringW`·`ImmNotifyIME`로 Windows IME 컨텍스트에 결과를 만들고, 시험 API가 생성한 ANSI 호환 `WM_CHAR`를 회수한 뒤 `WM_IME_COMPOSITION(GCS_RESULTSTR)`을 한 번 큐에 넣었다. 제품의 IME API 반환값·문자열 변환·편집/그리기 코드를 시험 훅으로 대체하지 않았다. 다만 이벤트 전달 순서를 시험 드라이버가 제어했으므로 실제 자모 키 입력·조합 중 표시·후보 선택·취소·Enter 동작을 검증한 것으로 취급하지 않는다. `evidence:client`

실행/화면/드라이버 기록은 `work/korean-input-20261027/`에 있다. 최종 검증은 `native-06`, `probe-event-06.log`, `verified-mixed-input.png`, `verified-final.png`이며 이전 실험의 중복 입력·접속 종료 화면과 구분한다. 최종 실행은 원본 해시 불변·소유 프로세스 종료·오디오 복구를 확인했다.

## 남은 연결

- 실제 자모 조합·후보창·취소·한/영 전환과 확정 Enter/전송 Enter의 분리, 붙여넣기·길이 경계 및 모든 입력칸의 저장/재접속 확인.
- 일본어/UTF-8 시스템 ACP 환경의 실제 동작. 원래 편집기는 한/두 바이트 경계를 전제로 하므로 UTF-8 입력 완료를 주장하지 않는다.
- [그리드 채팅](../protocol/grid-chat.md)의 송신 변환·서버 연결을 보완했다. 실제 하나+합성 상대에서 한글 혼합 송신·본인 반송·한글 답장 표시와 전체/동진영 버튼을 확인했다. IME 이벤트를 제어한 시험이라는 한계는 유지하며 두 원본 동시 실행·실제 스폿 한글 송신은 남아 있다.

`KoreanLocalizationTest`에는 실제 CharacterCreation 단계와 코덱을 이용한 한글 12자 성·혼합 이름·기함 이름 등록 및 파일 재개방, 중복·13자 거부, 채팅 65자 마지막 한글과 전체/진영/함대·스폿 왕복, 66자/NUL/지원 밖 문자 거부를 추가했다. Gradle 실행과 실제 입력은 이 작업에서 하지 않았다. 계정·비밀번호의 ASCII 정책은 변경하지 않는다. 편지는 현재 빈 받은편지함 응답 외의 송신·보관 연결이 부족하므로 한글 편지 완료로 처리하지 않는다. 실제 IME 조합·후보·취소·확정 Enter 분리도 이전 미확인 상태를 유지한다.

## 편지·메신저와 IME의 추가 조사 (2026-10-29)

작성: 최병호. `korean-stage2-wt`에서 기존 정적 산출물과 원본을 읽었다. 다음은 송수신 구현 인계이며 편지 완료나 물리 IME 검증 결과가 아니다. 이번 묶음은 원본 입력 상태 머신을 수정하지 않았다.

| 기능 | 코드/메시지 | 현재 서버 연결 |
|---|---|---|
| 주소록 | `0f04/0f05`, 교환 `0f0b`, 삭제 `0f0c` | 초기 빈 목록 응답 외의 실기/저장 미확인 |
| 메신저 | 상태 `0f06/0f07`, 변경/접속 `0f0d/0f0e`, 본문 `0f0f` | 송신/보관 엔진 미연결 |
| 편지 목록 | `0f08/0f09`, 항목 `0f0a` | `GameExchange`는 28바이트 조회에 빈 종료만 반환 |

`004b78a0`의 외부 선택자는 `0x4b`가 메신저, `0x4c`가 편지 송신이다. 내부 switch case 번호를 그대로 쓰면 한 칸 어긋난다. `00543570`의 입력 읽기→`004eacf0`→`004eaaf0`→UTF-16 레코드 복사와 선택자 `0x4b`는 메신저 경로다. 이번 표시 전용 연결을 이 입력/송신 호출로 확대하지 않는다. `evidence:client`

편지 읽기/답장 준비 `0053ba30`은 제목 `+0x25a`와 본문 `+0x35c`의 UTF-16을 ANSI로 바꾸고, 각각 256/1,024바이트의 임시 배열을 거쳐 다시 일본어 디코더로 넘긴다. 이 경로에는 한글 손실과 고정 버퍼 경계 검토가 필요하다. 향후 표시에는 원래 UTF-16을 편집기 setter로 직접 연결하고, 송신에는 ACP 편집 버퍼를 strict CP949로 읽어 wire UTF-16으로 복사하는 방식을 각각 적용한다. 제목/본문에 이름용 내부 표현을 넣거나 표시 후보를 그대로 송신에 재사용하지 않는다. 작성 `0053c1e0`과 메일 수신 레코드/네트워크 직렬화의 길이·NUL·받는 이 ID·권한을 함께 확인한 뒤 서버 구현과 검증해야 한다. `evidence:client`(경로·물리 버퍼) / `evidence:guess`(후속 설계).

IME는 `004e7200`이 COMPOSITION/ENDCOMPOSITION/KEYDOWN/CHAR를 나누고, Enter keydown은 `004ffdc0`에서 제출 대기 플래그를 세운다. END 이벤트는 원본에서 빠르게 반환하며, `004ff820`은 조합/확정 길이와 전역 상태를 함께 사용한다. 기존 훅의 새 확정 이벤트 1회 소비와 제어한 Enter 송신 성공만으로 조합 확정 Enter·Esc 취소·후보 선택을 보장할 수 없다. 조합 중/확정/취소의 이벤트 순서와 native `+0/+1/+3/+0xc/+0xd` 플래그, 전송 대기열을 소유 UI 스레드에서 관찰한 뒤 필요한 수정만 적용한다. 문자열 없는 취소 후 잔류/재삽입, 확정 Enter와 다음 별도 Enter, 최대 길이 직전 조합·마지막 한글 바이트를 실행 담당의 필수 시나리오로 남긴다. `evidence:client`(정적 분기) / `evidence:guess`(검증 시나리오).

## 편지·메신저의 Unicode 표시와 송신 경계 보완 (2026-10-29)

작성: 최병호. `52be4fb` 기반 `E:/logh7/work/korean-stage4-wt`의 구현이다. `mail_text.h`, `mail_input.h`와 설치 연결, guard 후보 및 Python 원본 대조 검사를 추가했다. 원본과 이전 작업 폴더는 보존했고 git·DLL 빌드·guard 실행·서버·게임·Frida는 실행하지 않았다.

원본 `004b4b60`은 편지의 제목과 본문을 별도 UTF-16 풀로 만든 뒤 스택 레코드에 복사한다. 제목 배열은 **128 UTF-16 단위**, 본문은 **512 단위**이며 각각 NUL 한 단위를 포함한다. 제목 다음에는 본문 길이 필드가 있다. 앞 조사의 `+0x25a→+0x35c` 전체 차이 258바이트를 제목 배열 크기로 해석하면 안 된다. 안전한 송신 상한은 제목 127·본문 511 단위다. 이것은 확인한 물리 배열 경계이며 서버의 허용 정책이나 모든 원작 입력란의 설정값을 확정한 것이 아니다. `evidence:client`

표시는 다음 좁은 경로만 바꾼다. 번역 리소스용 사설 글리프나 이름용 4배 확장 표현을 제목·본문에 넣지 않는다.

| 경로 | 보완 내용 |
|---|---|
| 읽기 화면 `0053ad30` | 본문·선택 제목·상대 이름은 이미 원래 UTF-16 풀에 직접 전달되므로 유지. 목록 제목의 ANSI 임시 배열 구간만 건너뛰고 원래 `00505b50` 셀 setter에 UTF-16과 네 칸 들여쓰기 전달 |

| 답장 준비 `0053ba30` | 제목/본문의 ANSI 변환·256/1,024바이트 배열 복사를 모두 건너뛰고 `00505000`에 직접 전달. 받은편지함의 `Re:`와 첫 줄/개행 뒤 `>`를 UTF-16으로 재현하며 끝 개행 뒤에는 `>`를 덧붙이지 않음. 보낸편지함 재사용은 원문 유지 |

제목/본문은 고정 배열 안에서 NUL과 올바른 서로게이트 쌍을 확인한다. 답장 인용으로 길어진 임시 문자열은 동적 UTF-16이며, 원래 편집기 setter의 설정 길이 처리를 그대로 이용한다. 새 정책으로 원문을 ANSI 바이트 수만큼 자르지 않는다. 받는 이와 날짜·버튼·UI 객체 할당을 대체하지 않는다. `evidence:client`(원본 분기·setter·수명) / `evidence:guess`(우회 구현).

편지 송신 두 CALL은 native CString의 ACP 입력을 strict UTF-16으로 먼저 읽고 두 배열 상한을 검사한다. 성공한 동안만 스택 수명의 변환 결과를 thread-local 프레임에 연결한다. 원래 `004b4b60`의 두 풀 변환만 이를 직접 복사하며, 레코드 초기화·ID·길이/NUL·선택자 `0x4c`·전송과 소멸은 원래 코드가 수행한다. 실패는 전체 편지 송신을 건너뛰고 해당 송신 뒤의 편집 모드 종료를 막는다. 원래 UI가 반환값을 검사하지 않으므로 후속 두 모드 전환 CALL도 함께 제한했다. 거부 시 사용자 안내 문구는 추가하지 않았다.

빈 제목에 쓰는 리소스는 원래 두 조회 CALL에서만 Unicode 복원 후 손실 없는 ACP로 변환해 CString에 복사한다. 리소스용 사설 바이트를 송신 제목으로 쓰지 않는다. 본문 줄 접기 `0053ce40`은 일본어 반각 범위를 한 바이트로 취급하므로 `0053ced2` 한 CALL의 선행 바이트 판정도 현재 ACP에 맞춘다. 기존 줄 접기·NUL 추가와 다른 호출은 유지한다.

메신저 Enter/버튼의 두 `004eaaf0` CALL은 같은 strict ACP 변환과 511단위 검사를 거쳐 `004ea8b0`에 복사한다. 실패한 경우에는 원래 풀/CString 정리 지점으로 이동하고 레코드 복사·송신·편집기 지우기를 모두 건너뛴다. 성공 시 원래 선택자 `0x4b`와 받는 이 메타데이터 복사를 유지한다. 호스트 ACP 949를 대상으로 한 구현이며 시스템 로캘을 변경하지 않는다. UTF-8 ACP의 원래 편집기 동작이나 CP949에서 표현할 수 없는 문자의 포커스 왕복을 보장하지 않는다.
