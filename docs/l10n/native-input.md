# 원본 입력란의 코드페이지와 IME 확정 결과

작성자: 최병호 · 2026-10-27

## 수정 경로

원본 편집 버퍼는 ANSI CString이고 포커스를 얻을 때 MFC의 Windows ANSI 변환을 사용한다. 반면 `00507f20`의 표시/편집값 반영 두 곳(`00508092`, `00508137`)은 일본어 CRT 변환 `004eac60`을 호출한다. ACP 949인 시험 호스트에서는 한글 입력 바이트를 일본어로 잘못 해석한다. 두 호출만 Windows ACP→UTF-16으로 바꾸고, 같은 함수의 일본어 IME 상태 문구 호출(`005080c0`)과 원본 리소스 변환은 유지한다. `evidence:client`

편집기의 한/두 바이트 구분 `004fff60`도 일본어 CRT의 출력 가능 문자 판정을 사용한다. 해당 호출 한 곳을 현재 ACP의 DBCS 선행 바이트 판정과 Unicode 문자 분류로 바꿔 CP949 한글의 중간 바이트를 커서/삭제 경계로 사용하지 않게 한다. 호스트 로캘이나 키보드 설정은 바꾸지 않는다. `evidence:client`

`004ff820`의 조합 문자열 없는 확정 분기는 새 IME 이벤트인지 확인한 뒤 결과를 읽지만, 일본어 전각 공백만 인정하고 실제 결과 대신 리터럴 공백을 삽입한다. 이 분기를 실제 확정 문자열 삽입으로 바꿨다. 반환 길이가 양수이며 1,024바이트 임시 버퍼보다 작은지 확인한 뒤 NUL을 쓴다. `004ffb84`에서는 새 IME 이벤트만 처리하고 소비한 이벤트 플래그를 지워 보존된 결과를 다시 넣지 않는다. 처리한 `GCS_RESULTSTR` 메시지는 기본 처리기로 다시 넘기지 않는다. `evidence:client`(원래 분기·호출) / `evidence:guess`(이벤트 소비 보완).

호환 모듈은 기존 EXE 해시 확인과 변경 위치의 원바이트 확인을 모두 통과한 사본에만 설치된다. 원본 EXE·MsgDat는 수정하지 않는다.

## 확인 범위

- x86 빌드와 다른 EXE의 후킹 거부 검사 통과. CP949의 현대 한글 11,172음절 변환 왕복, CP932 일본어, 영문, 잘못된 미완성 바이트의 strict 거부 검사 통과. 이 검사는 전체 글리프의 실제 렌더 확인이 아니다.
- ACP 949 호스트의 비활성 데스크톱에서 실제 CD 클라이언트 하나로 로그인·전략 진입과 기존 일본어 지도/HUD 표시를 확인했다.
- 실제 채팅 입력란에 `한글테스트 ABC 日本`을 한 번 반영하고, 왼쪽 이동·Backspace로 일본어 한 글자를 삭제한 뒤 영문을 추가했다. 이어 한글을 중간에 넣고 같은 조작으로 한 음절을 삭제했다. 네 단계의 실제 CString 내용과 바이트 커서 위치를 대조했고 화면에서도 확인했다.

마지막 검증은 **입력란 구성요소 시험**이다. 소유 프로세스의 UI 스레드에서 `ImmSetCompositionStringW`·`ImmNotifyIME`로 Windows IME 컨텍스트에 결과를 만들고, 시험 API가 생성한 ANSI 호환 `WM_CHAR`를 회수한 뒤 `WM_IME_COMPOSITION(GCS_RESULTSTR)`을 한 번 큐에 넣었다. 제품의 IME API 반환값·문자열 변환·편집/그리기 코드를 시험 훅으로 대체하지 않았다. 다만 이벤트 전달 순서를 시험 드라이버가 제어했으므로 실제 자모 키 입력·조합 중 표시·후보 선택·취소·Enter 동작을 검증한 것으로 취급하지 않는다. `evidence:client`

실행/화면/드라이버 기록은 `work/korean-input-20261027/`에 있다. 최종 검증은 `native-06`, `probe-event-06.log`, `verified-mixed-input.png`, `verified-final.png`이며 이전 실험의 중복 입력·접속 종료 화면과 구분한다. 최종 실행은 원본 해시 불변·소유 프로세스 종료·오디오 복구를 확인했다.

## 남은 연결

- 실제 자모 조합·후보창·취소·한/영 전환과 확정 Enter/전송 Enter의 분리, 붙여넣기·길이 경계 및 모든 입력칸의 저장/재접속 확인.
- 일본어/UTF-8 시스템 ACP 환경의 실제 동작. 원래 편집기는 한/두 바이트 경계를 전제로 하므로 UTF-8 입력 완료를 주장하지 않는다.
- 한글 송신의 UTF-16 보존과 실제 상대 수신. 수신 표시 성공을 송신 성공으로 취급하지 않는다.
- 같은 그리드 채팅 `0f1c` 서버 연결. 시험 중 기본 채널의 Enter가 서버의 `Unsupported game opcode 0xf1c`로 접속을 종료하는 것을 확인했다. 이미 연결된 같은 스폿 `0f1d`와 별도 경로다. 원래 그리드 채팅 규칙·패킷과 송신 변환을 확인하고 연결해야 한다.
