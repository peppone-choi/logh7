## ja-JP에서의 정적 예측과 대안

`FUN_004eac60`은 `Japanese` 문자열로 CRT 로캘 설정 후 멀티바이트→와이드 변환을 호출한다. `FUN_004b0960`은 와이드→멀티바이트 변환(`FUN_005ff87c`) 뒤 `CreateFontA`의 charset 인자 1, `GetTextExtentPoint32A`, `ExtTextOutA`를 사용한다. `FUN_004aec70`에도 charset 1 글꼴 생성 경로가 있다. 따라서 CRT 변환과 GDI 출력은 따로 확인해야 한다. 기존 문서의 LC_CTYPE 표기와 달리 내보내기의 실제 첫 인자는 0이다. 범주 이름은 CRT 식별 없이 확정하지 않는다. `evidence:client` E-405.

`setlocale("Korean")`이 해당 구형 CRT에서 성공하면 CP949 변환을 기대하지만 시스템 ACP 자체를 바꾸지는 않는다. ja-JP/ACP932에서 CP949 글꼴명 `굴림`의 바이트가 ANSI API 경계에서 잘못 해석되고 대체 글꼴이 선택될 수 있다. DEFAULT_CHARSET은 한국어 charset을 보장하지 않으므로 CP949 텍스트도 일본어·반각 문자·대체 글리프로 보일 위험이 높다. 실제 결과는 선택된 글꼴 charset과 코드페이지에 의존하므로 반드시 깨진다고 단정하지 않는다. `evidence:guess`, Microsoft [CreateFontA](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-createfonta), [setlocale](https://learn.microsoft.com/en-us/cpp/c-runtime-library/reference/setlocale-wsetlocale?view=msvc-170), [ExtTextOutA](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-exttextouta) 참조(2026-09-28 확인). 최신 CRT 문서를 2004년 바이너리의 동작 증명으로 취급하지 않는다.

1. **ko-KR 시스템 로캘 + ACP949 + 한국어 글꼴**로 같은 패키지 재시험을 우선한다. UI 언어 변경만으로 대체하지 않으며 재부팅 뒤 ACP를 확인한다. 원래 일본어 리소스와 exe 내장 문자열은 깨질 수 있다. `evidence:guess`.
2. ja-JP 유지가 필요하면 ASCII 글꼴명 `Gulim`과 **HANGEUL_CHARSET=129** 조합을 다음 실험으로 삼는다. ASCII 이름은 글꼴명 바이트 해석 변수를 줄이고 명시적 charset은 GDI 글꼴 선택을 좁힌다. 두 CreateFontA 호출 지점의 명령/인자를 검증한 뒤 사본 패치해야 하며, 이번 패키지에는 charset 코드 패치를 넣지 않았다. 선택된 face/charset와 GDI 출력 바이트를 함께 관찰해야 한다. `evidence:guess`.
3. CP932 전제 길이·줄바꿈 로직 때문에 A안이 실패하면 ADR-0004 B안의 **CP932 슬롯 사설 매핑**을 검토한다. CP932→UTF-16 이후의 역매핑과 실제 한글 출력 경로(와이드 GDI 또는 적절한 CP949/charset)가 함께 필요하다. DAT 바이트 매핑만으로 일본어 글꼴에서 한글이 나오지는 않는다. IME·서버 직렬화도 양방향 매핑이 필요하다. `evidence:guess`.

CP949는 EUC-KR과 완전히 같지 않으며 확장 한글도 표현한다. 이번 표식은 기본 한글 위주라 확장 음절·IME 검증을 대신하지 않는다. `evidence:guess`(PoC 범위).

## 배치와 되돌리기 — 리드 전담

패키지 `manifest.json`의 `relative_path`는 **게스트의 실행 가능한 게임 사본 루트** 기준이다. 추출 설치본의 분리된 exe/data 디렉터리 기준이 아니다. `payload` 아래 파일만 대응 경로에 배치하며 `.patch.json`은 호스트 감사 자료다. `evidence:guess`(실험 절차).

| 상대 경로 | 배치 SHA-256 |
|---|---|
| G7MTClient.exe | 2a901619878512f43982c9199f2ba654af9f203ea27308aea483bcf84a50979a |
| data/MsgDat/constmsg.dat | 4a7735c3c5ac6b424dbd0ca254eea8b8ec96a236ddccf6284891a91718087fac |

해시는 실제 생성 파일에서 계산했다. `evidence:client` E-404.

1. 리드가 클라이언트를 종료하고 VM 스냅샷을 만든다. 게스트 대상 두 파일을 별도 백업하고 해시를 manifest의 `original_sha256`과 비교한다. 다르면 설치본/업데이트 차이를 먼저 확인하고 이 패키지를 덮어쓰지 않는다. `evidence:guess`.
2. guestcontrol로 payload 두 파일을 복사하고 게스트에서 배치 해시를 확인한다. 기존 정상 실행과 같은 호스트 전용 서버·명령행 인자를 사용한다. `evidence:guess`.
3. 되돌릴 때 클라이언트를 종료한 뒤 **배치 직전 게스트 백업** 두 파일을 복원한다. 원본 해시가 일치했던 경우에 한해 패키지 `rollback/`의 두 파일도 같은 결과다. 원본 해시 재확인 후 실행한다. 로캘까지 바꿨다면 VM 스냅샷으로 환경을 복구한다. `evidence:guess`.

### 리드에게 요청: 관찰 기준

- ja-JP 기준 화면과 패치 화면을 파일 스크린샷으로 수집한다. 예상 표식은 `암호 C2426`, `로그인 C2427`, `종료 C2428`; 로그인 후 가능하면 `게임 시작 C2429`와 `캐릭터 없음 C2444`도 확인한다. `evidence:guess`.
- Cnnnn만 보이고 한글이 네모/반각/일본어로 보이면 표식의 로딩은 성공, 글꼴·코드페이지는 실패 후보다. 전체가 안 보이면 화면 소스·배치·초기화 실패를 먼저 분리한다. `evidence:guess`.
- 글자 잘림·겹침·행 높이·긴 안내문 줄바꿈을 확인한다. 표식 접미사 때문에 원문보다 길어진 영향도 구분한다. `evidence:guess`.
- 해당 화면의 원래 토큰이 없으면 토큰 치환 성공을 주장할 수 없다. `candidates.json`의 tokens가 있는 항목 또는 별도 도달 가능한 항목으로 값 치환·줄바꿈을 관찰한다. 코드에서의 토큰 보존 검사는 화면 치환 검증이 아니다. `evidence:guess`.
- ja-JP 실패 후 ko-KR/ACP949에서 같은 두 파일을 재시험한다. 가능하면 CRT 로캘 반환값·선택 face/charset·변환 바이트를 수집한다. 한 화면 성공만으로 채팅 왕복·IME·전체 UI 완료 판정을 하지 않는다. `evidence:guess`.
